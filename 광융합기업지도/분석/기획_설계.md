### 1-2. 문서 행간의 숨은 니즈

- **"상세한 기획 문서가 존재"** — 과업지시서가 꼼꼼합니다. 지오코딩 실패 건 수동 보정, 가상 스크롤, 스케줄러 동기화까지 적혀 있어 **실무를 아는 분이 작성**한 것으로 보입니다. 기획 재작업이 거의 필요 없습니다.
- **공고 제목의 "프로토타입"** — 과업지시서는 완성형 플랫폼인데 공고는 프로토타입입니다. **의뢰자도 전부를 15일에 기대하지는 않는 것**으로 읽힙니다. 다만 문서상 검수 조건이 "100% 구현"이라 그대로 두면 위험합니다(2장 ①).
- **"코스피·코스닥·코넥스 등 연동 가능 기업 外 일반 기업은 엑셀 연동 고려"** — 재무 API의 한계를 이미 인지하고 계십니다. 그런데 **그 '外'가 대부분**이라는 점이 화면 설계를 좌우합니다(2장 ②).
- **IT PM 경험 없음 + 협업 인력 없음** — 기술 판단을 대신해 드려야 합니다. 특히 무엇을 먼저 만들지의 순서.
- **하자보수 6개월** — 장기 관계를 전제하고 있습니다. 1차·2차로 나누는 제안이 오히려 자연스럽습니다.

## 2. 리서치 — 착수 전 확인이 필요한 항목

### ① 과업지시서 전체 범위와 15일 일정이 맞지 않습니다 ★

과업지시서는 **프론트 + 백엔드(Spring/MySQL) + 관리자 + 외부 API 3종 + 산출물 7종 + 하자보수 6개월**을 요구하고, 5.2의 검수 조건은 **"기능 요구사항의 100% 구현"** 입니다. 그런데 공고 기간은 **15일**이고 제목은 **"프로토타입"** 입니다.

이 상태로 계약하면 **검수 기준이 과업지시서 전체**가 되어, 15일 뒤 "미완성"이 됩니다.

**대안 (데모 적용):** **1차 프로토타입 범위를 문서로 확정**하고 계약합니다. 15일에는 지도 탐색 경험의 핵심(클러스터링·다중 필터·상세·재검색·반응형·엑셀·지오코딩 보정)을 **실제 동작하는 수준**으로 만들고, 백엔드 API 서버·외부 데이터 연동·산출물 7종은 2차로 분리합니다. 관리자의 **[범위 구분]** 화면이 그 초안입니다.

> 순서에도 이유가 있습니다. 재무 데이터 커버리지가 확인되어야 화면에서 재무를 어떻게 다룰지가 정해지고, 그에 따라 API 연동 방식과 DB 설계가 달라집니다. 순서를 바꾸면 만들어 놓고 다시 만들게 됩니다.

### ② 금융공공데이터 API로는 대상 기업 대부분의 재무정보를 못 받습니다 ★

[금융위원회 기업 재무정보 API](https://www.data.go.kr/data/15043459/openapi.do)는 **법인등록번호 기준** 조회이며, 재무제표가 공개되는 기업(상장·외부감사 대상 등)만 값이 있습니다. 광융합기업은 **비상장 중소기업이 대부분**입니다.

데모 표본 168개사로 실제 계산한 결과:

| 기업 규모 | API 조회 가능 |
|---|---|
| 대기업 | **100%** |
| 중견기업 | 77.3% |
| **중소기업** | **12.3%** |
| 전체 | 25.0% (재무 미보유 39.3%) |

과업지시서의 "일반 기업 부문은 엑셀 데이터 연동 고려"가 **예외가 아니라 주 경로**가 됩니다.

**대안 (데모 적용):** 재무 항목마다 **`API 연동 / 엑셀 입력 / 미보유` 출처 배지**를 달아, 값이 없는 것이 오류가 아니라 **공개 대상이 아니어서**임을 사용자가 알 수 있게 했습니다. 관리자에 **커버리지 진단 화면**을 넣어 비율을 상시 확인합니다.

### ③ 국민연금 데이터의 "종업원 수"는 기업 단위가 아닙니다

[국민연금 가입 사업장 내역](https://www.data.go.kr/data/3046071/openapi.do)은 **사업장(공장·지점) 단위**로 집계되고 **법인 3인 이상**만 공개됩니다. 본사·공장·연구소가 각각 별도 사업장이라 기업 단위로 바로 쓰면 실제보다 작게 나오고, 3인 미만은 조회되지 않습니다.

**대안 (데모 적용):** 사업자등록번호 기준으로 사업장을 **합산**하고, 미공개 기업은 값을 비운 뒤 **"미공개"** 로 표기해 0명으로 오해되지 않게 했습니다.

### ④ 산업단지 주소는 지오코딩 실패율이 높습니다

과업지시서 3.2에 **"API 변환 실패 건에 대한 수동 좌표 입력 및 수정 기능"** 이 명시되어 있습니다. (구)지번·블록 표기·비표준 건물명이 섞인 산업단지 주소는 자동 변환이 자주 실패하고, **좌표가 틀리면 지도 서비스 전체의 신뢰가 무너집니다.**

**대안 (데모 적용):** **3단계 파이프라인** — ① 자동 변환 ② **신뢰도 판정**(정확/근사/실패) ③ 실패·근사 건만 모아 지도에서 보정. 관리자에서 실제로 동작합니다.

> 참고로 [카카오 지오코딩 무료 쿼터는 월 300만건](https://devtalk.kakao.com/t/api-3/144320)이라 이 규모에서 **비용 문제는 없습니다.** 문제는 비용이 아니라 실패 건을 사람이 확인하는 절차입니다. (근거 없이 리스크를 만들지 않기 위해 확인했습니다.)

### ⑤ 수천 개 마커는 클러스터링 + 가상 스크롤로 해결됩니다

비기능 요구사항 4의 **"데이터 페이징 및 가상 스크롤"** 요구에 대응해 데모에 실제 구현했습니다. 168건 표본에서 **DOM에 그려지는 리스트 행은 항상 11~15개**로 유지됩니다(실측). 실서비스에서는 뷰포트 기준 서버 조회(BBOX 쿼리)를 더합니다.

### ⑥ 외부 API는 실시간 호출이 아니라 스케줄러 동기화가 맞습니다

과업지시서의 협의 사항 판단이 정확합니다. 공공 API는 응답 지연·장애가 잦고 재무·종업원 데이터는 분기/연 단위로만 갱신되므로 실시간일 이유가 없습니다. 화면은 항상 자체 DB를 읽으므로 **외부 API가 죽어도 서비스는 정상 동작**합니다.

## 5. 제안 스택과 견적

**스택 (과업지시서 준수)**
- **React + Spring Boot + MySQL** — 권장 스택 그대로. MySQL은 `POINT` 타입 + **SPATIAL 인덱스**로 BBOX 조회 최적화
- **카카오맵 API** — 국내 주소·POI 정확도가 높고 지오코딩 쿼터가 넉넉함
- **동기화 배치** — 재무 분기 / 종업원 월 / 지오코딩 등록 시점. 화면은 자체 DB만 조회
- SSR(SEO)은 2차. 프로토타입 단계에서는 탐색 경험 검증이 우선

**견적**
