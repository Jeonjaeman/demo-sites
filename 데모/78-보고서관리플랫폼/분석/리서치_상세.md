# 1. 시나리오 기반 니즈 분석 (1단계)

## 1-1. 등장인물

이 프로젝트는 공고가 3개 화면(관리자·고객사·QR조회)이라고 썼지만, **실제 등장인물은 7명**이다.
공고에 이름이 안 나온 4·5·6·7번이 프로젝트를 터뜨리는 쪽이다.

| # | 인물 | 원하는 것 | 불안한 것 | 공고 언급 |
|---|---|---|---|---|
| ① | **임상기관 담당자** (송파구, PM 겸임, 1명) | 시험 끝나면 보고서 올리고 QR 뽑아서 끝. "지난번 보고서 다시 보내달라" 메일이 사라지는 것 | 잘못된 보고서를 잘못된 고객사에 노출 · **개발업체 연락 두절** · 본인 퇴사/휴가 시 아무도 못 씀 | ○ |
| ② | **고객사 브랜드 마케터** | QR을 지금 당장 받아 패키지 시안에 앉히는 것. 인쇄 가능한 벡터 파일 | 인쇄한 뒤 QR이 안 되는 것 · 광고 문구가 식약처에 걸리는 것 | ○ |
| ③ | **고객사 품질·RA 담당** | 식약처가 실증자료를 요구했을 때 **15일 안에** 원본과 시험기관 요건 증빙을 뽑는 것 | 원본 PDF를 못 찾음 · 시험기관 요건(경력 5년 감독자 등) 증빙이 없음 | ✕ (숨은 핵심) |
| ④ | **소비자** (매장·집) | QR 찍고 **3초 안에** "이 제품 진짜로 시험했구나"를 아는 것 | 이상한 사이트로 튀는 것(큐싱) · 영어 논문 같은 PDF가 폰에서 열리는 것 | ○ (화면만) |
| ⑤ | **인쇄·패키지 업체** | 벡터 QR + 최소 크기·여백·색 스펙 | PNG를 확대해 인쇄 → 스캔 실패 → 수만 개 재인쇄 | ✕ |
| ⑥ | **인수인계받을 다음 개발업체** | README·ERD·runbook·발주사 명의 계정·비밀키 위치 | 파악 비용이 재개발 비용과 같아지는 것 | ○ (제안 필수 ④) |
| ⑦ | **식약처 조사관 / 해외 바이어** | 표시·광고가 실증되는지 · 영문으로 확인 가능한지 | — | ✕ |

**한 사람이 두 역할을 겸하는 지점 (권한 설계의 시작점)**
- ①은 **기관 담당자이자 이 플랫폼의 최고관리자이자 발주사 PM**이다. 단일 장애점(SPOF).
- ②와 ③은 **같은 고객사 계정 안의 다른 사람**이다. 마케터는 QR만, RA는 원문 PDF가 필요하다.
  한 계정을 돌려 쓰면 마케터가 원문 전체를 갖게 되고, 퇴사 시 회수가 안 된다.
- 임상기관은 고객사이기도 하다 — 자기 브랜드 제품에 시험을 붙이는 고객사가 생기면 ①과 ②가 겹친다.

## 1-2. 시간순 여정 (발견 → 판단 → 행동 → 대기 → 실행 → 사후)

**같은 보고서 1건을 세 사람이 본다. 보이는 것이 달라야 한다.**

| 항목 | 임상기관 관리자 | 고객사 (인증) | 소비자 (무인증) |
|---|---|---|---|
| 보고서 원문 PDF | ● 전체 | ● 전체 (RA 권한) / ◐ 마케터는 열람만 | ✕ **절대 금지** |
| 시험번호·시험명 | ● | ● | ● |
| 제품명·브랜드 | ● | ● | ● |
| 시험기간·피험자 수 | ● | ● | ● (숫자만) |
| 시험 결과 요약·판정 | ● | ● | ● (승인된 문장만) |
| 시험책임자 성명·경력 | ● | ● | ◐ 기관명만 |
| 피험자 개인정보(연령·성별·사진) | ● | ◐ 가명처리본 | ✕ **절대 금지** |

| 다른 고객사의 보고서 | ● | ✕ | ✕ |
| 유해사례·부작용 기록 | ● | ● | ◐ "유해사례 없음" 등 결론만 |
| QR 발급 이력·스캔 통계 | ● 전체 | ● 자사분만 | ✕ |
| 단가·계약 정보 | ● | ◐ 자사분 | ✕ |

> **공고의 "화면은 하나로 두되 계정에 따라 범위가 달라진다"는 소비자 화면에는 적용되지 않는다.**
> 소비자는 로그인하지 않는다 = 인증 없는 공개 URL이다. 같은 컴포넌트에 권한 플래그만 걸어두면
> 언젠가 반드시 원문이 공개된다. **표면(surface)을 3개로 나누고, 공개 표면은 화이트리스트 방식**이어야 한다.

## 1-4. 명시된 니즈 vs 숨은 니즈

**명시된 니즈**
1. 보고서 등록·관리 (고객사·보고서번호 기준)
2. 보고서별 QR 생성 + 발급 이력
3. 고객사 계정 — 번호 검색·조회·QR 다운로드
4. 권한 분리
5. QR 스캔 조회 화면 (PC·모바일)
6. 기존 자료 업로드
7. 서버·DB·보안·도메인·인증서 신규 구축 (**발주사 명의 계정**)
8. 산출물 5종 (요구사항정의서·화면설계서·소스코드·DB스키마·운영매뉴얼)

**숨은 니즈 (단서 → 도출)**

| 단서 (공고 원문) | 숨은 니즈 |
|---|---|
| "필요한 내용을 간단히 정리한 상태" · "기획 문서가 없어 기획부터" | **의뢰자는 자기가 뭘 원하는지 화면으로 봐야 안다.** 데모가 곧 요구사항 정의서 역할 → 지원 단계에서 화면을 보여주는 쪽이 압도적으로 유리 |
| "IT 프로젝트 관리 경험 없음" · "비개발자가 이해할 수준으로" | **용어를 번역해 줄 파트너**를 원한다. 스택 나열이 아니라 "이걸 쓰면 다음 업체가 붙기 쉽다"는 설명 |
| "구글 드라이브에 올려 QR을 만들어 제공한 적 있음" | **이미 실패를 겪었다.** 링크가 바뀌거나 파일이 지워지면 QR이 죽는 경험. 여기를 정확히 짚으면 신뢰가 생김 |
| "추후에 구독 형태로 제공하려 함" · 준비 중: 구독 조건 | 이번에 결제는 빼되 **구독으로 쪼갤 수 있는 데이터 구조**(조직·플랜·사용량·QR 수명)를 지금 넣어야 한다. 나중에 스키마를 갈아엎으면 QR이 다 죽는다 |
| "개발한 업체와 연락이 끊기면…" (우려 1순위) | **인수인계는 문서가 아니라 화면·계정 소유·자동화로 증명해야 한다.** 이 공고의 승부처 |
| "산출물 완성도 1순위 / 금액 2순위" | 최저가 경쟁이 아니다. **문서 5종의 실물 샘플**을 보여주는 쪽이 이긴다 |
| 결과물: 요구사항정의서·화면설계서·DB스키마·운영매뉴얼 | 문서를 **읽을 사람이 비개발자 1명**이다. 워드 100장이 아니라 화면과 대조되는 문서여야 함 |
| "발급 중인 시험 보고서 양식과 실제 발급 데이터, 고객사 목록" 준비됨 | **데이터 모델을 그들의 양식에 맞춰야 한다.** 시험번호 체계·판정 코드가 이미 존재 → 마이그레이션 없다지만 필드 매핑 협의는 필요 |
| "월 단위 유지보수 의뢰 예정" | 유지보수가 부가가 아니라 **본 계약의 일부**. 월 정액 조건을 지원서에 숫자로 |
| 지원자 111명 | 기능 나열로는 안 보인다. **"당신이 못 본 것"** 한 방이 필요 |

## 1-5. 비는 구멍 (정의가 없는 예외 — 미팅 확인 필요)

공고를 그대로 만들면 아래 15개는 정의가 없어서 **운영 첫 해에 전부 터진다.**

| # | 비는 구멍 | 왜 터지나 | 우리가 제안할 기본값 |
|---|---|---|---|
| 1 | 수만 개 인쇄 후 **보고서가 개정되면?** | 인쇄물은 회수 불가 | 고정 토큰 QR + 버전 관리. QR은 항상 최신 승인본으로 |
| 2 | **도메인이 바뀌면?** (사명 변경·이전) | 정적 QR이면 전부 사망 | 짧은 전용 도메인 1개를 QR 전용으로 고정, 영구 보유 정책 문서화 |
| 3 | **고객사 계약이 끝나면 QR은 살아 있나?** | 시장에 제품이 남아 있음 | "계약 종료 후에도 최소 3년(또는 유통기한+1년) 안내 페이지 유지" 정책 필요 |
| 4 | 보고서 PDF에 **피험자 사진·개인정보**가 있으면 소비자에게 그대로? | 민감정보(건강정보) 무단 공개 | 원본/공개본 2트랙. 공개본은 마스킹 확인 체크 없이는 공개 불가 |
| 5 | **위조 QR·타사 도용** | 위조품에 우리 QR을 붙임 | 공개 화면에 "이 자료가 적용되는 제품"을 명시 + 제보 창구 |
| 6 | **한 보고서에 QR이 여러 개** (제품 여러 SKU / 국문·영문 / 국내·수출) | 스캔 통계·개정 반영이 갈림 | 보고서 1 : QR N 구조. QR마다 라벨·용도·언어 지정 |
| 7 | **소비자에게 어디까지 보이나** (전문 vs 요약) | 정의가 없으면 원문이 나감 | 공개 항목 화이트리스트 + 요약 카드 |
| 8 | **스캔 통계는 누구 것인가** | 고객사가 원할 것(구독 상품의 핵심) | 자사 QR 통계만 고객사에 공개 |
| 9 | **고객사가 여러 브랜드/담당자면?** | 계정 공유 → 퇴사 시 회수 불가 | 조직(고객사) - 브랜드 - 사용자 3계층 + 역할(RA/마케터/뷰어) |
| 10 | **구독 만료 시 QR 처리** | 미납으로 QR을 끄면 제품이 죽은 링크를 달고 유통 | "구독 만료 = 부가정보 차단, 기본 진위확인은 영구 무료" 정책 |
| 11 | **보고서 번호 중복·재사용** | 기관마다 번호 체계가 연도 순환 | 내부 UUID + 표시용 시험번호 분리 |
| 12 | **잘못 발급한 QR 회수** | 오등록 후 이미 인쇄됨 | QR 폐기 상태 + 폐기 사유 안내 페이지 (404 금지) |
| 13 | **누가 원본 PDF를 받아갔나** | 유출 시 추적 불가 | 다운로드 감사로그(계정·시각·IP) + 워터마크 |
| 14 | **담당자 1명이 부재하면** | 등록·발급 전면 정지 | 관리자 2계정 필수 + 위임 |
| 15 | **해외 바이어·수출용** | 영문 요구 | 공개 화면 국/영 2개 언어, QR 파라미터로 분기 |

## [A-1] ★ 최상위 — 정적 QR(파일 URL 직접 인코딩)은 이 프로젝트에서 성립하지 않는다

**발견**
의뢰자가 이미 해 본 방식(구글 드라이브에 올려 QR 생성)은 **정적 QR**이다. 정적 QR은 URL 자체를 코드에 인코딩하므로 대상 URL·도메인·파일이 바뀌면 **이미 인쇄된 코드가 전부 죽는다.** 수만 개가 인쇄된 뒤에는 재인쇄 외에 방법이 없다.

실제 사고: **하인즈(Heinz) 케첩 병 QR** — 2012~2014년 캠페인 종료 후 프로모션 도메인을 갱신하지 않았고, 그 도메인을 성인 사이트 업체가 사들여, 병에 인쇄된 QR을 찍은 소비자가 성인 사이트로 연결됐다. **QR은 완벽하게 스캔됐다. 죽은 것은 도메인이었다.**

또한 Pew Research 조사 기준 2013~2023년 사이 존재하던 웹페이지의 **25%가 2023년 10월 시점에 접근 불가**, 2013년 페이지는 **38%가 소멸**했다. 제품 패키지의 물리적 수명(수개월~수년)이 URL 수명보다 길다.

**근거 URL**
- https://time.com/3928281/heinz-ketchup-bottle-qr-code/
- https://www.campaignlive.co.uk/article/heinz-pr-disaster-qr-codes-ketchup-link-hardcore-porn/1352189
- https://bitly.com/blog/static-vs-dynamic-qr-codes/
- https://www.qrlfy.com/articles/do-qr-codes-expire
- https://scanova.io/blog/how-long-does-qr-code-last/

**우선순위** [A] 그대로 만들면 작동하지 않음

**데모 구현 제안**
- QR은 **파일 URL이 아니라 고정 단축 도메인 + 불변 토큰**으로 발급 — `https://<전용도메인>/r/{token}`.
  토큰은 보고서가 아니라 **"발급 건"에 붙는다.** 보고서가 v2로 바뀌어도 토큰은 그대로.
- 관리자 화면에서 **「v2 게시」 버튼을 누르면, 화면 오른쪽의 QR 미리보기는 그대로인데 공개 화면 내용만 v1→v2로 바뀌는 것**을 데모에서 실제로 보여준다. (같은 QR·다른 내용 — 이게 이 데모의 핵심 데몬스트레이션)
- 「이력」 화면에 `v1 발행 → v2 개정(사유·시각·처리자) → 현재 유효본` 타임라인.
- 「정적 QR로 만들었다면」 비교 토글 — 누르면 같은 시나리오에서 **QR이 404가 되는 모습**을 나란히 보여준다. (의뢰자가 겪은 구글 드라이브 방식을 화면으로 재현)

## [A-2] ★ "화면은 하나, 계정에 따라 범위만 다름"은 소비자 화면에 적용 불가 — 표면 3분리 필요

**발견**
공고 원문: *"화면은 하나로 두되 접속한 계정에 따라 자사 관리자와 고객사가 볼 수 있는 범위가 달라져야 한다."*
이 원칙은 관리자↔고객사 사이에서는 맞다. 그러나 **소비자는 계정이 없다.** QR 스캔 화면은 인증 없는 공개 URL이며, 링크만 알면 전 세계 누구나 연다. 같은 컴포넌트에 권한 플래그만 얹는 구조에서는 플래그 하나 실수로 **고객사 기밀(처방·원료)과 피험자 정보가 영구 공개**된다. 공개 URL은 검색엔진·메신저 프리뷰·캡처로 즉시 확산되어 회수가 불가능하다.

**근거 URL** (권한 3분할·공개표면 화이트리스트 관행)
- https://www.ktr.or.kr/test-report/2018/index.do (KTR: 인증 없는 성적서 조회는 "번호+업체명" 대조로 **존재·상태만** 알려주고 내용은 안 보여줌)
- https://www.ktr.or.kr/test-report/contentsid/961/index.do (위변조 방지 시스템 — 앱으로 시험결과·제품명·접수일·발급일 **한정 항목만** 확인)
- https://info.credly.com/credly-frequently-asked-question (Credly: 공개 배지 = 발급기관 검증 + 최소 항목, 원본 데이터는 비공개)

**우선순위** [A]

**데모 구현 제안**
- 표면을 셋으로 물리적 분리: `admin.html`(기관) / `client.html`(고객사, 인증) / `r.html`(공개, 무인증).
- 공개 표면은 **화이트리스트**: DB에서 `public_fields`에 등록된 키만 렌더. 데모에서 관리자 화면의
  「공개 항목」 체크박스를 끄면 공개 화면에서 **실제로 그 줄이 사라지는 것**을 보여준다.
- 공개 화면 하단에 「이 화면에 표시되지 않는 항목」을 명시(원본 PDF·피험자 정보·처방) — 소비자에게도, 검수자에게도 설계 의도가 보인다.

## [B-1] ★ 화장품법 제14조 표시·광고 실증제 — QR이 연결하는 자료는 "광고의 일부"이고, 책임은 고객사에 있다

**발견**
제품에 인쇄된 QR과 그것이 여는 시험자료는 **화장품 표시·광고**에 해당한다. 화장품법은:
- **제14조(표시·광고 내용의 실증)** — 영업자·판매자는 자기가 행한 표시·광고 중 **사실과 관련한 사항을 실증할 수 있어야** 한다.
- 식약처장이 실증자료 제출을 요청하면 **요청받은 날부터 15일 이내** 제출. 정당한 사유 시 연장 가능.
- 기한 내 미제출하면서 계속 광고하면 → **표시·광고 행위의 중지 명령**.
- **중지명령 위반 시 1년 이하 징역 또는 1천만원 이하 벌금(병과 가능).**
- **제13조(부당한 표시·광고 금지)** 위반 시 → 등록취소·영업소 폐쇄·품목 제조/수입/판매 금지 또는 **1년 범위 업무정지**.

**여기가 핵심이다: 실증 의무를 지는 자는 임상기관이 아니라 「영업자(화장품책임판매업자) = 고객사」다.**
그런데 실증에 필요한 **원본 자료와 시험기관 요건 증빙은 임상기관이 갖고 있다.**
즉 이 플랫폼은 단순 파일 보관함이 아니라 **고객사의 15일 시계를 대신 지켜주는 도구**다. 지원자 111명 중 이 프레임을 잡은 사람은 거의 없을 것이다.

**근거 URL**
- https://easylaw.go.kr/CSP/CnpClsMain.laf?popMenu=ov&csmSeq=1301&ccfNo=4&cciNo=2&cnpClsNo=2 (실증 15일·중지명령·1년/1천만원)
- https://kcia.or.kr/ad/about/law.php (화장품법 제13조·제14조 조문)
- https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=205691 (화장품법 전문)
- https://easylaw.go.kr/CSP/CnpClsMain.laf?popMenu=ov&csmSeq=1301&ccfNo=4&cciNo=2&cnpClsNo=1 (제13조 부당 표시·광고)

**우선순위** [B] 법 위반 소지 — 단, **고객사 쪽 리스크**라서 "우리 고객의 고객을 지켜주는 기능"으로 팔린다

**데모 구현 제안**
- 고객사 보고서 상세에 **「실증자료 패키지 내려받기」** 버튼 — 클릭하면 (i) 원본 보고서 PDF (ii) 시험기관 요건 확인서(기관명·시험책임자·경력·IRB 승인번호) (iii) 발급 증명(발급일·해시·QR 토큰) (iv) 표시·광고 문구 대조표를 **하나의 ZIP으로 실제 생성**(Blob).
- 화면 상단에 **「식약처 실증자료 요청 대응 — 제출기한 D-15」 카운트다운 카드**. 고객사가 "요청 접수" 버튼을 누르면 D-day가 실제로 계산되어 표시되고, 패키지 생성까지 원클릭.
- 보고서 상세에 **「이 자료로 실증 가능한 표현 / 불가능한 표현」** 2열 표를 자동 생성(아래 B-3과 연결).

## [B-2] 실증자료 「요건」 미충족이면 자료가 있어도 실증이 안 된다 — 등록 단계에서 게이트를 걸어야 한다

**발견**
「화장품 표시·광고 실증에 관한 규정」(식약처 고시)과 관련 지침에 따르면 인체적용시험 자료는 다음을 만족해야 실증자료로 인정된다:
- **국내외 대학 또는 화장품 관련 전문 연구기관**에서 시험한 것으로서 **기관의 장이 인정한 기관**에서 수행
- **관련분야 전문의 또는 병원·국내외 대학·화장품 관련 전문연구기관에서 5년 이상 해당분야 시험경력을 가진 자**의 지도 및 감독 하에 수행·평가
- 인체적용시험 **결과보고서에 부작용 등 발생사례 및 발생에 따른 치료·보상 등 조치내역을 포함**하여 기재 (규정 개정으로 명문화)
- 조사자료는 표본설정·질문사항·질문방법이 **통계적 방법**과 일치할 것
- 실증방법은 **학술적으로 널리 인정되거나 업계 표준인 과학적·객관적 방법**일 것
- 제출 시 시험·조사기관 정보(명칭·대표자명·주소·연락처), 실증 내용 및 결과, **영업비밀 해당 여부와 사유**를 함께 기재

즉 **PDF만 올려 두면 "실증자료"가 아니다.** 요건 메타데이터가 함께 있어야 한다.

**근거 URL**

## [B-3] 표시·광고 금지·주의 표현 — QR 옆에 인쇄될 문구가 진짜 리스크다

**발견**
식약처 「화장품 표시·광고 관리 지침(민원인 안내서)」 최신판(2025.8.14) 및 「화장품 광고 자문 기준 및 해설서(2023)」 기준:

## [C-1] 계약 종료·구독 만료 시 QR을 그냥 끄면 안 된다 — "만료 랜딩"이 필수

**발견**
동적 QR은 구독·플랜이 만료되면 **작동을 멈춘다.** 업계에서 2023~2024년 소형 QR 플랫폼 폐업·인수합병으로 그 플랫폼에서 만든 코드가 **복구 불가능하게 죽은 사례**가 다수 보고됐다. 물리 자산(패키지)은 여전히 유통되고 스캔되는데 링크만 죽는 구조다.
이 프로젝트는 **"추후 구독 형태로 제공"**이 명시돼 있으므로, 지금 구조를 잘못 잡으면 **미납 고객사의 제품 수만 개가 죽은 QR을 달고 매대에 남는다.** 이건 임상기관의 브랜드 사고가 된다.

**근거 URL**
- https://www.qrlfy.com/articles/do-qr-codes-expire
- https://qrcodekit.com/news/dynamic-qr-code-expired/
- https://www.qrcodechimp.com/do-qr-codes-expire/
- https://time.com/3928281/heinz-ketchup-bottle-qr-code/ (도메인 만료 사고)

**우선순위** [C] 운영 중 반드시 터짐 (+ 구독 전환 전제라 [A]에 가까움)

**데모 구현 제안**

## [C-2] 큐싱(Quishing)·QR 도용 — 공개 화면 자체가 "진짜임"을 증명해야 한다

**발견**
QR 피싱(큐싱)은 KISA·금융보안원이 지속 경고 중인 위협이다. **정품 QR 위에 가짜 QR 스티커를 덧붙이는** 수법, 정부기관 사칭 QR로 악성앱 설치를 유도하는 사례가 보고됐고, 2023년 기준 QR 관련 피싱 신고가 전년 대비 60% 이상 증가한 것으로 알려져 있다.
이 프로젝트 고유의 위험은 두 가지다: ① 소비자가 우리 QR을 위조 QR과 구별할 방법이 없다 ② **타사가 우리 보고서 URL을 자기 제품에 도용**해도 막을 방법이 없다(URL은 공개니까).

**근거 URL**

- https://www.skshieldus.com/security-insights/trends/qr-code-quishing-checklist
- https://www.ahnlab.com/ko/contents/content-center/34280
- https://m.boannews.com/html/detail.html?idx=135364

**우선순위** [C]

**데모 구현 제안**

- 문서 **SHA-256 해시 표시 + 대조** — 소비자/고객사가 받은 PDF의 해시를 붙여 넣으면 일치 여부를 즉시 판정.

## [C-3] QR 인쇄 물리 스펙 — PNG 한 장만 주면 수만 개가 안 찍힌다

**발견**
- 인쇄물 최소 크기: **2×2cm 권장**, 절대 최소 1.5cm(무광지·양호한 조명·최신 폰·짧은 URL 조건에서만).
- 모듈(점) 크기: 최종 인쇄 기준 **0.1~0.15mm 이상**이어야 카메라가 분해.
- **Quiet zone(여백) = 모듈 폭 × 4.** 모듈 0.5mm면 사방 2mm 이상 흰 여백.
- 스캔 거리 ≤ 코드 폭 × 10.
- 오류보정 레벨: L 7% / M 15% / Q 25% / H 30% 복원. **작은 코드는 L·M**, H가 필요하면 인쇄 크기를 최소 30% 키워야 함.
- 정적 QR은 긴 URL을 그대로 인코딩해 **모듈이 조밀해지고 소형 패키지에서 스캔률이 떨어진다.** 동적 QR(짧은 토큰)은 격자가 성기어 작게 인쇄해도 잘 읽힌다 — [A-1]의 부수 이점.

**근거 URL**
- https://www.uniqode.com/blog/qr-code-best-practices/how-to-perfectly-size-your-qr-codes
- https://wavecnct.com/blogs/how-small-can-a-qr-code-be
- https://linkbreakers.com/help/article/qr-code-size-and-print-dimension-benchmarks
- https://www.supercode.com/blog/dynamic-vs-static-qr-codes

**우선순위** [C]

**데모 구현 제안**
- QR 다운로드를 **「인쇄 패키지」**로 제공: `SVG(벡터) · EPS · PNG 300dpi · 사양서 PDF`.
  사양서에 최소 크기(mm)·quiet zone·오류보정 레벨·권장 색(단색 K100)·금지사항(그라디언트·저대비·로고 과다 삽입)을 명시.
- 다운로드 전 **「인쇄 크기 시뮬레이터」** — 슬라이더로 10~30mm를 움직이면 화면에서 QR이 실제 mm 크기로 그려지고,
  **모듈 크기(mm)와 스캔 가능 거리(cm)가 실시간 계산**되어 표시된다. 임계값 아래로 내리면 경고 배너.
  (하드코딩 금지 — 버전·모듈 수·오류보정으로 실제 계산)
- 「이 QR에 담긴 문자 수 / 코드 버전 / 모듈 수」를 함께 표시해 정적 vs 동적 차이를 눈으로 보여준다.

## [C-4] 스캔 통계는 봇을 걸러야 숫자가 의미를 갖는다 (구독 상품의 핵심 가치)

**발견**
QR 랜딩 URL은 카카오톡·슬랙·메신저 링크 프리뷰 봇, 검색엔진 크롤러, 보안 스캐너가 자동으로 긁는다. 필터 없이 집계하면 **실제 소비자 스캔이 아닌 접속이 통계에 섞여** 고객사에 잘못된 숫자를 준다. 구독 상품에서 스캔 통계가 핵심 가치가 될 가능성이 높으므로(고객사가 "우리 제품 QR이 몇 번 찍혔나"를 원함) 초기 설계에 넣어야 한다.
동시에, 접속 로그(IP·쿠키·기기정보)는 다른 정보와 결합 시 개인정보에 해당할 수 있다는 것이 개인정보보호위원회의 입장이므로 **최소 수집 원칙**을 지켜야 한다.

**근거 URL**
- https://inpyeonglaw.com/archives/20897/ (쿠키·행태정보의 개인정보 해당성, 개인정보위 입장)
- https://www.qr-code-generator.com/blog/do-qr-codes-expire/
- https://bitly.com/blog/static-vs-dynamic-qr-codes/ (동적 QR의 스캔 추적)

**우선순위** [C]

**데모 구현 제안**
- 스캔 로그를 **원시 / 유효** 2개로 나눠 보여준다. 「봇 제외」 토글을 누르면 그래프가 **실제로 다시 계산**되어 낮아진다.
  (판정 기준: UA 패턴·헤드리스·동일 IP 연속·referrer 프리뷰 — 데모에서는 mock 로그에 플래그를 넣고 진짜 필터링)

- 고객사 화면에는 **자사 QR 통계만** 보이게(역할별 시야 차이 구현 증거).

## [C-5] 관리자 1명 = 단일 장애점 / 고객사 계정 공유 = 퇴사 시 회수 불가

## [C-6] ★ 인수인계는 문서가 아니라 "화면"으로 증명해야 한다 — 이 공고의 승부처

**발견**
외주 개발 소스코드 분쟁은 **계약서에 소유권·인수인계를 명시하지 않아** 발생하며, 특히 개발 완료 후 운영·유지보수·고도화를 고려하지 않은 경우가 많다. 다른 개발사로 넘어갈 때 **소스코드와 각종 계정 소유권**을 반드시 확인해야 한다는 것이 업계 공통 지적이다.
하자보수는 통상 **검수 종료 시점부터 1~3개월** 무상이고 이후는 별도 과금이며, 유지보수 계약은 개발 계약과 별개로 **월정액**으로 맺는 것이 관행이다.
국내 홈페이지 유지보수 시세는 **월 5만 원대(텍스트·이미지 교체) ~ 20만 원대(구조·SSL·업데이트) ~ 100만 원대(신규 기능·DB 연동·성능 최적화)** 범위로 형성돼 있다.

## [C-7] 보고서 개정·재발급의 문서 관리 관행 — 버전은 반드시 이력으로 남는다

**발견**
시험성적서·분석성적서(COA) 발급 관행에서 **개정·재발급 이력 관리와 감사증적(audit trail)은 표준**이다.
LIMS는 시료·시험·결과·승인 이력을 감시증적과 함께 관리하며, 계산값은 **버전 관리 객체**로 다룬다.
식약처는 통합 LIMS에서 **전자 시험·검사성적서를 발급하고 정부24와 연계**해 의뢰인이 언제 어디서나 발급·열람·저장·제3자 제출을 할 수 있도록 개선했다 — **국가기관이 이미 "전자성적서 + 온라인 제3자 제출" 모델로 가고 있다.**
KTR은 성적서 위변조 방지를 위해 특수용지·홀로그램·QR을 써 왔고, **블록체인 기반 디지털 시험성적서**로 전환했다.

**근거 URL**
- https://www.foodtoday.or.kr/news/article.html?no=199712 (식약처 LIMS 전자성적서 + 정부24 연계)
- https://zdnet.co.kr/view/?no=20221129141316 (KTR 시험성적서 블록체인 도입)
- https://www.ktr.or.kr/test-report/contentsid/961/index.do (KTR 위변조 방지 시스템)
- https://sgsystemsglobal.com/glossary/lims-laboratory-information-management-system/

**우선순위** [C]

**데모 구현 제안**
- 보고서 상세에 **버전 타임라인** (v1 발행 → v2 개정: 사유·변경 요약·처리자·시각). 각 버전의 **SHA-256 해시** 표시.

## [참고] 표준 관행 — 진위확인 화면의 문법 (KTR·Credly)

**KTR 시험성적서 조회 (2018년~) — 국내 표준 문법**
- 입력: **성적서 번호(연도-번호)** + **업체(공장)명** + 언어(국문/영문)
- 안내 문구: "접수 연도와 번호 및 업체(공장)명을 입력 후 확인 버튼을 클릭하면 내용이 나타납니다"
- 결과: 진행상태(시험진행중/시험완료), 접수진행상태(미발급/발급준비/발급완료)
- **위변조 확인 메뉴가 별도로 존재** — 조회와 진위확인이 분리돼 있다
- 위변조 방지: 특수용지(은화·워터마크)·홀로그램(복사 시 은색→검정)·QR·온라인 상시 확인 시스템 → **블록체인 디지털 성적서**로 전환

**Credly / Accredible — 글로벌 자격 검증 문법**
- 모든 **발급기관이 검증**되고, 모든 자격이 "발급기관이 이 자격을 실제로 만들었는가"로 검증됨
- 공개 배지 페이지에 **Verify 버튼** — 클릭 한 번으로 제3자가 진위 확인
- 배지 자체는 최소 정보만, 상세는 발급기관 페이지로

> **가져올 문법**: ① 조회는 `번호 + 소유자명` 2개 키 대조 ② 진위확인 메뉴를 조회와 분리 ③ 공개 화면은 "발급기관 검증"을 최상단에 ④ 상태를 명시적 라벨로 (진행중/발급완료/개정/만료)

## 6. 미팅에서 반드시 물어야 할 것 (지원서 "의뢰자 확인 필요" 항목 후보)

1. **보고서 개정이 실제로 얼마나 자주 발생하나?** (연 몇 건) → 버전 정책의 강도 결정
2. **소비자에게 어디까지 보일 것인가** — 요약만 / 결과 그래프까지 / 원문 PDF까지. **기본값은 "요약만"으로 제안**
3. **고객사 계약 종료 후 QR 유지 기간** — 제품 유통기한 + α. 기본값 제안: **종료 후 3년**
4. **한 고객사에 담당자가 몇 명인가** — 권한 계층 확정
5. **시험번호 체계** (연도 순환 여부·중복 가능성) → 내부 UUID 필요성
6. **보고서 PDF에 피험자 사진·개인정보가 실제로 포함되는가** → 공개본 분리 방식 결정
7. **구독 상품의 과금 단위** (고객사당 / 보고서당 / QR당 / 스캔 수) → 지금 스키마에 반영해야 함
8. **참고 자료 1**(미팅 예정 파트너 공개분)의 내용
9. 기존 구글 드라이브 QR이 **이미 인쇄돼 유통 중인 제품이 있는가** → 있다면 **레거시 QR 인수 경로**가 필요
10. 발주사 명의 계정 개설 주체(사업자 정보·결제수단) 및 도메인 희망 문자열
