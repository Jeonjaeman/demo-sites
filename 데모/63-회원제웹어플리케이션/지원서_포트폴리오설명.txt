[1] 회원제 커뮤니티 웹앱 (본 공고 대응 데모)
https://jeonjaeman.github.io/demo-sites/incircle/
https://jeonjaeman.github.io/demo-sites/incircle/admin/

- 진행 과정
  공고의 요구를 사용 흐름으로 재구성해 빠진 상태(승인 거절
  통보·탈퇴 게시물·워터마크 대상 범위)를 찾고, 리서치로 함정
  세 곳(유튜브 임베드와 보안 요구의 모순, 승인제와 Supabase
  Auth의 충돌, 신고·블라인드의 법정 절차)을 근거와 함께 확인한
  뒤, 인프런·Discourse·Skool·클리앙의 게시판 문법과 Awwwards
  수상작 2곳·GDWEB 수상작 1곳을 브라우저로 실측해 구축했습니다.
- 특징
  "권한 3단계"를 숫자 하나가 아니라 게시판 6종×액션 4종의
  72칸 매트릭스로 정의하고, 화면 상단의 계정 상태 전환기로
  6개 시야(비로그인/승인대기/1·2·3등급/관리자)가 같은 데이터를
  얼마나 다르게 보는지 — RLS 정책 SQL과 반환 행수까지 — 직접
  확인하게 만들었습니다. 이 구조가 곧 귀사 프로젝트의 설계
  초안입니다.
- 핵심 요소
  계정 상태 전환기(시야별 게시판·버튼 실전환), 게시판 밀도
  3종(일반 5열·카드·갤러리), 영상 보호 3안 비용 실계산, canvas
  워터마크 파일 각인 다운로드와 유출본 역추적, 서명 URL 만료
  카운트다운, 신고 44조의2 상태머신, 승인 큐 24시간 SLA, 공지
  CMS(즉시/예약), 마스킹 방식별 API 응답 대조, RLS 성능
  시뮬레이터(70명→4,000명), 42P17 재귀 진단기, 보안 자가진단
  8항목, 리전별 국외이전 판정·처리방침 문구 생성, 활동 로그
  보존 카운터·삭제 잠금.

  대응.

[3] 학원 통합 관리 시스템 (실운영 · 권한 3단계 · 1인 운영자)
https://jeonjaeman.github.io/dojang-live/

- 진행 과정
  실제 계약해 운영까지 올린 프로젝트입니다. 원장·강사·데스크
  3단계 권한으로 담당 범위만 조회되는 구조를 설계했고, 수정
  요청 당일 반영 체계로 운영 중입니다.
- 특징
  귀사 공고와 같은 조건이 두 가지 겹칩니다 — 등급별 접근
  제어(3단계 권한)와 운영 인력 1인. 매뉴얼이 화면 밖에 있으면
  안 쓰인다는 것을 실운영에서 배웠고, 그래서 본 공고 데모의
  운영 매뉴얼을 관리자 화면 안에 내장했습니다.
- 핵심 요소
  3단계 권한 분리, 담당 범위만 조회, 출결·수납·상담 기록,
  실운영 유지보수.

[공통 진행 방식]
① 기능 목록을 사용 흐름으로 재구성해 빠진 상태를 찾고 ② 웹
리서치로 함정(법·기술·운영)을 근거와 함께 확인하고 ③ 도메인
서비스와 어워드 수상작을 브라우저로 실측해 수치로 디자인하고
④ 발견을 동작하는 기능으로 구현하고 ⑤ 콘솔·모바일·연산을
실측으로 검증합니다. 본 공고 데모에서도 검증 중 관리자 화면
3개 탭의 모바일 가로 넘침과 공지 CMS 누락을 자체 발견해
고쳤습니다. 실제 프로젝트도 같은 과정으로 진행합니다 — 착수
1~2주의 화면설계서·DB 설계 확정 단계에서 게시판 6종의 정체와
영상 보호 방식부터 함께 정리해 드리겠습니다.
