## 1. 시나리오 기반 니즈 분석

### 1-1. 등장인물

| # | 인물 | 누구인가 | 무엇을 원하나 | 무엇을 불안해하나 |
|---|---|---|---|---|
| ① | **발주기관 계약 담당 주무관** | 국가유산 수리공사를 발주한 지자체·국가유산청 소속. 업체가 제출한 계약보증서·하자보수보증서를 접수·검토 | 눈앞의 종이(또는 PDF) 보증서가 **진짜인지 3분 안에 확인**하고 결재 올리기 | 위조 보증서를 통과시켰다가 사고가 나면 **본인 책임**. 조합에 전화해 확인한 것은 기록이 안 남음 |
| ② | **국가유산 수리업체 실무자 (조합원)** | 소규모 전문업체. 대표+직원 3~10명 수준, 사무직 1명이 계약·보증·세무를 겸함 | 보증서를 **오늘 안에** 발급받아 발주처에 제출 | 인증서가 안 먹힌다 · 어느 메뉴로 가야 할지 모르겠다 · 마감이 오늘이다 |
| ③ | **수리업 신규 진입 예정자** | 국가유산수리업 등록을 준비 중. 조합 가입 여부를 검토 | 조합이 뭘 해주는지 · 가입 조건·출자금·수수료가 얼마인지 | 잘못 알고 가입했다가 등록이 반려될까 봐. **전화하기 전에 웹에서 다 알고 싶다** |
| ④ | **조합 실무 담당자 (요구사항 확정·검수)** | 이번 프로젝트 창구 1명. IT 비전공 | 민원 전화를 줄이고 · 오픈 후 **본인이 직접** 공지·팝업을 올리는 것 | 개발 용어를 못 알아들어 검수를 못 함 · 오픈 후 개발사가 사라지면 아무것도 못 고침 |
| ⑤ | **조합 관리자 / 전산 겸임자** | 전담 전산 인력 없음. 총무·기획 인력이 겸임 | 계정·권한·게시물이 사고 없이 굴러가는 것 | 관리자 계정이 털리면? 자료실에 개인정보 파일이 올라가면? **책임 소재가 본인** |
| ⑥ | **일반 국민·언론·유관기관** | 조합 개요, 임원, 공시, 채용을 확인 | 기관 개요·연락처를 빠르게 | (거의 없음 — 그러나 **첫인상이 조합의 신뢰도** 그 자체) |
| ⑦ | **기존 인터넷 영업점 운영 벤더** | 현 시스템을 만들고 유지보수 중인 제3자 | 자기 시스템이 안 망가지는 것 | 남이 자기 시스템에 손대는 것. **협조 여부가 이 프로젝트의 최대 외부 변수** |

> ★ 겸업 지점: ②와 ③은 **같은 사람이 시기만 다른 것**이고, ④와 ⑤도 **같은 담당자 1명**일 확률이 높다.
> 즉 "비회원 화면"과 "회원 화면", "콘텐츠 관리자"와 "시스템 관리자"를 완전히 분리해 설계하면
> 실제로는 한 사람이 두 개의 매뉴얼을 들고 헤매게 된다. → **역할 전환이 화면 안에서 자연스러워야 한다.**

### 1-2. 시간순 여정

#### 여정 A — 발주기관 주무관의 "보증서 진위 확인" (이 사이트의 존재 이유 1순위)

| 단계 | 상황 | 쓰는 화면 | 이 기능이 없으면 |
|---|---|---|---|
| **발견** | 업체가 계약보증서를 제출. 조합 이름은 처음 봄 | 검색엔진 → 조합 **메인** | 조합명을 검색해도 회원 로그인 화면이 먼저 나와 "여기가 맞나?" 하고 이탈 → **조합에 확인 전화** |
| **판단** | "여기서 진위 확인이 되나?" 30초 안에 판단 | 메인의 **발급사실 조회 진입 블록**(상단 고정) | 메뉴를 3번 클릭해도 못 찾음. 현재 홈페이지가 조합소개+회원업무 혼재라 생기는 민원의 실체가 이것 |
| **행동** | 보증서에 적힌 번호·금액·일자를 입력 | **발급사실 조회 폼** | 입력 항목이 증권번호 하나뿐이면 → 옆 자리 다른 업체 보증서도 번호만 바꿔 다 보인다 (§2 F2) |
| **대기** | 조회 실행 | 결과 화면 | 조회 실패 시 "왜 실패했는지"(번호 오류 / 금액 불일치 / 해지된 증서)가 구분 안 되면 **무조건 전화** |
| **실행** | 결과를 결재 문서에 첨부 | **조회 확인서 출력(PDF/인쇄)** | 화면 스크린샷을 찍어 붙임 → 감사 때 증빙력 없음 → 다시 전화 (§2 F12) |
| **사후** | 3개월 뒤 하자보수 시점에 재확인 | 확인서의 **검증번호 재조회** | 처음부터 다시 입력. 보증서 원본을 이미 반납해 번호를 모름 |

#### 여정 B — 조합원(수리업체)의 "보증서 발급" (오늘 안에 끝내야 함)

| 단계 | 상황 | 쓰는 화면 | 이 기능이 없으면 |
|---|---|---|---|
| **발견** | 발주처가 "내일까지 계약보증서" 요구 | 조합 **메인 → 조합업무 > 보증** | 어떤 보증인지(계약/선금/하자/지급) 구분을 못 해 **전화 문의** |
| **판단** | 필요 서류·수수료·소요시간 확인 | **조합업무 상세** (구비서류·요율·처리시간) | 서류 하나 빠뜨려 재방문·재접수 |
| **행동** | 로그인 시도 | **공동인증서 로그인** | ⚠️ 여기가 실제 민원 1위 지점 — 인증서가 이 브라우저에 없음 / 용도제한 인증서라 거부 / 팝업 차단 (§2 F4·F11) |
| **대기** | 인증 통과 후 회원 업무 화면으로 이동 | **영업점 인계(브리지)** | 대표 홈페이지에서 로그인했는데 영업점에서 **또 로그인**을 요구 → "왜 두 번 하냐"는 민원 (§2 F5) |
| **실행** | 인터넷 영업점에서 보증 신청·발급 | (기존 시스템 — 이번 범위 밖) | — |
| **사후** | 발급된 증서를 발주처에 제출, 발주처가 조회 | 여정 A로 연결 | 조회가 안 되면 조합원이 **다시 조합에 전화** (같은 건으로 전화가 2번) |

#### 여정 C — 조합 담당자의 "오픈 준비 → 일상 운영" (공고의 최대 우려가 사는 곳)

| 단계 | 상황 | 쓰는 화면 | 이 기능이 없으면 |
|---|---|---|---|
| **발견** | 오픈 전, 초기 게시글을 직접 등록해야 함 (공고 45줄) | **관리자 > 대시보드 오픈 체크리스트** | 무엇을 몇 건 넣어야 하는지 몰라 오픈이 밀림. **일정 지연 1순위 원인** |
| **판단** | 어디까지 내가 고칠 수 있나 | **관리자 > 직접 수정 가능 영역 지도** | "이건 개발사에 요청해야 하나?"를 매번 물어봄 → 유지보수 청구 폭증 |
| **행동** | 공지 등록 · 팝업 게시 · 배너 교체 | 콘텐츠 편집기 (미리보기 → 발행) | 편집기에서 깨진 HTML을 붙여 넣어 **공개 화면이 무너짐**. 되돌리기 없으면 복구 불가 |
| **대기** | 게시 후 확인 | 버전 이력 · 되돌리기 | 잘못 올린 글을 못 되돌림 |
| **실행** | 팝업이 행사 종료 후에도 계속 뜸 | **게시 종료일 필수 + 만료 임박 위젯** | 지난 공고 팝업이 몇 달째 떠 있음 — 기관 사이트의 고전적 사고 (§2 F9) |
| **사후** | 자료실에 서식 파일 업로드 | **업로드 전 개인정보 검사** | 개인정보 포함 원본 파일 게시 → 72시간 내 유출신고 의무 (§2 F7) |

### 1-3. 역할별 시야 차이 (= 권한 설계의 핵심)

같은 **"보증서 1건"** 데이터를 역할에 따라 다르게 봐야 합니다. 이 표가 곧 API 응답 스키마입니다.

| 데이터 항목 | ① 발주기관(비회원) | ② 조합원 본인 | ④ 조합 콘텐츠 담당 | ⑤ 조합 최고관리자 |
|---|---|---|---|---|
| 증권번호 | 입력값과 **일치 여부만** | 전체 | 접근 불가 | 전체 |
| 조합원 상호 | 앞 2자 + 마스킹 (`대○○○`) | 전체 | 접근 불가 | 전체 |
| 사업자등록번호 | 입력 대조용 (표시 안 함) | 전체 | 접근 불가 | 전체 |
| 대표자명·주소·연락처 | **표시 금지** (개인정보) | 본인분만 | 접근 불가 | 전체 |
| 보증금액 | 입력값 대조 결과만 (`일치`) | 전체 | 접근 불가 | 전체 |
| 보증채권자(발주처) | 본인 기관일 때만 | 전체 | 접근 불가 | 전체 |
| 발급/만료일 | 유효 여부 (`유효`/`만료`/`해지`) | 전체 | 접근 불가 | 전체 |
| 조회 로그(누가·언제·어떤 IP) | 없음 | 본인 증서 피조회 이력 | 없음 | 전체 + 이상징후 |
| 공지·자료실 게시 | 읽기 | 읽기 | 쓰기·발행 | 쓰기·발행·삭제 |
| 계정·IP 허용목록 | — | — | **불가** | 가능 |

> 핵심: **④ 콘텐츠 담당자는 증서 데이터에 접근할 이유가 전혀 없습니다.**
> 관리자 화면을 하나로 만들고 "관리자면 다 본다"로 설계하면, 홈페이지 담당자가
> 전 조합원의 보증 내역을 볼 수 있게 됩니다. 권한 2단 분리가 필수입니다.

### 1-4. 명시된 니즈 vs 숨은 니즈

**명시된 니즈**
1. 대외용 대표 홈페이지 신규 구축 (조합소개·조합업무·자료실·고객센터·공지사항·발급사실 조회)
2. 반응형 (PC·모바일)

### ① 그대로 만들면 작동하지 않음

#### F1. "기존 발급사실 조회 기능을 최대한 활용"이 성립하려면 조회 API가 있어야 하는데, 있다는 근거가 없다

**발견.** 공고는 "기존 홈페이지의 관련 기능을 최대한 활용해 연계"(42줄)라고만 적혀 있습니다.
그런데 국내 공제조합의 실제 구현을 보면, 발급사실 조회는 **대표 홈페이지가 아니라 인터넷창구(사이버창구) 쪽 레거시 화면**에 붙어 있습니다.

- 건설공제조합: 대표 홈페이지(`www.cgbest.co.kr`) 「고객센터 > 발급사실조회/통지」에 **10종 메뉴**(보증서 출력, 보증서발급 사실조회, 보증채권자별 보증발급조회, 임대차연체사실 통지, 현장별 하도급대금지급보증 공시조회, 건설기계대여대금지급보증 현장별보증 공시조회, (보증가능금액/자본금)확인서발급 사실조회, 공제증권발급 사실조회, 제증명발급 사실조회, 개인신용정보조회 사실조회)가 있으나, **실제 처리는 인터넷창구 `cyberbiz.cgbest.co.kr`** 로 넘어갑니다.
  근거: https://www.cgbest.co.kr/cgbest/customers/inquiry.do
- 전문건설공제조합(K-FINCO): 대표 홈페이지 「고객지원 > 발급사실/진행현황」에 Vue 레이어 팝업으로 붙어 있는데, 소스에 **`scrMbrno` · `scrBocod` · `scrBogyy` · `scrBogno` · `scrGbgyy` · `scrGbgno` 같은 레거시 전문(電文) 파라미터가 hidden input으로 그대로** 넘어갑니다. 즉 신규 대표 홈페이지가 **기존 시스템의 내부 필드명을 알고 있어야** 조회가 성립합니다.
  근거: https://www.kfinco.co.kr/cs/status (2026-09-01 소스 확인)

→ **API가 아니라 "화면 + 내부 파라미터 규약"인 경우가 표준입니다.** 계약 시점에 이걸 모르면 공수 산정이 통째로 틀립니다. 공개 문의 1건(`killingfield`, 2026.08.27)이 정확히 이 질문을 했고 **클라이언트는 답을 못 했습니다.**

**데모 구현안 — 「연계 방식 시뮬레이터」 (verify.html + admin.html)**
- 발급사실 조회 페이지 상단에 **연계 모드 3단 폴백을 실제 토글**로 배치:
  ① `신규 조회 API` ② `기존 영업점 화면 연계(리디렉트/새창)` ③ `야간 배치 미러 DB(읽기전용 복제)`
- 모드를 바꾸면 **화면이 실제로 바뀝니다** — 응답 소요시간, 데이터 기준시각(`실시간` / `오늘 03:00 기준`), 영업점 점검 중일 때의 동작, 조회 가능 항목 수가 모드마다 다르게 렌더링.
- 관리자에 **「연계 가능성 진단」** — 조합의 현재 조건 6개(같은 루트 도메인인가 / 기존 벤더 협조 가능한가 / DB 직접 접근 가능한가 / 조회 전용 계정 발급 가능한가 / 인증 모듈 종류 / SSL 구성)를 체크하면 **점수가 실제 계산되어 권고 모드가 바뀝니다.**
- 어느 모드에서도 실패할 때의 **대체 화면**(점검 안내 + 유선/팩스 확인 절차 + 예상 복구 시각)까지 구현.

#### F2. 조회 입력값을 "증권번호 하나"로 설계하면 번호를 1씩 올려가며 전 조합원의 영업정보를 긁을 수 있다

**발견.** 업계 표준은 **다중 항목 대조**입니다. 실측 결과:

- **엔지니어링공제조합** 「발급증권사실조회」: **증권종류 + 증권번호 + 발급일자 + 보증금액**(하이픈·콤마·마침표 제외)이 **전부 필수 입력**.
  근거: https://www.egic.co.kr/jsp/manual/manual04.jsp
- **전문건설공제조합** 발급사실 조회 팝업(소스 실측): **보증번호(2분할) + 사업자번호 + 상호명 + 보증금액 + 발급일자**. 상호명에는 유효성 검사까지 붙어 있습니다 — "두 글자 이상", "특수문자 불가", **"법인격 표기(주식회사·(주) 등)만 입력 불가"**(= `(주)`만 넣고 긁는 것을 차단).
  근거: https://www.kfinco.co.kr/cs/status
- 즉 **보증서 실물을 손에 든 사람만 통과할 수 있게** 입력값을 설계하는 것이 이 업계의 확립된 관행입니다.

**법적 축.** 조회 결과에 대표자명·주소를 붙이면 개인정보 제공이 됩니다. **개인사업자의 사업자등록번호는 개인정보에 해당**(법인은 해당 없음)한다는 것이 통설입니다.
근거: https://www.lawmeca.com/17108-사업자-등록번호도-개인정보인지의여부/
공고는 "회원가입이나 로그인 없이 누구나 접근"(41줄)을 요구하므로 **무인증 조회**가 전제입니다 — 남용 방지 장치가 없으면 그대로 크롤링 표적이 됩니다.

**데모 구현안 — 「열거 공격 시연」 (verify.html)**
- 조회 폼을 **`증권번호 단독` / `다중 대조(권장)`** 두 모드로 실제 전환.
- **단독 모드**를 선택하면 「연속 조회 시뮬레이션」 버튼이 나타나고, 누르면 **번호를 1씩 증가시키며 목데이터에서 다른 업체 증서가 줄줄이 조회되는 것**을 눈으로 보게 합니다(총 N건 노출, 상호·금액 리스트업).
- **다중 대조 모드**로 바꾸고 같은 시뮬레이션을 돌리면 **전부 실패**(0건). 대조 항목 수를 2→3→4로 늘리면 성공 확률이 실제로 계산되어 표시.
- 결과 화면에 **마스킹 규칙 토글** — 상호 앞 2자 노출(`대○○○`), 사업자번호 뒤 5자리 마스킹, 보증금액은 **일치 여부만** 표시(금액 자체를 안 보여주는 옵션).
- **실패 3회 → 캡차**, **동일 IP 일 30건 한도**, **감사 로그 적재**를 실제 카운터로 동작시키고 관리자 화면에서 오늘 조회 수·차단 IP·실패율을 그래프로.

#### F3. 공동인증서 웹 로그인은 "브라우저마다 따로 등록"이고, 설치형 보안 플러그인 방식은 수명이 1~2년

**발견 3-1 — 브라우저 인증서의 구조적 제약.**

**발견 3-2 — 설치형 보안 플러그인은 퇴출 중.**

#### F7. 관리자 화면을 "인터넷에 열린 URL + 아이디/비밀번호"로 만들면 안전성 확보조치 기준을 못 맞춘다

근거: https://www.cela.kr/4/?bmode=view&idx=168696184 · https://intothesec.com/149

**함정.** 조합엔 전산 인력이 없어 VPN·망분리를 운영할 수 없습니다. 그렇다고 관리자 URL을 그대로 열어두면 크리덴셜 스터핑의 표적입니다. → **운영 가능한 수준의 절충**이 필요합니다.

**데모 구현안 — admin.html 「보안 설정」 탭**
- **접속 IP 허용목록 관리**: 현재 접속 IP를 자동 표시 + `이 IP 등록` 버튼. 미등록 IP에서의 접근을 **시뮬레이션 버튼으로 차단 화면 재생**.

### 4-3. 예산 내 / 추가 비용 / 향후 별도 (공고 67줄이 명시적으로 요구한 3분할)

**A. 예산 내 (800만원)**
- 대표 홈페이지 전 페이지 (조합소개·조합업무·자료실·고객센터·공지사항·발급사실 조회) + 반응형
- 관리자 CMS (공지·자료실·**페이지 블록**·배너·팝업·권한 2단·접속기록·버전 이력)
- 발급사실 조회 — **②안(기존 인증/기능 활용 + 토큰 교환)** 기준 연계 1식
- 공동인증서 로그인 → 인터넷 영업점 인계 1식 (기존 인증 체계 재사용)
- 웹 접근성 **자체 준수**(KWCAG 2.2 기준 설계·퍼블리싱·자체 점검)
- 결과물 5종 + 운영 매뉴얼 + **담당자 교육 2회** + 무상 하자보수 **12개월**
  (무상 하자보수 1년이 공적 기준선 — https://www.inpage.kr/blog/website-contract-guide)

**B. 추가 비용이 필요한 기능** (범위·조건이 확인되면 별도 산정)
| 항목 | 이유 |
|---|---|
| 인증 연계 **①안(신규 API)** 채택 | 기존 인터넷 영업점 수정 필요 → 기존 벤더 협조·작업 비용은 조합 부담 |
| 발급사실 조회 **전용 API 신규 개발** | 기존 시스템에 조회 API가 없을 경우(F1) |
| 웹 접근성 **품질인증 마크 취득** | 심사 수수료 + 심사 대응(약 1개월, 유효기간 1년·갱신 필요) — http://www.kwacc.or.kr/Certification/Criterion |
| 공동인증서 **상용 인증 모듈 신규 라이선스** | 조합 보유분 재사용 시 0원. 신규 도입 시 제조사 견적 별도 |
| 영문 페이지 | 3개 조합 모두 ENG 제공 — 대외용이면 수요 발생 가능 |
| 과거 게시글 **DB 마이그레이션** | 공고에서 명시적으로 제외(45줄). 필요 시 건수 기준 별도 |
| 콘텐츠 원고 작성·사진 촬영 | 조합 제공이 원칙(61줄). 대행 시 별도 |

**C. 향후 별도 개발 권고**
- 프록시웹 방식의 전면 통합 / 인터넷 영업점 리뉴얼 (이번 범위 밖 — 공고 20줄)
- 나라장터 전자보증 직접 연계 (발주기관 앞 전자 발행·통지)
- 조합원 마이페이지(대표 홈페이지 측) · 알림톡/SMS 발송
- 모바일 앱 (공고에서 명시적 제외)
- 금융인증서·간편인증 추가 (전자서명법 개정 이후 확장 슬롯만 미리 확보)

**D. 의뢰자 부담 영역** (지원서에 반드시 명시)
서버·호스팅·회선 / SSL 인증서 / 도메인 / 공동인증서 모듈 라이선스 / 기존 영업점 벤더 협조 비용 / 콘텐츠 원고·이미지·폰트 라이선스 / 웹 접근성 인증 수수료 / 개인정보처리방침·이용약관 등 법률 문안 및 법적 판단 책임

### 4-4. 유지보수 (공고 74줄이 특별히 요구한 항목)
- 업계 관행은 **연간 개발비의 10~15%** — 800만 기준 **연 80~120만원**.
  근거: https://hyperhire.inblog.io/maintanance-rate
- 제안 구성(예): 무상 하자보수 12개월 → 이후 연 96만원(월 8만) 정기 유지보수
  (월 정기점검·보안 패치·백업 확인 + 월 2건 이내 콘텐츠/디자인 수정, 초과분 시간당 정산)
- **핵심 어필**: "유지보수를 적게 쓰게 만드는 것이 목표" — 관리자 CMS의 범위를 넓히고(F9),
  되돌리기·미리보기·접근성 검사를 붙여 **개발사를 부르지 않아도 되는 상태**를 납품물로 정의.

### 4-5. 「성공적 마무리」의 정의 (공고 72줄 — 제안에 반드시 포함)
1. 발주기관 담당자가 **전화 없이** 보증서 진위를 확인하고 **결재용 확인서를 출력**할 수 있다.
2. 조합원이 대표 홈페이지에서 로그인해 **한 번의 인증으로** 인터넷 영업점 업무로 넘어간다.
3. 조합 담당자가 **개발사 연락 없이** 공지·자료실·배너·팝업·메인 문구를 등록·수정하고, 잘못 올리면 되돌린다.
4. 접근성 기준(KWCAG 2.2)을 오픈 시점뿐 아니라 **1년 뒤에도** 유지한다(등록 단계에서 자동 검사).
5. 기존 인터넷 영업점이 **한 줄도 망가지지 않는다.**
6. 인수인계 후 **다른 개발사도 이어받을 수 있다**(소스·DB 스키마·배포/운영 매뉴얼·환경 문서).

### 4-6. 진행 상황 확인 방식 (공고 74줄 — 비개발자용)
- **주 1회 스테이징 링크** 공유 — 매주 화면이 늘어나는 것을 눈으로 확인
- 화면설계서를 **클릭 가능한 프로토타입**으로 제공(문서 대신 화면으로 검수)
- 주간 진행 보고 1장 — 지난주 완료 / 이번주 예정 / **조합이 결정해 줘야 할 항목**
- 이슈 목록을 스프레드시트 1개로 공유(용어 없이 화면 이름으로)
