# QUILL 퀼 — 시나리오·사용자 여정

> 모든 인물·매장은 가상입니다.

## 1. 등장인물

| 인물 | 원하는 것 | 불안한 것 |
|---|---|---|
| 본사 관리팀 (슈퍼관리자) | 전 지점 고객 데이터를 한 화면에서, 설문을 본사가 직접 수정 | 지점마다 제각각인 종이 설문 · 개인정보 사고 · 100개 지점 세팅 부담 |
| 원장 (매장 단위) | 우리 매장 고객 취향·유입 채널 파악, 디자이너별 성과 | 타 매장에 우리 데이터가 보이는 것 · 태블릿 운영 번거로움 |
| 디자이너 (개인) | 시술 전 내 고객의 취향·두피 상태를 미리 확인 | 입력이 번거로우면 안 씀 |
| 고객 (응답자) | 빠르게 끝나는 설문, 취향이 시술에 반영 | 내 연락처가 어디까지 가나 · 광고 문자 폭탄 |
| (레드팀 페르소나) 퇴사 예정 디자이너 | 고객 명단 확보 | — 시스템이 막아야 할 대상 |

## 2. 시간순 여정

| 단계 | 상황 | 화면 | 이 기능이 없으면 |
|---|---|---|---|
| 준비 | 본사가 설문 구성·수정 | builder | 수정할 때마다 개발사에 유상 요청 → "커스터마이즈" 요구의 이유 |
| 배포 | 저장 → 전 지점 태블릿 반영 | builder→survey | 지점별 버전 파편화 |
| 방문 | 신규 고객 착석, 태블릿 전달 | survey | 종이+수기 입력(현행) — 전사·보관·검색 불가 |
| 작성 | 2분 응답 + 동의 | survey | 동의 누락 = 수집 자체가 위법 |
| 제출 | 저장 + 화면 초기화 | survey | 다음 손님에게 앞 손님 정보 노출 |
| 시술 전 | 디자이너가 취향 확인 | admin(디자이너) | 설문이 시술에 안 쓰임 → 형식적 수집 |
| 주간 | 원장이 매장 현황·유입 분석 | admin(원장) | 감으로 마케팅 예산 배분 |
| 월간 | 본사가 전 지점 비교·엑셀 보고 | admin(슈퍼) | 지점별 취합 수작업 |
| 캠페인 | 동의자 대상 문자 안내 | admin·마케팅 대상 | 미동의자 발송 = 정보통신망법 위반 |
| 사고 대비 | 백업·복구 | admin·백업 | 데이터 유실 시 복구 불가 |

## 4. 기능별 존재 이유

| 기능 | 존재 이유 |
|---|---|
| 질문 12종 + 자유 커스텀 | "어떤 설문이든" — 재방문·직원·이벤트 폼까지 개발자 없이 |
| 동의 블록(필수/선택 분리) | 종이 설문지의 위법 소지 교정 · 과태료 방지 |
| 빌더 실시간 법 점검 | 관리자가 실수로 위법 구성을 만들지 않게 시스템이 감시 |
| 필수 동의 거부 시 저장 차단 | 동의 없는 수집 자체를 원천 봉쇄 (거부해도 종이 상담 대안 안내) |
| 키오스크 자동 초기화 | 공용 태블릿 세션 잔류 차단 |
| 디자이너 마스킹+내보내기 차단 | 퇴사 시 고객 DB 유출 경로 차단 |
| 마케팅 대상 자동 추출 | 미동의자 광고 발송(3천만원 과태료) 원천 차단 |
| 백업 슈퍼 전용 | 백업 파일 = 전 고객 DB. 최소 권한 |

## 5. 비는 구멍 (착수 미팅 확인 필요)

1. **가맹 구조** — 지점이 별도 사업자인가? → 위탁/제3자 제공 결정 → 동의 문구 확정
2. **보유 기간·파기** — 마지막 방문 후 몇 년? 자동 파기 배치 필요 여부 (공고도 "미팅 시 논의" 명시)
3. **기존 고객 재방문 처리** — 신규 전용인가, 재방문 시 이전 응답 불러오기인가 (동일인 식별 기준: 전화번호?)
4. **디자이너 계정 발급·회수 절차** — 퇴사 시 즉시 차단 프로세스, 100개 지점 계정 관리 주체
5. **태블릿 사양·대수** — 오프라인(와이파이 끊김) 시 임시 저장 필요 여부
6. **문자 발송 주체** — 본사 일괄인가 매장별인가
7. **PostgreSQL과 MySQL 병기** — 공고에 둘 다 명시. 단일 DB(MySQL 권장) 확정 필요
