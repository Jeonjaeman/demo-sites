### 1-2. 문서 행간의 숨은 니즈

- **"합법적인 선에서 수집"** + **"법적 이슈 최소화 위한 노출 방식 협의 필요"** — 의뢰자가 **직접 질문을 던졌습니다.** 답을 드리는 것이 이 제안의 핵심입니다(2장 ①).
- **"빠르게 시장을 검증"** — 목표가 완성이 아니라 **검증**입니다. 그렇다면 무엇을 지표로 볼지가 정해져야 하는데, 공고에는 없습니다. 크롤링 콘텐츠 조회수는 시장 검증 지표가 아닙니다(2장 ⑤).
- **"여성 커뮤니티"** — 이 단어가 요구사항 전체를 바꿉니다. 회원 기능이 "일반 회원가입"으로만 적혀 있지만, 실제로는 **누가 들어오는지가 서비스의 본질**입니다(2장 ②).
- **IT PM 경험 있음 · 우선순위 1위 완성도** — 기술 논의가 가능하고, 싸게보다 제대로를 원하십니다.
- **"이후 크롤링 대상은 점차 확대"** — 확장을 전제하므로 수집 대상 추가가 쉬운 구조여야 합니다.

## 2. 리서치 — 착수 전 확인이 필요한 항목

### ① 크롤링 콘텐츠 노출 방식이 이 프로젝트의 법적 경계입니다 ★

공고 3-2에 **"단순 링크 아웃바운드 또는 요약 형태의 노출 방식 협의 필요"** 라고 적어 주셨습니다. 정확한 문제 인식입니다. 법적으로는 이렇게 갈립니다.

| 방식 | 판단 |
|---|---|
| **링크만** | 링크는 복제에 해당하지 않아 **자유** (판례) |
| **제목 + 짧은 발췌** | 조건부 — 원문을 대체할 수 없는 분량이어야 |
| **상세 요약** | **위험** — 원문을 읽지 않아도 될 만큼 요약하면 "전재"로 판단 |
| **전문 복제** | 복제권·전송권 침해 + **DB제작자 권리** 문제 |

경쟁사 콘텐츠를 무단 수집한 사건에서 **총 4.5억원 배상** 판결이 확정된 사례가 있습니다. 또한 침해 게시물로 연결되는 링크를 **영리적·계속적으로 게시**하면 방조가 성립할 수 있다는 판례도 있습니다.

**대안 (데모 적용):** **노출 방식을 관리자에서 선택**하게 하고 각 방식의 **법적 위험도를 화면에 표시**했습니다. 기본값은 **제목 + 2~3줄 발췌 + 원문 링크**이며 **본문 전체는 저장하지 않습니다.** [노출 방식] 화면에서 세 방식의 실제 화면을 미리 볼 수 있습니다.

### ② 여성 커뮤니티에서 "안전"은 부가 기능이 아니라 제품 자체입니다 ★

공고의 회원 기능은 **"일반 회원가입, 로그인"**, 관리자 기능은 **"불량 유저 차단"** 뿐입니다. 그런데 여성 대상 커뮤니티에서 실제로 발생하는 문제는 **남성 유입·성적 괴롭힘·신상 특정·캡처 유출**이고, 이 중 하나만 터져도 커뮤니티는 회복하지 못합니다. 이용자가 글을 쓰는 이유가 **"여기서는 안전하다"** 이기 때문입니다.

**대안 (데모 적용):** 가입 단계에 **본인확인(성별) 게이트**를 넣었습니다. [휴대폰 본인확인 서비스](https://www.mobile-ok.com/)는 이름·생년월일과 함께 **성별 정보를 제공**하므로 별도 서류 없이 검증할 수 있습니다. 다만 **성별·연령대만 저장하고 이름·연락처는 저장하지 않습니다.** 신고 사유에 **개인정보 노출·성적 괴롭힘·불법촬영물 의심**을 분리하고, 긴급 사유는 **검토 전 즉시 가림** 처리합니다.

### ③ 2026년 7월부터 불법촬영물 유통방지 조치가 이미지까지 확대됐습니다

정보통신망법·전기통신사업법상 **불법촬영물등 유통방지를 위한 기술적·관리적 조치** 의무가 있고, **2026년 7월 1일부터 적용 범위가 동영상에서 이미지까지 확대**되었습니다. 조치에는 신고 기능, 명칭 비교를 통한 검색 제한, **특징 비교(필터링)를 통한 게재 제한**, 게재 시 사전 경고가 포함됩니다.

**대안 (데모 적용):** **1차에는 이미지 직접 업로드를 열지 않는 것**을 권합니다. 크롤링 콘텐츠도 **이미지 링크만 참조**하고 자체 호스팅하지 않습니다. 신고 → 즉시 블라인드 → 검토 흐름을 먼저 갖추고, 이미지 업로드는 필터링 연동이 준비된 뒤 여는 순서입니다.

> 의무 적용 대상 규모는 사업 성장 시점에 다시 확인이 필요합니다. 신규 서비스가 당장 대상인지는 별도 검토 사항이며, 여기서는 **가장 확실한 대응(업로드 미개방)** 을 제안합니다.

### ④ 크롤링한 글에 달린 댓글은 원문이 사라지면 갈 곳이 없습니다

크롤링 게시글에 좋아요·댓글이 붙는 구조인데, **원문이 삭제되거나 원 저작자가 삭제를 요청하면** 그 글에 쌓인 커뮤니티 활동도 함께 사라집니다.

**대안 (데모 적용):** 크롤링 글과 자체 글을 **시각적·구조적으로 분리**(카드 좌측 색상 띠 + 출처 배지)하고, 원문 삭제가 감지되면 **게시글은 비공개 처리하되 댓글은 보존**합니다. 크롤러가 원문 상태를 주기적으로 확인합니다(수집 로그에 반영).

### ⑤ 크롤링으로 채운 초기 데이터는 커뮤니티를 만들지 못합니다

콜드스타트를 크롤링으로 푸는 접근은 이해되지만, **남의 글에는 소속감이 생기지 않습니다.** 이용자가 남는 이유는 "내 이야기에 반응이 왔다"이지 "읽을 게 많다"가 아닙니다.

**대안 (데모 적용):** 시장 검증 지표를 **자체 글 작성률**로 잡고 관리자 대시보드 전면에 배치했습니다. 피드에서도 회원 글을 우선 노출하는 구조를 제안합니다.

### ⑥ 딜레이와 robots.txt 존중은 형사 리스크를 가르는 기준입니다

공고 3-1의 **딜레이 처리 필수**는 정확한 판단입니다. 법원은 크롤링의 형사책임을 판단할 때 **주관적 의도보다 객관적 기술통제 조치를 존중했는지**를 봅니다. 차단을 우회하거나 로그인 벽을 넘으면 정보통신망 침입죄가 성립할 수 있습니다.

**대안 (데모 적용):** robots.txt를 매 수집마다 확인하고 제외 경로는 건너뜁니다(로그에 기록). 요청 간격은 사이트별 설정(기본 2.5~3초), **로그인이 필요한 콘텐츠는 대상에서 제외**합니다.

## 4. 화면 구성

```
index.html (커뮤니티)
├─ 상단 안내 2종 — 본인확인 정책 · 크롤링 노출 정책
├─ 탭 — 전체 / 회원 이야기 / 읽을거리
├─ 카테고리 칩 6종
├─ 피드
│  ├─ 크롤링 카드 (파란 띠) — 제목 + 발췌 + 원문 링크 [본문 없음]
│  └─ 회원 카드 (분홍 띠) — 전문 + 좋아요 + 댓글
└─ 게이트 — 본인확인(3단계) / 글쓰기 / 신고(긴급 즉시 가림)

admin.html (관리자)
├─ 대시보드 — 자체 글 비율 ★ · 크롤링 상태 · 수집 로그
├─ 크롤링 설정 — 대상 2곳 · robots · 딜레이 · 중복 방지 파이프라인
├─ 신고 처리 — 긴급 우선 · 불법촬영물 대응 준비 현황
├─ 회원 관리 — 본인확인 여부 · 피신고 수 · 차단
├─ 노출 방식 ★ — 3가지 비교 + 위험도 + 실시간 미리보기
└─ 검토 항목 — 리스크 6건 + 적용한 대안
```

## 5. 제안 스택과 견적

**스택**
- **Next.js** (공고 관련 기술) — SSR로 크롤링 콘텐츠 SEO 확보, 커뮤니티 페이지는 CSR
- **Python(크롤링) + Node/Next API** — 파싱 생태계는 Python이 두텁고, 웹은 Next로 통일
- **PostgreSQL** — 원문 URL 해시 유니크 인덱스로 중복 차단
- **스케줄러** — 1시간 주기, 사이트별 딜레이·robots 확인 내장
- **본인확인** — 휴대폰 본인확인 서비스(성별·연령대만 수신·저장)

**견적**
