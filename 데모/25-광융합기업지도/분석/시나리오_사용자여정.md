# LUMINA — 시나리오로 읽는 과업지시서

> 과업지시서는 기능 목록이라 각 항목이 **어떤 상황에서 왜 필요한지**가 드러나지 않습니다.
> 이 문서는 요구사항을 실제 사용 흐름에 배치해 설명합니다.

---

## 1. 등장인물

| | 기업 탐색 이용자 | 데이터 담당자 | 발주 기관 |
|---|---|---|---|
| **누구** | 대기업 구매팀, 연구자, 투자 검토자, 지자체 담당 | 기업 DB를 관리하는 실무자 1명 | 광융합 진흥 기관 |
| **찾는 것** | "이 지역에 광센서 만드는 회사가 있나" | 데이터를 틀리지 않게 넣는 것 | 지역 산업 현황 가시화 |
| **불안한 것** | 정보가 낡았거나 틀렸을까 | 주소가 안 찍히는 건 어떡하나 | 예산 안에서 결과가 나올까 |
| **기기** | PC 위주 + 현장에서 모바일 | PC (관리자) | 보고 자료 |

**핵심:** 이 서비스의 이용자는 **찾는 목적이 분명한 사람들**입니다. 둘러보다 발견하는 게 아니라 *"경북에 있는 레이저 가공 중견기업"* 같은 조건을 이미 갖고 옵니다. 그래서 **다중 필터가 이 서비스의 본체**입니다.

## 2. 전체 그림

```
      [데이터 담당자]                              [탐색 이용자]
 사전  엑셀로 기업 목록 일괄 업로드 ──┐
      → 주소 자동 지오코딩            │
      → 실패·근사 건 지도에서 보정 ──┘ 좌표 확정
                                        │
 분기  외부 API 동기화 배치             │
      (재무 · 종업원)                   ↓
                              지도 진입 → 클러스터로 분포 파악

                              필터 좁히기(지역·분류·규모·매출)

                                        ↓
                              기업 클릭 → 상세 → 즐겨찾기 / 길찾기
```

## 3. 시나리오 A — 탐색 이용자 "구매팀 이 과장"

> 광학필름 협력사를 새로 찾아야 합니다. 기존 거래처가 한 곳뿐이라 대안이 필요합니다.

### 3-1. 진입 — "어디에 얼마나 있는지부터"

**상황.** 광융합기업이 전국에 몇 개나 되는지, 어디에 몰려 있는지 감이 없습니다.

**쓰는 기능.** 지도 + **클러스터링** (과업지시서 3.1 ①)

- 지도를 열면 **광주·대전·구미에 큰 원**이 뜹니다. "아, 여기가 클러스터구나"가 한눈에 들어옵니다.
- 마커를 전부 찍으면 화면이 점으로 뒤덮여 아무것도 안 보입니다. **클러스터링은 미관이 아니라 판독성 문제**입니다.
- 원을 누르면 확대되며 개별 기업이 드러납니다. 줌 4단계에서 168개 전체가 개별 마커로 보입니다.

> 이 기능이 없으면: 첫 화면에서 아무 정보도 못 얻고 이탈합니다.

### 3-2. 좁히기 — "광학필름, 중견 이상, 수도권"

**상황.** 조건이 명확합니다. 목록을 훑을 게 아니라 걸러내야 합니다.

**쓰는 기능.** 다중 필터 + 키워드 검색 (3.1 ③)

- **8대 산업 분류** — "디스플레이 광학"을 고르면 관련 없는 기업이 사라집니다.
- **기업 규모 / 매출 구간** — 구매팀에게는 *공급 안정성*이 중요해서 규모가 실질적 기준입니다.
- **지역** — 물류비와 직결됩니다.
- 필터는 **조합**되어야 의미가 있습니다. 하나씩만 걸리면 결국 목록을 다시 훑게 됩니다.

### 3-3. 영역 좁히기 — "이 근처만 다시"

**상황.** 지도를 수도권으로 옮겼는데 목록은 여전히 전국입니다.

**쓰는 기능.** **현재 지도 영역 내 재검색** (3.1 ③)

- 지도를 움직이면 **버튼이 나타납니다.** 자동으로 재검색하지 않는 이유는, 지도를 조금만 움직여도 목록이 계속 바뀌면 오히려 불편하기 때문입니다.
- 누르면 **보이는 영역 안의 기업만** 남습니다. 이 패턴은 카카오맵·네이버 지도·부동산 앱에서 이미 학습된 동작이라 설명이 필요 없습니다.

### 3-4. 판단 — "이 회사 규모가 되나"

**상황.** 후보 3곳을 추렸습니다. 이제 실제로 거래할 만한지 봐야 합니다.

**쓰는 기능.** 상세 패널 (3.1 ②)

- **매출·영업이익·종업원 수**가 판단 기준입니다.
- **그런데 여기서 문제가 생깁니다** ★ — 중소기업은 재무제표가 공개되지 않아 **API로 값이 안 옵니다**(데모 표본 기준 중소기업 커버리지 12.3%).
- 값이 그냥 비어 있으면 이용자는 **"데이터가 부실한 사이트"** 라고 판단하고 떠납니다.
- 그래서 **출처 배지**를 달았습니다 — `API 연동` / `엑셀 입력` / `재무제표 미공개 기업`. 없는 이유를 알려주면 신뢰가 유지됩니다.

### 3-5. 후속 — "나중에 다시 봐야지"

**쓰는 기능.** 즐겨찾기 · 길찾기 (3.1 ①②)

- 한 번에 결정하지 않습니다. 후보를 담아 두고 내부 검토를 거칩니다.
- 실제 방문 단계에서 **길찾기 연동**이 쓰입니다. 지도를 직접 만들 필요 없이 카카오맵·네이버로 넘기면 됩니다(과업지시서도 협의 사항으로 이 방식을 적어 두었습니다).

## 4. 시나리오 B — 데이터 담당자

> 기관에서 관리하는 기업 목록을 이 플랫폼에 올려야 합니다. 엑셀로 수백 건입니다.

### 4-1. 일괄 등록 — "하나씩 넣을 수는 없습니다"

**쓰는 기능.** 엑셀 일괄 업로드 (3.2 ①)

- 기업 데이터는 이미 엑셀에 있습니다. 수백 건을 폼으로 입력하는 건 불가능합니다.
- 업로드하면 **주소가 자동으로 좌표로 변환**됩니다. 이게 없으면 지도에 아무것도 안 찍힙니다.

### 4-2. 좌표 보정 — "이 주소는 왜 안 찍히지"

**상황.** 168건 중 6건이 지도에 안 나타납니다.

**쓰는 기능.** **지오코딩 실패 건 수동 보정** (3.2 ① — 과업지시서 명시)

- 산업단지 주소는 **(구)지번·블록 표기·비표준 건물명**이 섞여 자동 변환이 실패합니다.
  - 예: `광주 광산구 (구)하남공단 12블록`, `경남 창원시 성산구 공단로 밸리동`
- **좌표가 틀리면 지도 서비스 전체의 신뢰가 무너집니다.** 엉뚱한 곳에 찍힌 기업 하나가 전체를 의심받게 만듭니다.
- 그래서 **신뢰도를 3단계로 판정**합니다 — `정확(도로명 일치)` / `근사(도로 중심점)` / `실패`. 근사도 검토 대상으로 남깁니다.
- 실패·근사 건만 모아서 **지도에서 핀을 끌어 보정**합니다. 담당자가 주소를 아는 사람이므로, 자동화보다 사람이 빠릅니다.

> 과업지시서에 이 기능이 명시되어 있다는 건 **실무를 겪어 보신 것**으로 읽힙니다.

### 4-3. 주기 갱신 — "재무는 언제 업데이트되나"

**쓰는 기능.** 스케줄러 동기화 (4. 비기능 — 협의 사항)

- 재무·종업원 데이터는 **분기/연 단위로만 바뀝니다.** 실시간 API 호출은 의미가 없고 오히려 위험합니다.
- 공공 API는 지연·장애가 잦은데, 화면이 실시간으로 호출하면 **API가 죽을 때 서비스도 멈춥니다.**
- 배치로 자체 DB에 넣어 두면 외부가 죽어도 서비스는 정상입니다. 과업지시서의 판단이 맞습니다.

## 6. 시나리오를 그려보니 비는 구멍 — 미팅 확인 필요

### ① 기업 데이터는 어디서 오나요
과업지시서에 데이터 관리 기능은 있지만 **초기 데이터의 출처**가 없습니다. 기관 보유 명단인지, 협회 회원사인지, 공공데이터인지에 따라 **필드 구성과 초기 적재 방식이 달라집니다.**
> **확인:** 초기 등록 대상 기업 수와 보유 형태(엑셀 컬럼)를 받을 수 있는지?

### ② "8대 / 9대" 산업 분류의 실제 기준
3.1 ③에 **"산업 분류(8대, 9대)"** 라고만 적혀 있습니다. 광융합 분류 체계는 기관마다 다릅니다.
> **확인:** 사용하실 분류 체계 정의서가 있는지? (없으면 데모의 8대 분류를 초안으로 제안)

### ③ 기업 정보 수정 요청 창구
기업 정보가 틀렸을 때 **당사자가 알릴 방법**이 없습니다. 지도 서비스는 정보가 틀리면 항의가 들어옵니다.
> **확인:** "정보 수정 요청" 폼을 넣을지? (관리자 승인 후 반영)

### ④ 공개 범위 — 로그인이 필요한가
연락처·재무 정보를 **누구나 볼 수 있게** 할지 정해져 있지 않습니다. 기업 담당자 연락처는 개인정보 소지가 있습니다.
> **확인:** 전체 공개 / 로그인 후 열람 / 기관 내부용 중 어느 것인지? (4장 개인정보 요구사항과 직결)

### ⑤ 즐겨찾기는 로그인 없이 유지되나
현재는 브라우저에 저장하는 방식으로만 가능합니다. 기기를 바꾸면 사라집니다.
> **확인:** 회원 기능을 넣을지, 브라우저 저장으로 충분한지?

### ⑥ 검수 기준이 되는 "기능 100%"의 범위
과업지시서 5.2의 검수 조건이 **전체 범위**를 가리킵니다. 15일 프로토타입과 충돌합니다.
> **확인 (가장 중요):** 1차 범위를 문서로 확정하고 계약서에 첨부할 수 있는지? → 데모의 **[범위 구분]** 화면이 초안입니다.

### ⑦ 산출물 7종의 납품 시점
스토리보드·아키텍처 정의서·ERD·테이블 명세서·API 정의서·매뉴얼·테스트 보고서는 **본 구축 기준 산출물**입니다. 프로토타입 단계에 전부 요구되면 개발 시간이 문서 작성에 잠식됩니다.
> **확인:** 1차에는 화면 설계서와 소스코드만, 나머지는 2차로 미룰 수 있는지?

## 7. 정리

과업지시서는 **완성도가 높습니다.** 특히 다음 세 가지는 실무 경험이 없으면 적기 어려운 항목입니다.

- **지오코딩 실패 건 수동 보정** — 자동 변환이 완벽하지 않다는 걸 알고 계심
- **가상 스크롤 명시** — 대량 마커의 성능 문제를 미리 인지
- **실시간 호출이 아닌 스케줄러 동기화** — 공공 API의 불안정성을 반영

그래서 이 프로젝트의 쟁점은 **"무엇을 만들까"가 아니라 "15일에 어디까지 만들까"** 입니다.
착수 전에 1차 범위만 문서로 확정되면 나머지는 일정대로 진행됩니다.
