[1] CAMP FLOW(가칭) — 캠핑장 예약 플랫폼 MVP 제안 데모
https://jeonjaeman.github.io/demo-sites/campflow/
현재 상태: Argos v03 Deploy Ready PASS, 공개 별칭 HTTP 200 확인.

- 진행 과정   공고의 요구를 기능 목록으로 보지 않고,
              고객이 캠핑장을 발견하고 날짜를 고르고,
              상세에서 조건을 비교한 뒤 예약 요청과 결제 단계로
              이동하는 시간순 여정으로 재구성했습니다.
              그 과정에서 결제 완료와 예약 확정이 다른 시점이라는 점,
              환불 고지와 PG 심사가 일정 리스크라는 점,
              담당자가 수동으로 캠핑장 확인을 해야 하므로
              중복 예약과 대체 제안 흐름이 필요하다는 점을 분리했습니다.
              데모에는 매거진형 홈, 검색/필터, 상세, 예약 단계,
              완료/조회, 운영 패널의 핵심 흐름을 초안으로 넣었습니다.
- 특징        이번 공고와 직접 같은 문제입니다.
              공개 사용자는 빠르게 가능한 캠핑장을 찾고 싶고,
              운영자는 업체 로그인 없이 담당자 화면에서 등록·확정·취소를
              처리해야 합니다. 그래서 화면을 예쁜 랜딩으로 늘리기보다
              날짜별 재고, 사이트 상태, 환불 조건, 결제 전 안내,
              운영 상태 전환이 서로 맞물리는 구조를 우선했습니다.
              독립 QA의 P1 보완을 완료하고 공개 경로까지 검증했습니다.
- 핵심 요소   매거진형 캠핑장 탐색, 지역·유형·인원·반려견 필터,
              사이트별 가능/확인필요/마감 상태 표시,
              D-7/D-3/D-1 환불표, 결제 시뮬레이션,
              접수≠확정 상태 타임라인, 담당자 운영 큐,
              상태 변경, CSV 내보내기, PG 준비 체크리스트

[2] SEMINAR56 — 마케팅 세미나·강의 신청 플랫폼
https://jeonjaeman.github.io/demo-sites/seminar56/

- 진행 과정   강의 상세, 일정 선택, 신청, 입금 대기,
              운영자 콘텐츠 등록을 하나의 흐름으로 정리했습니다.
              신청자가 보는 화면과 운영자가 처리하는 화면을 나누고,
              정원 마감과 결제 대기 상태가 충돌하지 않도록
              상태값을 먼저 정의한 뒤 화면을 구성했습니다.
              단순 홍보 페이지가 아니라 목록·상세·신청·운영이
              이어지는 서비스형 구조로 설계한 사례입니다.
- 특징        이번 캠핑장 공고의 날짜별 예약 가능 여부와 가장 닮은 축입니다.
              세미나는 회차별 정원이 있고,
              캠핑장은 날짜와 사이트별 재고가 있습니다.
              둘 다 사용자가 신청 버튼을 누르는 순간의 상태와
              운영자가 확인하는 순간의 상태가 달라질 수 있으므로,
              마감·대기·확정 문구를 분명히 나누는 설계가 필요합니다.
- 핵심 요소   강의 목록, 상세 페이지, 신청 흐름,
              정원·마감 상태 계산, 입금 대기 안내,
              운영자 콘텐츠 등록 화면, 신청 상태 구분,
              사용자 안내 문구와 운영 처리 기준 분리

[3] BOOTHPIN — 행사 부스 신청·운영 플랫폼
https://jeonjaeman.github.io/demo-sites/boothpin/

- 진행 과정   행사 주최자와 참가 셀러의 시야를 나누고,
              부스 등급, 신청 조건, 결제 전 확인,
              운영자 승인 흐름을 화면 단위로 정리했습니다.
              특히 공고 요구를 그대로 나열하지 않고,
              참가자가 어떤 정보를 보고 신청을 결정하는지,
              운영자가 어떤 기준으로 승인·반려를 판단하는지를
              서로 다른 화면 목적에 맞게 배치했습니다.
              상태 규칙이 모호한 부분은 미팅 확인 항목으로 남겼습니다.
- 특징        이번 공고의 담당자 수동 확정 구조와 연결됩니다.
              캠핑장 예약도 자동 확정이 아니라 담당자가 업체에 확인한 뒤
              확정되는 흐름이므로, 신청 접수와 최종 확정을 분리해야 합니다.
              BOOTHPIN 사례의 승인·반려·대기 구조는
              캠핑장 예약의 접수·확인중·확정·대체제안·취소 상태를
              설명하는 데 바로 활용할 수 있습니다.
- 핵심 요소   행사/부스 목록, 신청 폼, 등급별 조건 표시,
              승인·반려 상태, 운영자 처리 큐,
              결제 전 확인 문구, 상태별 사용자 안내,
              미확정 정책의 확인 항목 분리

[4] TOPLOADER — 스포츠카드 통합 커뮤니티
https://jeonjaeman.github.io/demo-sites/toploader/

- 진행 과정   커뮤니티, 시세 확인, 거래 신뢰, 신고 흐름이 흩어진 문제를
              하나의 사용자 여정으로 묶었습니다.
              게시글을 보는 사람, 거래를 제안하는 사람,
              신고를 검토하는 운영자의 시야가 다르기 때문에
              화면별로 먼저 봐야 하는 정보와 위험 신호를 분리했습니다.
              시세와 신뢰 등급은 장식 요소가 아니라
              사용자가 행동을 결정하기 전에 확인해야 하는 판단 정보로
              배치했습니다.
- 특징        이번 공고와 업종은 다르지만,
              사용자 간 기대와 실제 운영 상태가 어긋날 때 분쟁이 생긴다는
              점이 같습니다. 캠핑장 예약에서도 결제, 환불, 확정 실패,
              대체 제안이 명확히 안내되지 않으면 고객 불만이 커집니다.
              TOPLOADER의 신고·신뢰·상태 표시 경험은
              예약 플랫폼의 분쟁 예방 카피와 운영 상태 설계에 적용됩니다.
- 핵심 요소   게시판·검색, 시세 차트, 신고 접수 흐름,
              회원 신뢰 등급, 거래 전 주의 문구,
              운영자 확인 상태, 분쟁 예방 안내,
              사용자 행동 전 위험 정보 노출
