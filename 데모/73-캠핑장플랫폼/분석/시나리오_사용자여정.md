# 시나리오 사용자여정

## 1. 등장인물

| 역할 | 목표 | 불안 | 봐야 하는 정보 |
|---|---|---|---|
| 캠핑장 탐색/예약 소비자 | 원하는 날짜에 갈 수 있는 캠핑장을 빠르게 찾고 결제까지 끝내기 | 결제했는데 예약이 확정되지 않음, 취소/환불 조건을 뒤늦게 알게 됨, 시설 정보가 실제와 다름 | 날짜별 가용성, 가격, 시설/규정, 환불률, 예약 상태, 담당자 연락 예정 시각 |
| 캠핑장 업체 담당자 | 빈 사이트를 정확히 팔고 중복예약을 막기 | 여러 채널에서 같은 사이트가 팔림, 플랫폼 요청을 늦게 확인함, 옵션/환불 처리 혼선 | 예약 요청, 사이트/객실 재고, 요청자 연락처, 결제 상태, 확정/불가 처리 결과 |
| 플랫폼 운영자 | 큐레이션 콘텐츠와 예약 요청을 관리해 1차 검증 성공 | 업체 직접 로그인이 없어 모든 운영이 수동으로 몰림, PG/환불/개인정보 이슈 발생 | 캠핑장 등록 상태, 콘텐츠 노출 상태, 예약 요청 큐, 결제 접수/취소 상태, 운영 체크리스트 |
| 결제/연락 담당자 | 결제 접수 후 업체 확인과 소비자 안내를 끊기지 않게 처리 | 결제는 되었는데 업체 확인이 늦어짐, 환불/부분취소 누락, 연락두절 민원 | 결제 식별자, 총액/옵션액, 연락 필요 예약, SLA, 환불 계산, 상태 변경 로그 |

## 2. 전체 시간순 여정

| 단계 | 소비자 시야 | 업체 담당자 시야 | 플랫폼 운영자 시야 | 결제/연락 담당자 시야 | 없으면 벌어지는 일 | 정적 데모 표현 |
|---|---|---|---|---|---|---|
| 발견 | 인스타그램식 매거진 피드에서 계절/지역/테마 캠핑장을 본다. | 아직 소비자 행동을 모른다. | 어떤 캠핑장이 큐레이션에 노출되는지 관리한다. | 없음 | 콘텐츠는 예뻐도 예약 가능성과 연결되지 않으면 탐색에서 끝난다. | 피드 카드마다 선택 날짜 기준 가능/마감/수동확인 뱃지 표시 |
| 판단 | 날짜, 가격, 반려견, 전기, 화로, 카라반, 인근 옵션을 비교한다. | 등록된 시설/규정이 소비자에게 어떻게 보이는지 확인해야 한다. | 정보 누락 캠핑장을 식별한다. | 없음 | 시설/환불/정원 정보가 부족하면 전화 문의로 회귀한다. | 상세 화면에 시설·규정·환불·업체확인 상태 체크리스트 |
| 예약 | 사이트/날짜/인원/옵션을 선택하고 예약자 정보를 입력한다. | 새 예약 요청이 들어올 준비를 한다. | 예약 요청이 어떤 캠핑장으로 들어가는지 본다. | 결제 전/후 연락 대상이 생긴다. | 옵션 총액, 정원 초과, 마감 상태를 잘못 계산한다. | 목데이터 기반 총액·옵션액·정원 가능 여부 실제 계산 |
| 결제 | 카드 결제처럼 보이는 단계에서 총액과 취소 조건을 확인한다. | 아직 확정 전이면 실제 재고를 확인해야 한다. | PG 심사/사업자/환불정책 준비 상태를 확인한다. | 결제 접수 후 업체 연락 태스크를 받는다. | 결제 완료를 예약 확정으로 오해한다. | “목 결제 접수”와 “업체 확인 대기”를 분리한 완료 상태 |
| 확정 | 확정/대체/취소 결과를 기다린다. | 요청 사이트를 확정하거나 대체안을 제시한다. | SLA 초과 예약을 모니터링한다. | 소비자에게 확정/불가/환불 안내를 보낸다. | 수동 확인 지연으로 연락두절 불신이 커진다. | 운영 패널 1개에서 예약 큐와 상태 버튼 표시 |
| 사후 | 예약 내역, 환불 예상액, 문의 경로를 확인한다. | 노쇼/취소/변경을 처리한다. | 취소 사유와 전환 데이터를 본다. | 환불/부분취소/옵션취소를 추적한다. | 환불 금액 분쟁, 개인정보 보유기간/삭제 문의 발생 | 완료 화면에 환불 계산표와 문의 SLA, 데이터 보존 안내 |

## 4. 핵심 시나리오

### 4.1 소비자: “이번 주말 가능한 반려견 동반 캠핑장 찾기”

1. 홈에서 “이번 주말” 날짜 칩을 선택한다.
2. “반려견 동반”, “전기 가능”, “화로 가능” 필터를 켠다.
3. 피드 카드가 가능/마감/수동확인 상태로 재정렬된다.
4. 상세에서 사진, 시설, 입퇴실, 취소/환불 조건을 확인한다.
5. 사이트와 옵션을 선택한다.
6. 예약자 정보를 확인하고 목 결제를 진행한다.
7. 완료 화면에서 “결제 접수, 업체 확인 대기”와 예상 연락 시각을 본다.

필수 기능:
- 날짜 기반 가용성 필터
- 시설/규정/환불 고정 패널
- 총액/옵션/환불 계산
- 예약 확정 전 상태 표시

### 4.2 플랫폼 운영자: “업체 로그인 없이 등록/확정 운영하기”

1. 운영 패널을 연다.
2. 캠핑장 목데이터를 등록/수정한다: 이름, 지역, 사이트 수, 환불정책, 옵션.
3. 새 예약 요청 큐를 본다.
4. 업체 연락 후 확정/대체/취소 중 하나를 누른다.
5. 소비자 완료 상태가 변경된다.

필수 기능:
- 관리자 멀티페이지가 아니라 모달/패널 1개
- 예약 요청 큐
- 상태 변경이 사용자 완료 카드에 반영되는 프론트 상태연산
- SLA 초과 경고

### 4.3 결제/연락 담당자: “결제 접수 후 업체 확인 실패”

1. 소비자가 결제 접수까지 완료한다.
2. 업체 확인 결과 해당 사이트가 이미 마감이다.
3. 담당자는 대체 사이트 제안 또는 취소/환불을 선택한다.
4. 소비자는 “대체 제안 확인” 또는 “환불 진행” 상태를 본다.

필수 기능:
- 결제 접수와 예약 확정 분리
- 대체 제안 상태
- 환불 예상액 계산
- 연락 로그/다음 응답 시각 표시

## 5. 기능 존재 이유 매핑

| 기능 | 존재 이유 | 우선순위 | 정적 데모 구현 방식 |
|---|---|---:|---|
| 매거진형 피드 | 탐색 진입과 큐레이션 가치 증명 | P0 | 목 캠핑장 배열을 카드 피드로 렌더, 스크롤/필터 상태 반영 |
| 날짜 칩/가용성 필터 | 예약 MVP의 핵심 검증 | P0 | 선택 날짜에 따라 availableSites를 계산 |
| 상세 규정/환불 패널 | 결제 전 분쟁 예방과 PG 심사 대응 | P0 | D-day별 환불률 목데이터 계산 |
| 예약/옵션 선택 | 공고의 부가 예약 옵션 요구 대응 | P0 | 옵션 체크 시 총액·옵션액·환불액 변화 |
| 목 결제 접수 | 실제 PG 없이 결제 흐름 검증 | P0 | 승인번호 형태 목데이터 생성, “실결제 아님” 표기 |
| 수동 확정 대기 | 공고의 담당자-업체 연락 구조 반영 | P0 | 완료 화면 상태 배지와 운영 패널 상태 전환 |
| 운영 패널 1개 | 업체 로그인 제외 조건에서 운영 가능성 표현 | P1 | 모달/사이드패널 하나로 등록/예약 큐 처리 |
| PG/사업자 체크리스트 | 15일 일정의 외부 의존성 노출 | P1 | 완료/운영 패널에 준비 상태 체크 표시 |
| 리뷰/커뮤니티 | 판단 보조 | P2 | 이번 정적 데모에서는 카드의 샘플 리뷰 1~2개만 |
| 업체 직접 로그인/CRUD | 공고 제외 범위 | 제외 | 만들지 않음 |
| 실제 서버/DB/PG/API | 사용자 요청상 구현 금지 | 제외 | 목데이터+프론트 상태연산만 |

## 6. 비는 구멍 / 미팅 확인 필요

1. 예약 확정 전 결제 접수 방식: 실제 승인, 가승인, 예약금, 무통장/카드 중 무엇인지.
2. 업체가 확정을 거절했을 때 소비자 보상/환불 SLA.
3. 캠핑장별 재고의 최신성 보장 방법.
4. 옵션상품의 제공자, 정산, 취소 조건.
5. 위치/지도 서비스 사용 시 API 비용과 위치정보 관련 검토 필요 여부.
6. 개인정보 제3자 제공: 예약자 연락처를 업체에 전달하는 시점과 고지 방식.
7. 정부지원사업 산출물 검수 기준: 실제 운영 가능한 코드인지, MVP 검증용 시연인지.
8. 오픈 후 A/S 범위: 버그 수정, 운영 대행, 콘텐츠 등록 지원, PG/환불 문의 대응 중 어디까지인지.
