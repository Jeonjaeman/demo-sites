# 데모73 디자인 재검수 v01

## status

**DESIGN HOLD — P1 4건, P2 5건**

- 기능형 플랫폼에 POSCO FLOW의 `100vh`, wheel hijack, pin/scrub, GSAP, Lenis, SplitText를 넣지 않은 판단은 맞다.
- 현재 구현은 색·폰트·보더·radius·arrow-wrap·일부 reveal/countUp을 이식한 **토큰 적용 단계**다. POSCO FLOW의 핵심인 이미지 스케일, 밝고 어두운 면의 리듬, 비대칭 구성, 상태별 장면 차이는 제출 수준에 못 미친다.
- 특히 제출 증거가 실제 화면을 잘못 설명한다. 구현자 contact sheet의 `04-booking-1440.png`와 `05-complete-1440.png`는 모두 성공 후 `complete.html` 화면이다. 반면 `qa/argos-v01/booking-*`는 실제 예약 1단계이고, `qa/argos-v01/complete-*`는 코드 없이 연 `complete.html`의 **예약조회 안내 상태**다. 후자는 결제 완료 성공 상태 캡처가 아니다.
- 코드/CSS/HTML은 이번 재검수에서 수정하지 않았다.

## design_goal

홈에서는 큰 이미지와 비대칭 리듬으로 캠핑장을 발견하게 하고, 검색·상세·예약·완료·운영패널에서는 상태와 다음 행동을 한눈에 구분하게 한다. POSCO FLOW의 시각 문법은 다음처럼 축소 이식한다.

1. 이미지: `작은 장식 사진 여러 장`이 아니라 `대표 장면 1개 + 보조 장면 2개`로 스케일 차이를 만든다.
2. 명암: 흰 카드의 연속을 끊되, 기능 화면은 다크 풀스크린 대신 `white / #E8F3FE / #161D27`의 제한된 상태 면을 쓴다.
3. 비대칭: 균등 그리드를 깨는 것은 홈·상세 갤러리에 집중하고, 폼·표에서는 열 너비와 정보 우선순위의 비대칭으로 바꾼다.
4. 모션: 네이티브 스크롤을 유지한다. 홈 reveal과 이미지 clip, 화살표, 상태 전환만 CSS/IntersectionObserver로 제한한다.
5. 제출 증거: booking, complete-no-code, complete-success를 서로 다른 상태로 명명하고 캡처한다.

## findings

### 캡처 증거 판정 — booking과 complete를 정확히 구분

| 증거 | 실제 상태 | 판정 |

| `qa/contact-sheet.jpg`의 `04-booking-1440.png` | 예약번호 `CF-20260829-0001`, 합계, 진행상태가 있는 `complete.html` 성공 화면 | **오표기. booking 증거로 사용 금지 (P1)** |
| `qa/contact-sheet.jpg`의 `05-complete-1440.png` | 위와 같은 `complete.html` 성공 화면 | complete-success로는 유효하나 04와 중복 |

- `complete-lookup-empty-{1440x900,1024x768,375x812}.png`
- `complete-success-received-{1440x900,1024x768,375x812}.png`

### 정량 관찰 기준

아래 점유율은 지정 캡처의 보이는 픽셀 경계를 기준으로 한 근사치다. 구현 수치가 아니라 **현재 시각 결과의 비교 기준**이다.

- 홈 1440: 본문 폭 약 `1152px = 화면의 80%`; 우측 3컷 총 면적은 첫 화면의 약 `11%`. 큰 제목 대비 이미지가 장식 수준이다.
- 홈 375: 검색 카드 하단이 `y≈797px = 첫 화면 높이의 98%`; 대표 이미지가 첫 화면에 0px 보인다.
- 상세 1440: 갤러리 약 `1152×580px = 첫 화면 면적의 51%`; 이미지 스케일은 충분하지만 예약 CTA가 첫 화면에 없다.
- 예약 1440: 주문요약 폭 약 `380px = 화면의 26%`; 예약 1024에서는 요약 전체가 첫 화면에서 사라진다.
- 예약 375: `옵션 선택` CTA 시작점이 `y≈718px = 첫 화면의 88%`; 현재는 간신히 보이지만 작은 높이·브라우저 UI·200% 확대에서 쉽게 접힌다.
- 완료-no-code 1440: 콘텐츠가 좌측 760px에 몰려 우측 약 `536px = 화면의 37%`가 의미 없는 빈 면이다.
- 완료-no-code 375: 예약조회 섹션 시작이 `y≈579px = 첫 화면의 71%`; 입력과 조회 CTA는 첫 화면 밖이다.
- 운영패널: 1440에서 폭 `720px = 50%`, 375에서 약 `360px = 96%`. 패널 자체 폭은 적절하나 모바일 카드 높이와 행 간격이 과하다.

### P1-01. 캡처 오표기와 완료 상태 누락이 제출 신뢰를 깨뜨린다

- 문제: booking과 complete-success가 같은 이미지로 제시됐고, Argos의 `complete-*`는 성공이 아닌 no-code lookup 상태다.
- 영향: 예약 입력 → 결제 시뮬레이션 → 요청 접수라는 핵심 전환을 증명하지 못한다.
- 최소 변경: 화면 구현을 건드리기 전에 캡처 시점·파일명·contact sheet 셀만 바로잡는다.
- 수용기준:
  1. booking 3뷰에 `1 / 4 날짜·인원`과 `옵션 선택`이 보인다.
  2. complete-success 3뷰에 예약번호, `실제 청구 0원`, `예약 요청 접수 · 캠핑장 확인 전`, 진행상태가 보인다.
  3. booking과 complete-success 이미지는 육안 및 파일 해시가 서로 다르다.
  4. complete-no-code는 `완료`가 아닌 `예약조회 빈 상태`로 표기한다.

### P1-02. 상세 페이지의 예약 CTA가 첫 장면에서 사라진다

- 1440에서 이미지 갤러리는 강하고 POSCO FLOW의 2:1 비대칭도 잘 가져왔지만, 첫 화면이 이미지 감상으로 끝난다.
- 375에서는 대표·보조 이미지가 연속으로 화면을 채워 예약 가능 상태·가격·CTA가 812px 안에 전혀 보이지 않는다.
- 기능형 플랫폼에서 이미지는 판단 근거이고 CTA가 행동 출구다. 둘 중 하나를 숨기면 안 된다.
- 최소 변경:
  - desktop/tablet: 갤러리 우측 열 하단 또는 갤러리 직후 첫 정보행에 `날짜 / 1박 가격 / 예약 가능 상태 / 날짜 선택` 패널을 첫 viewport 안에 배치한다.
  - mobile: 하단 sticky bar에 `₩68,000/1박` + 상태 + `날짜 선택`을 노출한다. 갤러리는 native swipe 1장 + `1/3` 인디케이터로 축약한다.
- 수용기준: 1440×900, 1024×768, 375×812 모두 첫 화면에 가격, 가능/확인필요/마감 텍스트, primary CTA가 동시에 보인다. sticky bar는 safe-area를 포함하고 콘텐츠 마지막 64px 이상을 가리지 않는다.

### P1-03. 모바일 검색은 필터가 첫 화면을 독점해 결과가 보이지 않는다

- 375에서 제목과 검색 폼·필터 chip이 812px를 넘기며 결과 이미지·캠핑장명·가격이 0px 노출된다.
- 검색 화면의 사용자 목표는 조건 입력 자체가 아니라 결과 비교다.
- 최소 변경: 검색 완료 후에는 입력 폼을 `제주 · 8/29–8/30 · 2명` 한 줄 요약 + `조건 변경` 버튼으로 접는다. 편의 필터는 2행까지만 보이고 나머지는 bottom sheet로 보낸다.
- 수용기준: 375×812에서 검색 완료 상태의 첫 결과 이미지 또는 캠핑장명이 `y≤680px`에서 시작하고, 가격·가능 상태·상세 CTA 중 최소 2개가 첫 화면에 보인다. 조건 변경은 44×44px 이상이다.

### P1-04. complete-success의 ‘성공’과 ‘확정 대기’가 한 카드 안에서 경쟁한다

- 현재 성공 카드 구현은 초록 체크와 “결제 시뮬레이션 완료”를 크게 보여 주지만 실제 비즈니스 상태는 `예약 요청 접수 · 캠핑장 확인 전`이다.
- 결제 성공과 예약 확정이 다른데 같은 성공 문법을 쓰면 사용자가 완료로 오해한다.
- 최소 변경: 상단은 `시뮬레이션 성공`을 작은 success 라인으로, 주 상태는 warning 계열의 `예약 요청 접수` 면으로 분리한다. 예약번호와 다음 단계 예상 흐름을 첫 카드 상단에 둔다.
- 수용기준:
  - 첫 제목은 `예약 요청이 접수됐어요`이고, 보조문으로 `결제 시뮬레이션 완료 · 실제 청구 0원`을 둔다.
  - `확정이 아닙니다`가 접히지 않고 보인다.
  - 예약번호와 `번호 복사`는 375×812 첫 화면에 보인다.
  - primary CTA는 `예약 상태 확인`, secondary는 `홈으로`, 운영 패널 액션은 tertiary로 분리한다.

### P2-01. 홈의 이미지 스케일과 명암 리듬이 제목을 받치지 못한다

- 1440의 제목은 약 56px급으로 강하지만 우측 3컷 면적은 첫 화면 약 11%에 그쳐 “매거진형 발견”보다 폼이 큰 검색 랜딩처럼 보인다.
- 1024에서는 이미지가 폴드 아래부터 크게 보이므로 오히려 장면성이 좋아진다. 1440과 375에서만 이미지 존재감이 약하거나 사라진다.
- 흰 배경이 히어로와 다음 큐레이션까지 이어져 장면 전환이 없다.
- 최소 변경:
  - 1440: 대표 이미지가 히어로 시각 면의 `65~72%`, 보조 2장이 나머지를 차지하는 `7:5` 비대칭 콜라주로 조정한다. 이미지 총 면적 목표는 첫 viewport의 `25~32%`.
  - 375: 검색 카드 이전 또는 카드와 겹치지 않는 위치에 대표 이미지 최소 `335×180px`를 노출하고 보조컷은 다음 장면으로 보낸다.
  - 다음 큐레이션 섹션은 흰 카드 여러 개 대신 `#E8F3FE` 면 또는 한 장의 `21:9` 풀폭 이미지로 끊는다.
- 수용기준: 1440 첫 화면 이미지 면적 25% 이상, 375 첫 화면 이미지 높이 160px 이상, LCP 이미지는 한 장만 eager, 텍스트 대비 4.5:1 이상.

### P2-02. 검색 단일 결과가 좁은 카드 하나로 남아 빈 여백이 과하다

- 1440에서 단일 결과는 약 368px 카드로 좌측에만 놓이고 우측 콘텐츠 영역 절반 이상이 빈 면이다.
- POSCO FLOW 목록형의 장점은 `상단 2px 시작선 + 정보 열의 명확한 우선순위`다. 1개 결과를 3열 카드 규칙에 억지로 두지 않는 편이 낫다.
- 최소 변경: 결과 1~2개일 때만 가로 리스트 변형을 사용한다. 이미지 40~45%, 정보 55~60%; 이름 → 가능 상태 → 날짜 → 가격 → 화살표 순으로 둔다. 3개 이상이면 기존 3/2/1열을 유지한다.
- 수용기준: 단일 결과 행이 콘텐츠 폭의 65% 이상을 사용하고, 이미지·상태·가격·CTA가 1440 첫 화면에 보인다. 카드 제목 2행, 설명 2행 이하, 그림자 0을 유지한다.

### P2-03. 예약 폼은 데스크톱은 안정적이지만 1024·375에서 요약 위계가 사라진다

- 1440은 폼 560px + 주문요약 380px의 기능적 비대칭이 적절하다. 다만 page title 외곽의 파란 사각선은 입력 focus처럼 보여 장식 위계가 혼동된다.
- 1024에서는 주문요약이 접힘 아래로 완전히 내려가 날짜·사이트·총액을 상호 확인할 수 없다.
- 375에서는 CTA가 첫 화면 하단 88% 지점에 있어 겨우 보이지만 합계·예약 상태가 없다.
- 최소 변경:
  - 제목의 파란 사각선은 제거하거나 3px 하단 accent로 바꾼다.
  - 1024 이하에서 `날짜 · 사이트 · 총액` compact summary를 단계바 아래 한 줄로 고정한다.
  - 375에서 단계 간 이동 CTA 위 또는 sticky bar에 총액을 함께 표시한다.
- 수용기준: 모든 뷰에서 현재 단계, 선택 날짜, 사이트 상태, 총액, 다음 CTA를 한 화면에서 확인할 수 있다. 폼 화면에는 스크롤 reveal을 쓰지 않는다.

### P2-04. complete-no-code는 큰 안내 카드와 조회 섹션이 중복되고 빈 면이 많다

- 1440은 상단 안내 카드 760px와 아래 조회 소개가 같은 의미를 두 번 말하며, 우측 약 37%가 비어 있다.
- 375는 상단 카드가 328px 높이를 차지해 실제 예약조회 입력이 첫 화면 밖으로 밀린다.
- 최소 변경: no-code 상태에서는 상단 카드와 조회 소개를 한 블록으로 합친다. `예약번호 입력 → 연락처 뒤 4자리 → 예약 조회`가 첫 화면의 주 작업이 되게 한다.
- 수용기준: 1440에서 조회 폼은 콘텐츠 상단 `y≤260px`, 375에서 첫 입력은 `y≤360px`, primary CTA 하단은 `y≤720px`. 중복 제목은 1개만 남긴다.

### P2-05. 운영패널은 카드·badge가 반복되어 처리 우선순위가 흐리다

- 1440에서 패널 폭 50%는 적절하다. 그러나 KPI 3카드, 예약 행의 연블루 면, 상태 badge, 우측 액션 3개, PG badge가 동시에 경쟁한다.
- 375에서 KPI 3장이 가로 3열로 유지되어 라벨이 2~3행으로 꺾이고, 빈 상태 카드 높이가 약 230px라 체크리스트가 늦게 나온다. 예약 0건인데 CSV CTA가 같은 위계로 살아 있다.
- 최소 변경:
  - KPI는 border card 대신 숫자 3열 + 세로 hairline으로 축약한다.
  - 예약 행은 `현재 상태`를 가장 진하게, 권장 primary 액션 1개만 바로 보이고 나머지는 overflow 메뉴로 보낸다.
  - 0건이면 CSV를 disabled/hidden 처리하고 empty 블록 높이를 120~160px로 줄인다.
- 수용기준: 모바일에서 KPI 영역 높이 120px 이하, empty 상태 160px 이하, 첫 PG 체크 항목이 `y≤650px`에 보인다. 상태는 색뿐 아니라 텍스트·아이콘으로 구분한다.

## accessibility

- 모든 텍스트 대비 WCAG 2.2 AA: 일반 텍스트 `4.5:1`, 큰 텍스트·UI 경계 `3:1` 이상.
- `#00A3F1` 위 흰 글자는 금지하고 `#161D27`을 사용한다.
- sticky CTA는 44×44px 이상, primary 높이 52px, safe-area 포함. 확대·가상 키보드에서도 마지막 입력과 CTA를 가리지 않는다.
- 상태는 색 하나가 아니라 아이콘+명시 텍스트로 구분한다: `예약 가능`, `확인 필요`, `마감`, `요청 접수`, `확정`, `취소`.
- 운영패널은 P2-01 별도 이슈대로 focus trap·배경 inert를 갖춰야 하며, 디자인 완료 판정에도 포함한다.
- `prefers-reduced-motion: reduce`에서 reveal, clip, arrow, countUp을 즉시 최종 상태로 만든다. 내용이 opacity 0으로 남으면 실패다.
- mobile bottom sheet/drawer는 Escape, 닫기, trigger focus return, DOM 순서=시각 순서를 지킨다.
