# 데모73 캠핑장 예약 플랫폼 — 페이지 기획

## 1. design_goal

공고의 핵심 검증 질문인 **“사용자가 매거진형 캠핑장 콘텐츠를 탐색하고, 날짜를 고른 뒤 예약·결제 흐름까지 막힘없이 도달하는가”**를 최소 페이지로 증명한다. 홈은 감성적 발견을 담당하고 검색 이후는 빠른 비교와 오류 없는 예약에 집중한다.

MVP의 1차 성공은 다음 한 문장으로 정의한다.

> 사용자가 큐레이션 또는 검색에서 캠핑장을 선택하고, 날짜·인원·옵션·예약자 정보를 입력한 뒤 실제 청구 없는 결제 시뮬레이션을 완료하여 예약 요청 번호를 확인한다.

예약은 즉시 확정형이 아니다. 공고에 따라 `사용자 요청 → 담당자 연락 수신 → 담당자가 캠핑장에 확인 → 확정/예약 불가 통보` 흐름을 화면과 카피에 반영한다.

## 2. 사용자와 목표

| 역할 | 원하는 것 | 불안 | 필요한 화면 |
|---|---|---|---|
| 일반 캠퍼 | 여러 곳에 흩어진 정보를 한곳에서 보고 원하는 날짜에 예약 | 실제 가능한지, 총액이 바뀌는지, 결제가 됐는지 | 홈, 검색, 상세, 예약, 결과, 예약조회 |
| 플랫폼 담당자 1명 | 캠핑장·옵션을 직접 등록하고 들어온 요청을 빠르게 처리 | 운영자에게 연락했는지, 고객에게 어떤 상태가 보이는지 | 관리자 콘솔 |
| 캠핑장 운영자 | 담당자의 연락을 받고 예약 가능 여부를 회신 | 별도 시스템 학습 부담 | **화면 없음** — 공고에 따라 업체 로그인·업체 포털 제외 |

사용자 계정/회원가입은 공고에 없으므로 MVP에서 제외한다. 예약조회는 `예약번호 + 예약자 연락처 뒤 4자리` 방식의 데모로 제안한다.

## 3. 범위와 정보 구조

### 3.1 사이트맵

```text
/ index.html                         발견 허브·매거진 큐레이션
├─ /search.html                     날짜·조건 검색 결과
│  └─ /camp.html?id={campId}        캠핑장 상세
│     └─ /booking.html?id={campId}  예약 4단계 + 결제 시뮬레이션
│        └─ /complete.html?code={}  예약 요청 결과
├─ /reservation.html               예약조회·상태·취소 요청
├─ /guide.html                     이용안내·확정 절차·데모 고지
└─ /admin.html                     담당자용 최소 관리자 콘솔
```

`camp`, `complete`는 query parameter가 있어도 독립 페이지로 딥링크된다. 모달로 상세/결제를 대체하지 않는다. 관리자는 업무 메뉴를 페이지로 늘리지 않고 한 콘솔 안의 `예약 / 캠핑장` 두 탭으로 최소화한다.

### 3.2 공통 내비게이션

- 로고 → 홈
- 캠핑장 찾기 → 검색
- 큐레이션 → 홈의 큐레이션 시작점이 아니라 홈 자체로 이동 후 콘텐츠 상단에 초점. 원페이지 메뉴처럼 쓰지 않는다.
- 예약조회 → 예약조회
- 이용안내 → 이용안내
- `날짜로 찾기` → 검색
- 관리자는 공개 GNB에 노출하지 않고 데모 안내 하단의 별도 링크로 진입한다.

### 3.3 핵심 전환 흐름

```text
발견(index)
  ├─ 검색바 입력 ───────────────→ 검색(search)
  └─ 큐레이션 카드 선택 ───────→ 상세(camp)
                                      ↓ 날짜·인원 선택
                                  예약(booking)
                                      ↓ 결제 시뮬레이션
                                  결과(complete)
                                      ↓ 상태 확인
                                  예약조회(reservation)
```

이탈 복구:

- 검색 결과 0건 → 날짜/필터 변경
- 상세 선택일 마감 → 같은 지역 다른 캠핑장
- 예약 입력 오류 → 입력 유지 + 첫 오류 포커스
- 결제 시뮬레이션 실패 → 입력/요약 유지 + 재시도
- 예약 불가 통보 → 검색 조건을 유지한 대체 캠핑장 탐색

## 5. 페이지 상세

## P01. 홈 `index.html`

### 목적

SNS/매거진처럼 캠핑장을 둘러보게 하되, 장식적 스크롤 경험에 머물지 않고 검색과 예약으로 보내는 허브다. 모든 기능을 한 페이지에 복제하지 않는다.

### 사용자가 해야 할 일

1. 감성 콘텐츠로 탐색 의향을 만든다.
2. 지역·날짜·인원을 입력하거나 큐레이션 캠핑장을 선택한다.
3. 검색 결과 또는 상세로 이동한다.

### 섹션과 다음 행동

| 순서 | 섹션 | 내용·레이아웃 | 다음 행동 |
|---:|---|---|---|
| 1 | Hero + 통합 검색 | eyebrow `CURATED OUTDOORS`, 2행 display `머무를 풍경을 고르고, 날짜까지 이어서.`; 우측 비대칭 자연 사진 4컷; 검색바 | `날짜로 캠핑장 찾기` → P02 |
| 2 | 이번 주 큐레이션 | `물가 가까운 자리` 등 카드 3장. 지역·1박가·날짜 가능 상태 | 카드 → P03 |
| 3 | 매거진 스트림 | 큰 이미지와 짧은 에디토리얼 문장 3개를 좌/우 교대. 각 기사형 블록에도 캠핑장 1곳 연결 | `이 풍경의 캠핑장 보기` → P03 |
| 4 | 테마 풀블리드 | 쿨톤 21:9 사진 + `장비보다 가볍게 떠나는 오토캠핑` | `조건으로 비교하기` → P02(테마 query) |
| 5 | 신뢰 숫자 | 데모 데이터 기준 `12곳 / 4개 지역 / 3단계 확인`; 70% countUp. 실제 데이터 이상으로 과장 금지 | `예약 방식 보기` → P07 |
| 6 | 최근 등록 | 그림자 없는 연블루 카드 3장 | 카드 → P03 |
| 7 | CTA + footer | `날짜를 정하면, 가능한 자리만 보여드릴게요.` | P02 |

### Desktop

- Hero min-height 720px, 콘텐츠 1280px, 카피 6컬럼 + 콜라주 6컬럼.
- Hero 아래 160px, 이후 섹션 120~160px 리듬.
- 매거진 스트림은 이미지 7:5와 카피 5:7을 번갈아 배치. 중앙정렬 반복 금지.
- 테마 이미지만 100vw. 텍스트는 1280px 컨테이너 안에 둔다.

### 375 mobile

- Hero는 `100vh`가 아닌 콘텐츠 기반 min-height 640px. 카피 → 통합 검색 → 대표 이미지 순.
- 보조 사진은 2장만 가로 native scroll; snap은 보조일 뿐 wheel/touch를 가로채지 않는다.
- 큐레이션·최근 등록은 1열. 매거진 카피는 이미지 아래 배치.
- 섹션 간 72px, gutter 20px.

### 상태

- 추천 데이터 loading: 3장 skeleton + `추천 캠핑장을 불러오고 있어요.`
- empty: `새 큐레이션을 준비 중이에요.` + `전체 캠핑장 보기`.
- error: 큐레이션만 실패해도 검색바는 사용 가능. `추천 콘텐츠를 불러오지 못했어요.` + 재시도.

## P02. 검색 결과 `search.html`

### 목적

날짜 가능 여부, 지역, 가격, 편의시설을 빠르게 비교해 상세 1곳을 선택하게 한다.

### 사용자가 해야 할 일

1. 현재 검색 조건과 결과 수를 확인한다.
2. 필터·정렬을 조정한다.
3. 캠핑장을 선택한다.

### 섹션과 다음 행동

| 순서 | 섹션 | 내용 | 다음 행동 |
|---:|---|---|---|
| 1 | 페이지 제목 | `9월 12일–13일, 예약 가능한 캠핑장` + 결과 수 | 조건 수정 |
| 2 | 검색 조건 bar | 지역·날짜·인원, `조건 변경` | dialog/bottom sheet |
| 3 | 필터·정렬 | 유형, 가격, 편의시설, 부가 옵션, `추천순/낮은 가격순` | 즉시 목록 갱신 또는 `적용` |
| 4 | 결과 목록 | 캠핑장 카드 3/2/1열; 가능/확인 필요/마감 | P03 |
| 5 | 페이지네이션 | 데모 데이터가 12개를 넘을 때만 노출 | 다음 결과 |
| 6 | 대체 제안 | 0건일 때 인접 날짜·지역 3개 | 조건 적용 |

### Desktop

- 제목/검색 bar 상단. 콘텐츠는 280px sticky filter + 결과 영역.
- 결과 영역 상단에 `12개 결과`와 정렬 select.
- 3열 카드, gap 24px. 필터 접기 시 4열로 늘리지 않는다.

### 375 mobile

- 상단에 검색 조건 요약 2줄과 `변경`.
- 필터·정렬 버튼 2개를 50:50. 필터는 bottom sheet, 정렬은 작은 sheet.
- 적용 chip은 가로 native scroll. 결과는 1열.
- 필터 sheet 하단에 `12개 결과 보기` sticky CTA.

### 상태

| 상태 | 카피 | 행동 |
|---|---|---|
| Loading | `선택한 날짜의 예약 가능 여부를 확인하고 있어요.` | skeleton 6/3개 |
| Empty | `선택한 날짜에 예약 가능한 캠핑장이 없어요.` | 날짜 바꾸기 / 조건 초기화 |
| Error | `검색 결과를 불러오지 못했어요. 선택한 조건은 그대로 두었습니다.` | 다시 시도 |
| Partial | `3곳은 캠핑장 확인이 필요해요.` | 카드에 `확인 필요` 표시 |

## P03. 캠핑장 상세 `camp.html?id={campId}`

### 목적

사진의 감성과 예약 판단 정보(가격·시설·규칙·가능 상태)를 함께 제공해 예약 진입 결정을 돕는다.

### 사용자가 해야 할 일

1. 사진·위치·사이트 정보를 확인한다.
2. 날짜·인원·사이트 타입을 선택한다.
3. 가격과 확인 절차를 이해하고 예약으로 이동한다.

### 섹션과 다음 행동

| 순서 | 섹션 | 내용 | 다음 행동 |
|---:|---|---|---|
| 1 | Breadcrumb + 제목 | 지역 / 캠핑장명 / 한 줄 설명 | 검색 결과로 돌아가기 |
| 2 | 갤러리 | 대표 1 + 보조 4, 사진 개수 | 전체 사진 보기 dialog |
| 3 | 핵심 정보 | 유형, 주소, 체크인/아웃, 최대 인원, 반려동물 등 | 판단 |
| 4 | 소개 | 에디토리얼 2~3문단, 과장 없는 운영 정보 | 시설 확인 |
| 5 | 사이트 타입 | 오토/데크 등 카드, 기본가·정원·남은 상태 | 타입 선택 |
| 6 | 편의시설 | 선형 아이콘 + 텍스트, 제공/미제공 구분 | 판단 |
| 7 | 부가 옵션 | 인근 음식점·장작·바비큐 등 실제 등록 옵션 | 예약에서 선택 |
| 8 | 이용·취소 안내 | 운영 규칙, 확정 절차, 취소 정책 요약 | P07 또는 예약 |
| 9 | 비슷한 캠핑장 | 같은 지역 3장 | 다른 P03 |
| — | 예약 패널 | 날짜, 인원, 타입, 1박가, 확인 필요 고지 | `이 날짜로 예약하기` → P04 |

### Desktop

- 갤러리 8:4 비대칭, 높이 560px.
- 본문 `minmax(0,1fr)` + 우측 380px sticky 예약 패널.
- 규칙·취소 정보는 아코디언으로 숨기지 않고 핵심 3줄을 먼저 표시, 자세히 보기만 확장.

### 375 mobile

- 갤러리는 한 장씩 native swipe, `1 / 5` 인디케이터와 `사진 전체 보기`.
- 예약 패널은 본문 안에 배치하고 하단 sticky bar에 `₩68,000 / 예약 계속`.
- sticky bar가 마지막 섹션과 겹치지 않도록 본문 하단 여백 96px+safe-area.

### 상태

- 선택 날짜 마감: 날짜 셀 disabled, CTA `다른 날짜 보기`.
- 확인 필요: CTA는 사용 가능하되 `예약 요청 후 담당자 확인` 고지.
- 데이터 오류: 제목/사진 등 캐시 정보는 남기고 예약 패널만 `가능 여부를 확인할 수 없어요` + 재시도.
- 잘못된 id: `캠핑장을 찾을 수 없어요` + P02.

## P04. 예약·결제 시뮬레이션 `booking.html?id={campId}`

### 목적

사용자가 입력 누락·비용 오해 없이 예약 요청을 제출하고 결제 시뮬레이션을 완료하게 한다.

### 사용자가 해야 할 일

1. 날짜·인원 확인
2. 부가 옵션 선택
3. 예약자 정보 입력·약관 동의
4. 결제 시뮬레이션 완료

### 단계와 다음 행동

| 단계 | 섹션 | 필드·정보 | 다음 행동 |
|---:|---|---|---|
| 1 | 날짜·인원 | 체크인/아웃, 성인/아동, 사이트 타입 | `옵션 선택` |
| 2 | 부가 옵션 | 장작, 바비큐 세트, 인근 음식 픽업 등 수량·가격. 선택 항목 없음을 허용 | `예약자 정보` |
| 3 | 예약자 정보 | 이름, 휴대전화, 이메일(선택), 요청사항, 개인정보·취소정책 동의 | `결제 확인` |
| 4 | 결제 시뮬레이션 | 주문명, 합계, 데모 카드 입력 또는 정적 모의 PG, 실제 청구 없음 고지 | `결제 시뮬레이션 완료` → P05 |

### 공통 요약

- 캠핑장, 날짜, 인원, 사이트, 옵션, 숙박 금액, 옵션 금액, 총액.
- 금액 변경 원인을 행별로 보여준다. 숨은 수수료 금지.
- `예약은 담당자가 캠핑장에 확인한 뒤 확정됩니다.`
- `이 데모에서는 실제 결제가 발생하지 않습니다.`

### Desktop

- 상단 4단계 표시.
- 좌 폼 + 우 360px sticky 주문 요약.
- 단계별로 URL hash 또는 history state를 갱신해 뒤로 가기 복구.
- 한 화면에 한 primary CTA.

### 375 mobile

- `2 / 4 옵션 선택` 축약 표시.
- 주문 요약은 접힌 금액 bar가 아니라 핵심 합계가 항상 보이도록 하단 sticky bar `총 ₩92,000 / 다음`.
- 키보드가 열릴 때 sticky bar가 입력을 가리지 않도록 viewport 대응.
- 결제 단계에서만 전체 주문 요약을 펼쳐 최종 확인.

### 검증·상태

| 상태 | 처리 |
|---|---|
| 입력 오류 | 상단 오류 요약 + 첫 오류로 초점. 값 유지. label 아래 구체적 문구 |
| 가용성 재확인 loading | 제출 잠금 + `마지막으로 예약 가능 여부를 확인하고 있어요.` |
| 가용성 변경 | `방금 선택한 사이트가 마감됐어요.` + 날짜/사이트 재선택, 입력값 보존 |
| 결제 loading | 버튼 label `결제 시뮬레이션 처리 중` + 중복 제출 방지 |
| 결제 error | `결제 시뮬레이션을 완료하지 못했어요. 실제 청구는 발생하지 않았습니다.` + 재시도 |
| 결제 success | 중복 요청 방지 후 P05 이동 |
| 사용자 cancel | `결제 시뮬레이션을 취소했어요. 입력한 예약 정보는 유지됩니다.` |

데모 카드 입력이 실제 PG처럼 보일 경우 상단/버튼/결과에 `시뮬레이션`을 세 번 명시한다. 실제 카드번호를 입력하지 않도록 샘플값 선택 버튼을 제공한다.

## P05. 예약 요청 결과 `complete.html?code={reservationCode}`

### 목적

결제 성공과 예약 확정을 혼동하지 않게 하고, 예약번호와 후속 절차를 명확히 전달한다.

### 사용자가 해야 할 일

1. 예약번호를 저장한다.
2. 현재 상태가 `확인 대기`임을 이해한다.
3. 예약조회로 이동한다.

### 섹션과 다음 행동

| 순서 | 섹션 | 내용 | 다음 행동 |
|---:|---|---|---|
| 1 | 결과 | success 아이콘, `결제 시뮬레이션이 완료됐어요` | — |
| 2 | 예약번호 | Bai Jamjuree, 복사 버튼 | 복사 |
| 3 | 현재 상태 | `예약 요청 접수 · 캠핑장 확인 전` warning badge | 절차 확인 |
| 4 | 예약 요약 | 캠핑장·날짜·인원·옵션·총액, `실제 청구 0원` | — |
| 5 | 다음 절차 | ① 담당자 접수 ② 캠핑장 확인 ③ 확정/불가 안내 | P06 |
| 6 | 행동 | primary `예약 상태 확인`, secondary `홈으로` | P06/P01 |

### Desktop / 375 mobile

- Desktop: 결과 카드 max-width 760px 중앙, 주변 장식 최소.
- Mobile: border 없는 전체폭. 예약번호는 줄바꿈되지 않게 20px, 복사 버튼 44px.
- 성공 confetti·burst 금지. reduced-motion 여부와 무관하게 정적 아이콘 사용.

### 상태

- 잘못된 code: `예약 정보를 찾을 수 없어요` + P06 조회 폼.
- 재방문: 성공 애니메이션 반복 없이 현재 상태를 읽어준다.
- API error: 예약번호를 알고 있으면 화면에 유지하고 재시도.

## P06. 예약조회·취소 `reservation.html`

### 목적

비회원 사용자가 예약 진행 상태를 확인하고, 허용된 경우 취소 요청을 남기게 한다.

### 사용자가 해야 할 일

1. 예약번호와 연락처 뒤 4자리를 입력한다.
2. 상태·다음 절차를 확인한다.
3. 필요하면 취소 요청 또는 새 검색을 한다.

### 섹션과 다음 행동

| 순서 | 섹션 | 내용 | 다음 행동 |
|---:|---|---|---|
| 1 | 조회 폼 | 예약번호, 연락처 뒤 4자리 | `예약 조회` |
| 2 | 예약 요약 | 캠핑장·날짜·금액·옵션 | P03 |
| 3 | 상태 타임라인 | 접수 / 캠핑장 확인 중 / 확정·불가·취소 | 상태별 행동 |
| 4 | 연락 안내 | 담당자 확인 구조, 문의 채널 placeholder | 문의 또는 대기 |
| 5 | 취소 | 취소 가능 시 destructive secondary | 확인 dialog → 취소 요청 |

### 상태별 카피·행동

| 상태 | 제목 | 설명 | CTA |
|---|---|---|---|
| 접수 | `예약 요청을 접수했어요.` | `담당자가 내용을 확인하기 전입니다.` | `예약 내용 보기` |
| 확인 중 | `캠핑장에 가능 여부를 확인 중이에요.` | `담당자가 캠핑장 운영자에게 연락했습니다.` | 없음/문의 |
| 확정 | `예약이 확정됐어요.` | 체크인 정보와 준비 안내 | `캠핑장 정보 보기` |
| 예약 불가 | `선택한 일정으로 예약하기 어려워요.` | 실제 결제 없음/환불 정책에 맞는 문구 | `비슷한 캠핑장 찾기` |
| 취소 요청 | `취소 요청을 확인 중이에요.` | 처리 예상 절차 | 없음 |
| 취소 완료 | `예약 요청이 취소됐어요.` | `이 데모에서 실제 결제는 발생하지 않았습니다.` | `다시 찾기` |

### Desktop / 375 mobile

- Desktop: 조회 전 폼 560px 중앙. 조회 후 8:4 본문/요약.
- Mobile: 폼 full-width; 타임라인은 세로; 상태 카드에 핵심 CTA 하나.
- 취소 확인 dialog는 영향, 되돌릴 수 없음, 실제 결제 여부를 명시.

### 오류

- 인증 불일치: `예약번호 또는 연락처 정보가 맞지 않아요.` 어느 값이 틀렸는지 노출하지 않음.
- 5회 연속 실패: 데모에서는 잠금 상태를 시각화하되 실제 보안 기능처럼 과장하지 않는다.
- 조회 오류: 입력 유지 + 재시도.

## P08. 관리자 콘솔 `admin.html`

### 목적

담당자 1명이 캠핑장·부가 옵션을 직접 등록하고 예약 요청을 확인·상태 변경하는 최소 운영 화면이다.

### 사용자가 해야 할 일

1. 확인 대기 예약을 찾는다.
2. 캠핑장 운영자 연락 후 상태를 갱신한다.
3. 캠핑장 정보·가격·부가 옵션을 등록/수정한다.

### 정보 구조

- 탭 1 `예약 요청` — 기본 진입
- 탭 2 `캠핑장 관리`
- 사용자·업체·광고·정산·통계 상세 메뉴는 MVP 제외.

### 섹션과 다음 행동

| 탭 | 섹션 | 내용 | 다음 행동 |
|---|---|---|---|
| 예약 요청 | KPI | 오늘 요청, 확인 대기, 확정 | 목록 필터 |
| 예약 요청 | 필터 | 상태, 날짜, 캠핑장, 검색 | 목록 갱신 |
| 예약 요청 | 목록 | 예약번호, 고객, 캠핑장, 일정, 금액, 상태 | 상세 panel |
| 예약 요청 | 상세 panel | 연락처 마스킹, 요청·옵션, 상태 이력, 내부 메모 | `상태 업데이트` |
| 캠핑장 관리 | 목록 | 노출 상태, 기본가, 지역, 수정일 | 편집 panel |
| 캠핑장 관리 | 등록/편집 | 기본정보, 소개, 가격, 사이트, 편의시설, 부가 옵션, 이미지 | `저장` |

### 상태 변경 규칙

```text
접수
 ├─→ 캠핑장 확인 중
 │    ├─→ 확정
 │    └─→ 예약 불가
 └─→ 취소 요청 → 취소 완료
```

- 상태 변경 dialog에 `고객에게 보이는 문구`를 미리 보여준다.
- `확정`에는 캠핑장 확인 일시와 담당 메모가 필요하다.
- `예약 불가/취소 완료`는 사유를 선택/입력한다.
- MVP 데모는 외부 메시지를 실제 발송하지 않는다. `상태가 저장됐습니다. 데모에서는 알림이 발송되지 않습니다.`라고 표시한다.

### Desktop

- 240px 좌측 내비, 콘텐츠 max-width 없음(업무 표에 충분한 폭).
- 표 시작 2px ink line, 행 1px border. hover는 연블루.
- 상세는 우측 480px panel. 상태 업데이트 후 해당 행을 읽어 최신 상태를 확인.

### 375 mobile

- 좌측 내비를 상단 2탭으로 변환.
- KPI 3개 가로 overflow가 아니라 1열 또는 3등분 compact.
- 표를 카드형 행으로 전환: 예약번호/캠핑장/일정/상태/상세만 우선.
- 폼은 단일 열. 이미지 업로드는 실제 업로드 기능이 아니면 `샘플 이미지 선택`으로 카피 일치.

### 상태

- loading: KPI skeleton + 5행 skeleton.
- empty: `확인할 예약 요청이 없어요.` / `등록된 캠핑장이 없어요.` + 등록 CTA.
- error: `예약 목록을 불러오지 못했어요.` + 재시도, 다른 탭은 사용 가능.
- save success: inline status + toast `변경사항을 저장했어요.`
- save error: panel 유지, 값 보존, `저장하지 못했어요. 다시 시도해 주세요.`
- conflict: `다른 화면에서 상태가 변경됐어요.` 최신 상태 다시 불러오기.

### 실패·예외 경로

- P02 검색 0건에서 날짜 변경 후 결과 복구.
- P03 가용성 API 실패 시 콘텐츠를 잃지 않고 재시도.
- P04 제출 직전 마감 상태로 바뀌면 예약자 입력 보존.

- P06 잘못된 조회 정보가 어떤 값이 틀렸는지 노출하지 않음.
- P08 상태 충돌 시 덮어쓰지 않고 최신 상태 확인.

### 접근성

- 키보드만으로 P01→P05 완료.
- 모든 페이지에 하나의 명확한 `h1`; landmark와 skip link.
- 200% 확대, 320 CSS px에서도 핵심 기능 가로 overflow 없음.
- 44×44px 터치 타겟, 포커스 표시, 오류 요약, aria-live 확인.
- reduced-motion에서 숨은 콘텐츠·자동 스크롤·countUp 대기 없음.

## 9. findings

1. 공고의 `예약+PG`와 담당자 확인 후 `예약 확정`은 같은 순간이 아니다. 화면에서 `결제 시뮬레이션 완료`, `예약 요청 접수`, `예약 확정`을 분리해야 한다.
2. 매거진형 큐레이션을 홈 전체의 목적처럼 다루면 예약 검증이 약해진다. 감성은 P01, 비교는 P02, 신뢰는 P03, 오류 예방은 P04로 역할을 분리했다.
3. 업체 로그인 화면 제외는 IA 축소에 유리하지만 담당자 1명의 처리 부담이 커진다. P08에 `확인 대기` 우선순위와 상태 이력을 넣어 연락 단절 우려를 화면으로 보완한다.
4. 회원 기능이 없으므로 예약조회 인증 정책이 비어 있다. 데모용으로 예약번호+연락처 뒤 4자리를 제안하지만 실제 서비스 전환 시 개인정보·보안 검토가 필요하다.

## 12. needs_confirmation

1. `예약 요청 전에 결제`인지 `캠핑장 가능 확인 후 결제`인지 실제 정책이 확정되지 않았다. 본 MVP는 공고 문구에 맞춰 결제 시뮬레이션 후 담당자 확인으로 설계했으나, 실제 서비스에서는 결제 승인/취소·재고 정책과 함께 재결정해야 한다.
2. 예약 취소 가능 시점, 수수료, 환불 규칙이 원본에 없다. P06은 상태만 설계했고 금액 규칙은 확정하지 않았다.
3. 예약조회 인증은 가정이다. 휴대전화 인증 또는 사용자 계정이 요구되면 P06 범위가 달라진다.
4. 캠핑장 큐레이션 원고·목록은 클라이언트 준비 자료로 표시되어 있으나 최신본이 아직 작업 폴더에 없다. 실제 카피·필터·옵션 수는 자료 수령 후 확정한다.
