| 단서 | 숨은 니즈 |
|---|---|
| "1초 이내" + "폴링 주기 1초 이하" | 감지 지연 = **폴링 주기 + 응답 지연**. 1초 폴링이면 등록 직후 놓친 공지는 1초 초과 가능 → 트레이드오프 인지 필요 |

## 2. 웹 리서치 — 치명적 발견 (그대로 만들면 실패하는 지점)

### ⓪ 실행으로 드러난 두 결함 ★ (리뷰에서 발견·수정)

문서로 트레이드오프를 정리하는 것과, 코드가 실제로 그 주기를 지키는 것은 다릅니다.
납품 코드를 직접 실행해 재보니 수용 기준 첫 줄부터 미달이었습니다.

| 항목 | 고치기 전 | 납품본 | 원인 |
|---|---|---|---|
| 정상 상태 폴링 주기(설정 1.0초) | **1.118초** | **1.002초** | `sleep(주기)`를 요청 뒤에 붙여 실제 주기 = 주기 + 응답지연 |
| 한 거래소 타임아웃 시 다른 거래소 주기 | **4.05초** | **1.000초** | 두 거래소를 순차 폴링 → 한쪽 타임아웃(3초)을 다른 쪽이 대기 |

- 주기 측정은 10주기/20주기를 각각 실행해 `(T20−T10)/10`으로 계산했습니다.
  마지막 주기의 `sleep` 누락 편향을 제거하기 위해서입니다.
- 두 번째 결함은 `--break`(존재하지 않는 도메인 → DNS 50ms 즉시 실패)로는 드러나지
  않습니다. 실제 장애에 더 흔한 **응답 없음**을 재현하려고 `--hang` 옵션을 추가했습니다.
- 수정: **마감 시각 기준 대기** + **거래소별 독립 스레드**.

### ⓪-2 요청 제한 — 헤더로 확인된 사실 ★

공고 비기능 요구의 *"거래소 요청 제한을 넘지 않는 폴링 주기"*는 추정할 필요가 없습니다.
업비트가 응답 헤더로 남은 요청량을 알려줍니다.

```
Remaining-Req: group=origin; min=6; sec=0
Limit-By-Origin: Yes
Access-Control-Allow-Origin: *
```

Origin 값을 바꿔 가며(주기마다 독립 카운터) 6회씩 실제로 요청한 결과:

| 폴링 주기 | 분당 요청 | 성공 | 성공률 |
|---|---|---|---|
| 1초 | 60회 | 1/6 | 17% |
| 3초 | 20회 | 2/6 | 33% |
| 6초 | 10회 | 3/6 | 50% |
| **12초** | **5회** | **6/6** | **100%** |

- **분당 약 6회가 한계**입니다(`min=6` 헤더와 일치).
- `Limit-By-Origin: Yes` — **Origin 단위**로 셉니다. 도메인을 옮겨도 카운터만 새로
  시작될 뿐 1초 폴링은 동일하게 막힙니다.
- **429 응답에는 ACAO 헤더가 없습니다.** 그래서 브라우저에서는 상태 코드를 읽지 못하고
  `Failed to fetch`(CORS 오류)로 보입니다 — 요청 제한을 CORS 차단으로 오진하기 쉽습니다.
- 공지 엔드포인트(`api-manager`)는 이와 별개로 **Origin 헤더가 붙으면 도메인 무관 403**
  입니다(tengtengsoft.kr · github.io · localhost 3곳 실측 동일).
- **파이썬은 영향 없습니다.** `urllib`은 Origin 헤더를 보내지 않아 `group=origin` 버킷에
  들어가지 않습니다. 1초 주기 20주기 실행에서 실패 0회.

### ① "1초 이내"와 폴링 주기의 모순 ★ (이 과업의 핵심 함정)
감지 지연 = (다음 폴링 시각 − 공지 등록 시각) + 응답 지연. 폴링 주기가 1초면 등록 직후 폴링을 **놓친** 공지는 최악 **~1초 + 응답지연(실측 ~130ms)**이 걸려 1초를 넘긴다. 진짜 1초를 보장하려면 폴링을 1초보다 촘촘히 해야 하는데, 그러면 ②의 요청 제한에 걸린다.
→ 데모: `지연 vs 요청제한` 화면에서 주기별 **평균/최악 지연·분당 요청·1초 보장 여부·예산 초과**를 표로 보여줘 "동시에 만족하는 구간이 좁다"는 것을 수치로 드러낸다. 대안으로 **적응형 폴링**(평상시 여유 → 감지 직후 촘촘) 제안.

### ② 거래소 요청 제한/차단 — 공지 엔드포인트는 웹 트래픽 ★
업비트·빗썸 공지 목록은 트레이딩 API가 아니라 **웹/매니저 엔드포인트**에 가깝다. 1초 미만으로 계속 때리면 rate-limit·IP 차단 위험. 무료로 무제한 폴링이 되는 게 아니다.
→ 데모: **분당 요청 예산 가드**(거래소당 안전 상한 가정)와 경고를 넣어 "주기 너무 짧음 = 차단 위험"을 실시간 표시.

### ③ 중복 제거는 반드시 "id 기준" ★
제목 기준 dedup은 **재공지·제목 수정** 시 새 공지로 오인하거나 다른 공지를 같은 것으로 본다. 공지 고유 식별자(id/seq)로 seen-set을 관리해야 한다.
→ 데모: seen-set을 id로 관리. 중복 제거 OFF 토글 시 같은 공지가 매 주기 재출력되는 것을 로그로 실증.

### ④ 무중단·거래소 단위 예외 격리
`fetch → parse` 전체를 하나의 try로 묶으면 한 거래소 장애가 다른 거래소 감지까지 멈춘다. 예외를 거래소 단위로 잡고, 실패는 **백오프**로 흡수해야 스크립트가 죽지 않는다.
→ 구현: 거래소별 상태·백오프 독립. 업비트 접속 불가 시에도 빗썸 감지 지속. 실패 시 지수 백오프 후 자동 복구(실행 로그로 확인).

### ⑤ 응답 스키마 변경 리스크
두 거래소 공지 응답 스키마가 다르고 바뀔 수 있다. 파싱을 한 곳(`extract`)에 몰아 스키마 변경 시 그 함수만 고치게 설계.
