# 시나리오 · 사용자 여정 — ZEROLAG 신규 공지 감지

> 스크립트 과업이라 화면 사용자보다 **운영 흐름**이 중심입니다.

---

## 1. 등장인물

| 역할 | 누가 | 무엇을 원하나 | 무엇을 불안해하나 |
|---|---|---|---|
| **운영자(발주사)** | 스크립트를 서버에 띄워 돌리는 사람 | 신규 공지를 사람보다 빨리·자동으로 인지 | 새벽에 죽어있으면? 차단당하면? 같은 공지 여러 번? |
| **개발자(수행)** | 스크립트 작성자 | 최소 코드로 1초 이내·무중단·약관 준수 | "1초"와 "요청 제한"을 동시에 어떻게 만족? |

**핵심**: 이 스크립트는 화면이 없다. 그래서 데모는 **로직이 실제로 어떻게 도는지**(폴링·감지·복구·중복제거)를 눈에 보이게 만드는 것이 목적이다.

---

## 2. 시간순 여정

| 단계 | 상황 | 관련 로직 | 없으면 벌어지는 일 |
|---|---|---|---|
| 기동 | 스크립트 시작 | 최초 1회는 기존 공지를 기준선으로 저장(출력 안 함) | 기동하자마자 옛 공지 수십 개가 "신규"로 쏟아짐 |
| 폴링 | N초마다 공지 조회 | 주기 = config, 요청 예산 이내 | 너무 촘촘 → 차단 / 너무 느슨 → 감지 지연 |
| 감지 | 신규 id 발견 | seen-set에 없으면 제목 출력 | 중복 제거 없으면 같은 공지 매 주기 출력 |
| 실패 | 네트워크 오류·타임아웃 | 백오프 후 다음 주기 재시도(종료 안 함) | 예외로 스크립트 죽음 → 새벽 내 감지 공백 |
| 격리 | 한 거래소만 장애 | 거래소 단위 예외 격리 | 업비트 장애가 빗썸 감지까지 멈춤 |
| 복구 | 장애 해소 | 성공 시 백오프 리셋·감지 재개 | 수동 재시작 필요 |

## 3. "1초 이내"를 둘러싼 갈등 (이 과업의 본질)

- 운영자: "신규 공지 뜨면 **1초 안에** 알아야 한다."
- 현실: 감지 지연 = (다음 폴링까지 대기) + (응답 지연). 1초 폴링이면 **최악 ~1.2초**.
- 진짜 1초 보장 → 폴링 촘촘 → **분당 요청↑ → 차단 위험**.
- 데모의 `지연 vs 요청제한` 표가 이 갈등을 수치로 보여주고, **적응형 폴링**을 해법으로 제시한다.

---

## 4. 기능별 존재 이유

- **id 기준 중복 제거**: 제목 기준이면 재공지·수정에 오작동. 고유 식별자로만 안전.
- **지수 백오프**: 장애 시 재시도를 촘촘히 하면 차단 악화 → 점점 벌려 재시도.
- **거래소 단위 격리**: 한 곳 장애가 전체를 멈추지 않게.
- **설정 분리(config)**: 운영자가 코드 못 건드려도 주기·백오프 조정.
- **요청 예산 가드**: 약관 위반·차단 방지.
- **기동 시 기준선**: 시작 순간의 기존 공지를 신규로 오인하지 않게.

---

## 5. 상태 흐름 (구현됨)

- **폴링(거래소별)**: 대기 → (백오프 중이면 skip) → 요청 → 성공(감지) / 실패(백오프 예약)
- **공지**: 발행 → 첫 폴링에서 감지(출력) → seen 등록 → 이후 재폴링 시 무시

---

## 6. 비는 구멍 (착수 전 확인 필요)

임의로 정하지 않고 착수 시 확정(공고도 동일 입장).

1. **이용약관상 폴링 허용 범위** — 주기 1초 수준 반복 조회 가능 여부(차단 정책).
2. **실행 환경** — 파이썬 버전·OS(서버 사양).
3. **감지 결과 출력 형태** — 표준출력 / 로그 파일 / 함수 반환 중 택일.
4. **공지 등록 시각 기준** — 거래소 제공 시각을 기준으로 지연을 측정할지.
5. **응답 스키마** — 두 거래소 현재 응답 구조·변경 대응.
6. **재기동 시 seen 유지 여부** — 재시작 후 직전 기준선 복원할지(파일 저장).

> 데모는 합리적 기본값으로 구현했고, 위 6가지는 계약 시 확정할 항목으로 분리했습니다.
