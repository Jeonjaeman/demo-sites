# 업비트·빗썸 신규 공지 감지 스크립트 (실행 가능 납품물)

Python 3.7+ **표준 라이브러리만**으로 동작합니다. 별도 설치가 필요 없습니다.

```bash
python detector.py
```

## 파일
| 파일 | 설명 |
|---|---|
| `detector.py` | 감지 스크립트(무중단 폴링 루프, 거래소별 독립 스레드) |
| `config.py` | 폴링 주기·타임아웃·백오프·중복제거·seen 상한 설정(코드 수정 없이 조정) |
| `requirements.txt` | 외부 의존성 없음(표준 라이브러리만) |

## 실행 옵션
```bash
python detector.py                 # 무중단 실시간 감지(운영)
python detector.py --cycles 3      # 거래소별 3주기만 돌고 종료(테스트)
python detector.py --interval 1.0  # 폴링 주기 덮어쓰기(초)
python detector.py --demo-new 2    # 첫 주기에 최신 2건을 '신규'로 취급(감지 경로 시연)
python detector.py --break UPBIT   # (테스트) 즉시 실패 장애 주입 (DNS 해석 불가)
python detector.py --hang UPBIT    # (테스트) 응답 없음 장애 주입 (타임아웃까지 매달림)
```

## 설계상 중요한 두 가지

공고 수용 기준이 **“폴링 주기를 1초 이하로 유지한 상태에서 1초 이내 출력”**이라
아래 두 가지를 지키지 않으면 기준을 넘깁니다. 둘 다 실측으로 확인했습니다.

### ① 폴링 주기는 '마감 시각' 기준

`sleep(주기)`를 요청 **뒤에** 붙이면 실제 주기 = `주기 + 응답지연`이 되어 1초를 넘깁니다.
다음 폴링 시각을 미리 정해 두고 남은 시간만 대기합니다.

```
정상 상태 주기 측정 — 10주기/20주기를 각각 실행해 (T20−T10)/10 (종료 편향 제거)
  sleep(주기)를 뒤에 붙인 구조 : 1.118초   ← 설정 1.0초인데 초과
  마감 시각 기준 (현재)        : 1.002초   ← 설정값 그대로 유지
```

### ② 거래소마다 독립 스레드

두 거래소를 순차로 돌면, 한쪽이 타임아웃(3초)까지 매달릴 때 다른 쪽이 그만큼 기다립니다.
`--break`(DNS 즉시 실패)로는 이 문제가 드러나지 않아 `--hang`(응답 없음)을 따로 두었습니다.

```
UPBIT 를 응답 없음 상태로 두고 BITHUMB 의 폴링 간격만 측정
  순차 폴링        : 4.05초로 밀림
  독립 스레드 (현재) : 1.000초 유지 (간격 실측 최대 1.010초)
```

## 사용 엔드포인트 (2026-07 실측·동작 확인)
- **업비트**: `https://api-manager.upbit.com/api/v1/announcements?os=web&page=1&per_page=20&category=all`
  응답: `{"success":true,"data":{"notices":[{"id":..,"title":..,"first_listed_at":..}]}}` → `id` 기준 감지
- **빗썸**: `https://feed-api.bithumb.com/v1/notices?count=20`
  응답: `[{"title":..,"pc_url":"https://feed.bithumb.com/notice/1654265","published_at":..}]`
  → 고유 id 필드가 없어 `pc_url` 끝의 공지 번호를 식별자로 사용

> 두 엔드포인트는 기본 User-Agent로 차단될 수 있어 `config.py`의 `USER_AGENT`를 브라우저형으로 지정합니다.
> 스키마가 바뀌면 `detector.py`의 `_extract_upbit` / `_extract_bithumb` 함수만 수정하면 됩니다.

## 수용 기준 대조 (실행으로 확인)

| 공고 수용 기준 | 결과 | 근거 |
|---|---|---|
| 폴링 주기 1초 이하 유지 + 1초 이내 출력 | 충족 | 정상 상태 주기 **1.002초** · 최악 지연 = 주기 + 응답지연(~130ms) ≈ 1.13초 |
| 동일 공지가 두 번 이상 출력되지 않음 | 충족 | `--demo-new 2`로 4건 감지 후 2·3주기 재출력 0건 |
| 오류에도 종료되지 않고 다음 주기 복구 | 충족 | 지수 백오프 0.5→1→2→4초, 성공 시 리셋 |
| 한 곳이 응답하지 않아도 다른 곳 감지 계속 | 충족 | `--hang UPBIT` 중에도 BITHUMB 주기 **1.000초** 유지 |

실측 로그 예시(`--demo-new 2`):
```
[BITHUMB] 기준선 확보 — 기존 공지 20건 · 응답 116ms · 이후 신규만 출력 (시연: 최신 2건 신규 취급)
[BITHUMB] 신규 공지 (id=1654250): 이온(AEON) 원화마켓 추가 기념 에어드랍 이벤트 · 등록 2026-07-29 18:00:00
[UPBIT]   신규 공지 (id=6423): 디지털 자산 및 예치금 실사보고서 결과 공개 · 등록 2026-07-29T17:20:09+09:00
```

## 알려진 제약(정직 고지)
- **빗썸 `feed-api`는 `count` 값과 무관하게 최근 약 6건만 반환**합니다. 1초 주기 폴링에서는 신규 공지가 항상 목록 최상단에 먼저 뜨므로 감지에 지장이 없지만, 폴링 간격 사이에 6건을 초과하는 공지가 한꺼번에 올라오면 일부가 밀려날 수 있습니다(현실적으로 드묾).
- 두 엔드포인트는 **비공식(웹/피드) 엔드포인트**입니다. 거래소가 구조를 바꾸면 `_extract_*` 수정이 필요하며, **이용약관상 폴링 허용 범위**는 착수 전 확인 대상입니다(과도한 초단위 폴링은 차단 위험).
- 감지 결과 출력 형태는 현재 표준출력(print)입니다. 로그 파일 또는 함수 반환으로의 전환은 `log()` 한 곳만 바꾸면 됩니다.
- 기억하는 공지 id는 `SEEN_MAX`(기본 5,000건)로 상한이 있습니다. 무중단 실행에서 메모리가 계속 늘지 않도록 오래된 것부터 버립니다.
- **재시작하면 기준선을 다시 잡습니다.** 스크립트가 내려가 있는 동안 올라온 공지는 신규로 출력되지 않습니다. 상시 운영에서 이 구간까지 잡으려면 seen 목록을 파일에 저장하는 옵션이 필요합니다(착수 전 확인 항목).
