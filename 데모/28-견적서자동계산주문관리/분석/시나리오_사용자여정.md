# 시나리오 · 사용자 여정 — GREENDESK 교사 전용 B2B

> 기능 목록을 **시간순 사용 흐름**으로 재구성해, 각 기능이 왜 존재하는지와 정의가 비는 지점을 드러냅니다.

---

## 1. 등장인물

| 역할 | 누가 | 무엇을 원하나 | 무엇을 불안해하나 |
|---|---|---|---|
| **방문 교사** | 어린이집·유치원·초중고 선생님 | 신규 클래스/교구를 보고, 빠르게 견적을 받고 싶다 | 매번 담당자에게 전화·메일해야 하나? 금액이 맞나? |
| **승인 교사(회원)** | 승인된 선생님 | 인원·수량만 넣어 직인 찍힌 견적서를 직접 받고, 예전 것도 다시 받고 싶다 | 예산 결재용 문서가 제때 나올까, 수정하면 이전 게 사라지나 |
| **관리자** | 교구 회사 담당자 | 승인·발급·주문·대금을 한 화면에서 관리하고, 손 계산을 없애고 싶다 | 미수금 누락, 잘못된 단가로 발행, 서류 분실 |

**역할 겸임 주의**: 방문 교사 ↔ 승인 교사는 **동일인의 상태 전이**(가입신청→승인)입니다. 같은 사람이 승인 전/후로 **보는 화면이 달라져야** 합니다(승인 전 = 견적 계산만, 발행 불가 / 승인 후 = 발행·주문 가능). 이 경계가 곧 권한 설계의 핵심.

## 2. 시간순 여정 (발견 → 판단 → 행동 → 대기 → 실행 → 사후)

| 단계 | 상황 | 쓰는 화면 | 이 기능이 없으면 |
|---|---|---|---|
| 발견 | 신규 클래스·교구를 홈페이지에서 봄 | 안내(홈) · 교구표 | 교사가 B2B 경로를 못 찾아 이탈 |
| 판단 | "우리 반 25명이면 얼마?" | 견적 계산(수업/교구) | 전화·메일 왕복, 담당자 병목 |
| 진입 | 가입하고 기관 증명 | 회원가입 + 고유번호증 | 아무나 도매가 열람 → 단가 노출 |
| 대기 | 승인 기다림 | 승인 대기 화면 | 진행 상태 몰라 재문의 폭증 |
| 실행 | 견적서 발행·다운로드 | 견적서 상세 + PDF | 담당자 수작업, 야근, 오발행 |
| 수정 | 인원이 바뀜 | 수정 요청 → 재발행 | 1차 근거 소실, 분쟁 시 불리 |
| 주문 | 수업 예약/교구 주문 | 주문 신청 | 명단·주소가 메일에 흩어짐 |
| 사후 | 진행·청구·결제 추적 | (관리자) 주문 관리 | 미수금 누락, 정산 지연 |
| 재열람 | 지난 서류 다시 받기 | 마이페이지 발급 이력 | 재발급도 수작업 |

## 3. 역할별 시야 차이 (같은 데이터, 다른 화면)

| 데이터 | 교사가 보는 것 | 관리자가 보는 것 |
|---|---|---|
| 견적서 | 내 것만, 회차별 재다운로드 | 전 교사, 재발행/재발송 처리 |
| 회원 | 내 승인 상태 | 전 회원 승인/반려/서류/단가 노출 대상 |
| 주문 | 내 진행·청구·결제 현황 | 전 주문 상태 변경·미수금 집계 |
| 단가 | 계산 결과(금액만) | 단가표·강사비 규칙 **편집** |

→ 단가 규칙을 관리자가 바꾸면 교사 견적이 **즉시** 달라진다(데모에서 실측 검증). 이 "한 곳 수정 → 전체 반영"이 손 계산 제거의 핵심.

## 4. 기능별 존재 이유 (전수 매핑)

- **고유번호증 업로드/승인**: 도매 단가를 아무에게나 노출하지 않기 위한 게이트. 승인 = 단가 열람 권한 부여.
- **인원 구간별 강사비**: 강사는 15명당 1인 배정이 현실 → 구간 정액. 비례식이면 경계값에서 급증/역전.
- **회차 보존(rev)**: 예산 결재·세금계산서 증빙은 발행 이력이 곧 근거. 덮어쓰면 분쟁에서 진다.
- **PDF 직인·문서번호**: 결재 상신용 정식 문서. 위변조 방지(번호·발행일시).
- **주문 상태 3분리 + 청구/결제 플래그**: 진행과 대금 회수는 별개 축. 완료됐지만 미수금인 건을 잡아내야 함.
- **다운로드 센터**: 약관·단가표 등 반복 요청 서류의 셀프 서비스화.

---

## 5. 상태 흐름 (구현됨)

- **회원**: 가입신청 → 승인대기 → (승인 | 반려) → [삭제]
- **견적서**: 1차 발행 → (수정요청) → 재발행(2·3차, 이전 회차 보존) → 확정
- **주문**: 접수 → 진행중 → 완료 / 청구(방법·일자) / 결제완료(완료일)

---

## 7. 비는 구멍 (착수 전 미팅 확인 필요)

시나리오를 그리면 공고에 정의가 없는 예외가 드러납니다 — **임의로 정하지 않고 착수 시 협의**(공고도 동일 입장).

1. **강사비 구간·교구 단가표 확정값** — 데모는 합리적 가정치. 실제 규칙·경계(예: 45/46명) 확정 필요.
2. **견적 유효기간 경과 후** 재발행 규칙 — 자동 만료? 관리자만 재활성?
3. **반려 후 재신청** 동선 — 같은 계정 재제출? 새 신청?
4. **주문 취소·부분 취소** — 접수 후 취소 시 견적/청구 처리.
5. **혼합 주문**(수업 예약 + 교구 동시) — 한 견적에 묶을지, 분리할지.
6. **세금계산서 발행 주체·시점** — 견적 확정 시? 배송 완료 시?
7. **명단 파일 개인정보**(학생 명단) 보관·파기 주기.
8. **직인 이미지·증빙 양식·발신번호** 제공 시점(문자사 등록에 영업일 소요).

> 이 8가지는 데모 화면에는 합리적 기본값으로 구현되어 있고, 실제 계약 시 확정할 항목으로 분리해 두었습니다.
