## 1. 니즈 분석

### 명시된 니즈
| 요구 | 공고 원문 근거 |
|---|---|
| 회원가입/로그인 (이메일+소셜) | 2-1 |
| 라이브 스코어 보드 (종목별·날짜별) | 2-1 |

### 숨은 니즈 (공고 행간)
- **"아이디어만 있는 상태" + "IT 경험 없음"** → 화면설계 이전에 *API 계약·스토어 심사·운영 리스크*를 대신 판단해 줄 파트너가 필요. 견적보다 "이 사람이 함정을 아는가"가 선정 기준.
- **"외부 스포츠 API(유료) 계약 담당 인력 배정"** → 클라이언트가 API를 직접 계약함. 그런데 Sportradar와 API-Football은 **가격이 500배** 차이 나므로, 어떤 API로 설계하느냐를 착수 전에 확정해 줘야 함 (§2 리서치).
- **"기존 모바일 전용 앱들의 한계"** → 국내 라이브스코어 앱 대비 차별점은 "PC 웹 + 커뮤니티 통합". 커뮤니티가 붙는 순간 **도박 스팸·UGC 심사 요건**이 따라옴 — 공고에는 이 대비가 없음.
- **8주 내 스토어 등록** → 심사 리젝 1회당 1~2주 지연. 리젝 사유 1순위(UGC 요건)를 처음부터 설계에 넣어야 일정이 지켜짐.

## 2. 웹 리서치 — 치명적 발견 (근거 URL 포함)

### 발견 ① Sportradar와 API-Football의 가격 차이는 500배 — "등"으로 병기할 수 없는 결정
- API-Football: Free 100req/일 → 유료 $19~39/월 (7,500~150,000 req/일). 전 요금제에서 라이브 15초 갱신.
  https://www.api-football.com/pricing
- Sportradar: 공개 가격 없음(견적제). 스타트업 커스텀도 월 수천 달러부터, 일반적으로 $10,000+/월.
  https://www.lsports.eu/blog/sports-data-cost/ · https://datarade.ai/data-providers/sportradar/profile
- **판단**: 총예산 2,500만 원 프로젝트에서 Sportradar는 API 비용만으로 연 예산 초과. 1차 오픈은 API-Football(축구 중심) 기준으로 설계하고, 야구·농구 등 커버리지 확장은 2차에서 API 추가(TheSportsDB, API-Sports 계열 등) 검토가 현실적.
- **데모 반영**: 「검토 항목」 API 비용 시뮬레이터 — 동시접속 슬라이더로 요금제를 실계산.

### 발견 ② 클라이언트 직접 폴링 구조면 과금이 동접에 정비례 폭발
- 라이브 데이터는 15초 간격 갱신. 이용자 단말이 API를 직접 부르면 동접 10,000명 × 시청 2h × 240회/h = **하루 480만 요청** → 최고 요금제(150,000/일)로도 32배 초과.
- 서버가 전 경기를 15초에 1회 일괄 폴링(livescore 엔드포인트) → Redis 캐시 → WebSocket 팬아웃이면 **동접과 무관하게 일 ~7,000 요청** → $19 요금제로 충분.
- 공고의 "Redis 캐싱" 요구는 정확한 방향이며, 핵심은 캐싱 자체가 아니라 **"폴링 주체를 서버 1곳으로 고정"**하는 파이프라인 설계.
- **데모 반영**: 관리자 「API 모니터링」 — 폴링 파이프라인·쿼터 게이지·캐시 히트율·장애 시뮬레이션(스테일 서빙).

### 발견 ③ 커뮤니티를 넣는 순간 App Store 가이드라인 1.2가 적용 — 요건 미비 시 리젝
- UGC 앱 필수 4요소: ① 부적절 콘텐츠 필터 ② 신고 메커니즘 ③ **이용자 차단** ④ 신고 24시간 내 조치.
  https://developer.apple.com/app-store/review/guidelines/ · https://buddyboss.com/docs/app-store-guideline-1-2-safety-user-generated-content/
- 공고 2-2에는 "신고 기능"만 있고 **차단(block)이 없음** → 그대로 만들면 iOS 심사에서 리젝, 8주 일정의 마지막 마일스톤(스토어 등록)이 깨짐.
- **데모 반영**: 응원방 메시지 신고·차단, 마이페이지 차단 목록, 관리자 신고 큐 **24h SLA 타이머**.

### 발견 ④ 스포츠 커뮤니티는 불법 도박 홍보의 1순위 표적
- KISA 집계: 전체 스팸 문자의 43%가 도박 관련. 스포츠 응원 게시글·갤러리에 사설 토토 광고 댓글이 집중되며, 계정 차단만으로는 재가입을 막지 못함.
  https://csrc.kaist.ac.kr/blog/2022/03/24/디지털-질병-불법-도박사이트의-특징을-파헤치다/ · https://cleansports.kspo.or.kr/
- 오픈 직후부터 유입되므로 **런칭 시점에 자동 필터가 있어야 함**. 운영자가 새 패턴을 즉시 추가할 수 있는 금칙어 사전 구조가 표준.
- **데모 반영**: 응원방·게시판 금칙어 자동 블라인드(실동작), 관리자 금칙어 사전(추가 시 사용자 화면에 즉시 반영 — localStorage 공유), 자동 감지 로그.

### 발견 ⑤ Flutter 하나로 "웹까지" 커버하면 커뮤니티의 검색 유입이 죽음
- Flutter Web은 CanvasKit 렌더링으로 SEO 크롤링이 어렵고 초기 로딩(엔진 다운로드)이 김 — 검색 유입이 중요한 서비스에는 부적합하다는 것이 일관된 평가.
  https://asoasis.tech/articles/2026-03-14-2053-flutter-web-seo-limitations-and-workarounds/ · https://www.miquido.com/flutter-101/seo-in-flutter/
- 커뮤니티 게시글은 검색 유입이 성장 엔진 → **웹은 React(Next.js SSR), 앱은 Flutter/RN**으로 분리하는 것이 맞음. 공고 스택에 React.js가 이미 있어 자연스럽게 정합.
- 참고: 스포츠 경기 자체는 저작물성이 없어 스코어·기록 데이터 제공은 가능하나, **중계 영상은 별개의 저작물** — 커뮤니티에 불법 중계 링크 공유를 금지하는 운영 정책·필터 필요.
  https://www.kci.go.kr/kciportal/ci/sereArticleSearch/ciSereArtiView.kci?sereArticleSearchBean.artiId=ART001997079

## 5. 제안 스택 & 아키텍처

- **웹**: React (Next.js SSR — 커뮤니티 검색 유입 필수, 발견 ⑤)
- **앱**: Flutter (iOS/Android 동시) — 웹뷰 아님, 네이티브 렌더
- **백엔드**: Node.js + MySQL + Redis
- **실시간**: 서버 폴링 스케줄러(15초 일괄) → Redis pub/sub → WebSocket(Socket.io) 팬아웃 — 웹·앱 동일 채널 구독으로 "웹-앱 실시간 동기화" 충족
- **세션**: OAuth 2.0(카카오·구글·애플) + JWT — 웹·앱 세션 공유
- **API**: 1차 API-Football($19~39/월) — Sportradar는 예산 확정 후 재검토 (발견 ①)
