# FANPIT — 시나리오 · 사용자 여정

## 1. 등장인물

| 인물 | 원하는 것 | 불안한 것 |
|---|---|---|
| **직장인 팬 A (28)** — 퇴근 후 PC로 경기 시청 | 여러 경기 스코어를 한 화면에서, 응원방에서 같이 떠들기 | 스포일러 없이 내 경기만 빠르게, 도박 스팸에 시달리기 싫음 |
| **모바일 팬 B (34)** — 출퇴근길 앱 사용 | 관심 경기 알림, 웹에서 하던 활동이 앱에 이어지기 | 로그인 또 하기 귀찮음(세션 동기화), 데이터 지연 |
| **커뮤니티 헤비유저 C (41)** — 분석글 작성자 | 글이 검색에 노출되고 추천으로 보상받기 | 내 글 옆에 토토 광고가 붙어 커뮤니티 질이 떨어지는 것 |
| **운영자 D (의뢰자 측 1인)** — 비개발자 | 신고를 놓치지 않기, API 비용이 예측 가능하기 | 새벽 경기 중 스팸 폭주, API 장애 시 대응 방법을 모름 |

※ 운영 인력이 **1인**(공고: 내부 인력 1인 배정)이라는 점이 설계 전체를 지배 — 자동화(금칙어 필터·SLA 타이머·장애 시 캐시 서빙)가 없으면 운영이 성립하지 않음.

## 2. 시간순 여정

### A. 발견 → 시청 (팬 A, 수요일 19:30)
1. PC로 접속 → **스코어보드**: 종목 탭에 LIVE 수가 배지로 표시, 리그별 그룹.
   *이 기능이 없으면*: 경기를 찾으러 종목별 페이지를 순회 — 이탈.
2. 서울 노바 경기 클릭 → **경기 상세**: 스코어 히어로 + 응원 비율 바.
3. 득점 순간 스코어가 **bump 애니메이션**과 토스트로 갱신 (15초 폴링 데이터).
   *이 기능이 없으면*: 새로고침 연타 → 서버 부하 + 체감 품질 하락.

### B. 응원 → 소통 (팬 A, 경기 중)
4. **응원방** 입장 → 팀 응원 투표 → 실시간 채팅 참여, 답장(@닉네임).
5. 도박 스팸이 올라오지만 **자동 블라인드**로 회색 처리되어 흐름이 유지됨.
   *이 기능이 없으면*: 새벽 경기 응원방이 광고판이 됨 — 커뮤니티 신뢰 붕괴 (KISA: 스팸의 43%가 도박).
6. 욕설 이용자를 **신고 + 차단** → 그 이용자의 메시지가 즉시 사라짐.
   *이 기능이 없으면*: iOS 심사 리젝(가이드라인 1.2 — 차단 필수).

### C. 이동 → 연속성 (팬 B)
7. 지하철에서 앱 실행 → 웹과 **같은 세션**(JWT 공유) → 관심 경기·차단 목록 그대로.
   *이 기능이 없으면*: "웹 따로 앱 따로" — 공고가 지적한 기존 앱들의 한계 재생산.

### D. 사후 → 재방문 (팬 C, 경기 후)
8. **자유게시판**에 분석글 작성 → 추천 누적 → HOT 배지.
9. 다음 날 검색으로 글 유입 (Next.js SSR — Flutter Web이면 이 유입이 죽음).
10. **마이페이지**에서 내 글/댓글·관심 경기 확인.

### E. 운영 (운영자 D, 상시)
11. **대시보드**: DAU·동접·신고 KPI. 경기별 동접으로 서버 스케일 판단.
12. **신고 큐**: 24h SLA 타이머 — 잔여 시간이 붉게 바뀌기 전에 처리.
    *이 기능이 없으면*: 신고 방치 → Apple이 앱 제거 가능(1.2 위반).
13. **스팸 필터**: 새 패턴("총판" 등) 발견 즉시 금칙어 추가 → 전 화면 즉시 반영.
14. **API 모니터링**: 쿼터 게이지로 요금제 초과 예방, 장애 시 캐시 서빙 배너 확인.
    *이 기능이 없으면*: API 장애 = 서비스 전면 백지 / 쿼터 초과 = 월말 과금 폭탄.

## 3. 역할별 시야 차이 (권한 설계)

| 데이터 | 팬 | 운영자 |
|---|---|---|
| 블라인드 게시글 | 제목·본문 비공개, 사유만 표시 | 원문·사유·자동/수동 구분, 복구 가능 |
| 신고 내역 | 내가 한 신고 접수 여부만 | 전체 큐 + SLA 경과 + 제재 이력 |
| 이용자 정보 | 닉네임만 | 가입일·게시글 수·누적 신고·상태 |
| API 상태 | (장애 시) "N초 전 데이터" 배지만 | 폴링 파이프라인·쿼터·히트율 전체 |

## 4. 기능별 존재 이유 전수 매핑

| 기능 | 존재 이유 (여정 단계) |
|---|---|
| 종목 탭 LIVE 배지 | A-1 발견 비용 최소화 |
| 스코어 bump·토스트 | A-3 "실시간"의 체감 증거 |
| 응원 투표·비율 바 | B-4 소속감 — 커뮤니티 활성의 시작점 |
| 금칙어 자동 블라인드 | B-5 운영 1인 체제에서 유일한 현실적 방어 |
| 신고+차단 | B-6 App Store 1.2 필수 4요소 |
| 관심 경기 즐겨찾기 | C-7 재방문 트리거 (알림의 근거 데이터) |

| SLA 타이머 | E-12 "24시간 내 조치" 증빙 가능 |
| 쿼터 게이지 | E-14 API 비용 예측 가능성 |
| 장애 시뮬레이션 | E-14 장애 ≠ 백지 화면 (스테일 서빙) |

## 5. 비는 구멍 — 미팅에서 확인 필요

1. **종목 우선순위**: API-Football은 축구 중심. 야구(KBO)·농구 라이브 데이터는 별도 소스 필요 — 1차 오픈 종목 범위를 정해야 API 계약이 정해짐.
2. **응원방 익명성 수준**: 실명제/닉네임제/비로그인 열람 — 도박 스팸 방어 강도와 직결.
3. **알림 정책**: 관심 경기 득점 푸시 여부 (FCM/APNs — 앱 심사·서버 비용에 영향).
4. **성인 인증**: 스포츠 커뮤니티에 배당·승부 예측 콘텐츠를 허용할 것인가 — 허용 시 사행성 심의 리스크, 본 설계는 전면 금지 전제.
5. **중계 영상 정책**: 스코어 데이터는 적법하나 중계 영상 링크·클립 공유는 저작권 침해 — 링크 필터 범위 확정 필요.
6. **웹뷰 vs 네이티브**: 8주 일정 압박 시 앱을 웹뷰 하이브리드로 낮추는 선택지 — 심사 기준(4.2 최소 기능성)과 트레이드오프 설명 필요.
7. **운영 이관**: 오픈 후 금칙어·신고 처리를 누가 하는가 — 내부 1인 교육 + 운영 매뉴얼 범위.
