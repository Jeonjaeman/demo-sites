PRE-BUILD REVIEW

요구사항대로 만들면
어디서 문제가 생기는가

공고를 그대로 구현하기 전에 확인해야 할 지점 4곳을 리서치로 찾았고, 각각의 대안을 이 데모 안에 실제 동작하는 기능으로 구현했습니다.

RISK 01

Sportradar와 API-Football은 가격이 500배 차이납니다

공고에 병기된 두 API 중 Sportradar는 견적제로 월 수천 달러~1만 달러 이상, API-Football은 월 $19~39입니다. 어떤 API를 계약하느냐가 총예산(2,500만 원)보다 큰 연간 비용 변수가 될 수 있습니다.

→ 이 데모의 대응: 아래 API 비용 시뮬레이터로 동시접속 규모별 요금제를 실계산
RISK 02

이용자가 API를 직접 부르는 구조면 과금이 동접에 비례해 폭발합니다

라이브 데이터는 15초 간격 갱신입니다. 클라이언트 폴링 구조면 동접 1만 명 기준 하루 수백만 요청이 발생합니다. 서버가 한 번만 폴링하고 Redis에 얹어 WebSocket으로 뿌리면 동접과 무관하게 하루 약 5,800회로 고정됩니다.

→ 이 데모의 대응: 관리자 API 모니터링 화면에 폴링 파이프라인·캐시 히트율 구현
RISK 03

커뮤니티 기능만 넣으면 iOS 심사(가이드라인 1.2)에서 리젝됩니다

UGC 앱은 ① 부적절 콘텐츠 필터 ② 신고 기능 ③ 이용자 차단 ④ 신고 24시간 내 처리를 모두 갖춰야 App Store 심사를 통과합니다. 공고에는 신고·블라인드만 있고 차단이 빠져 있습니다.

→ 이 데모의 대응: 응원방 신고·차단 버튼, 마이페이지 차단 목록, 관리자 24h SLA 처리 큐
RISK 04

스포츠 커뮤니티는 불법 도박 스팸의 1순위 표적입니다

KISA 집계 기준 전체 스팸 문자의 43%가 도박 관련입니다. 스포츠 응원방·게시판은 개장 직후부터 사설 토토 홍보가 유입되며, 계정 차단만으로는 재가입을 막을 수 없어 자동 필터가 필수입니다.

→ 이 데모의 대응: 응원방에 금칙어 자동 블라인드가 실시간 동작 (관리자에서 사전 편집 가능)
