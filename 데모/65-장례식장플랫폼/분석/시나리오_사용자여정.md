# 장례식장 플랫폼 — 시나리오·사용자 여정

> 기능 목록을 시간순 사용 흐름으로 재구성한 문서. 1순위 가정: **본부-지점(직영/가맹) 체인**.
> 분석일 2026-08-15. 데이터는 전부 가상.

---

## 1. 등장인물

| 역할 | 누가 | 무엇을 원하나 | 무엇을 불안해하나 |
|---|---|---|---|
| **유족/상주 (핵심)** | 임종 직후 몇 시간 내 결정해야 하는 가족 | "지금 빈소가 비어 있는 지점"을 빨리 찾고, 총비용을 미리 알고, 바가지 안 쓰기 | 슬픔·시간압박 속 큰돈을 즉흥 결제 / 도착했더니 빈소 없음 / 견적과 실제 청구액 차이 |
| **지점장·지점 직원 (파트너)** | 자사 브랜드 지점의 실무자·장례지도사 | 빈 빈소를 채우고 용품을 팔고, 전화 응대·수기 관리를 줄임 | 온라인 예약이 실제 안치와 어긋남(더블부킹) / 정산 지연 / 노쇼 / 본부가 단가를 강제 |
| **본부 운영자 (마스터)** | 프랜차이즈/체인 본부 | 전 지점 거래액·실시간 현황·표준단가·정산 통합 관리, 분쟁 최소화 | 잘못된 실시간 현황이 곧 클레임 / 결제·환불 분쟁 / 선불식·가맹 법적 리스크 / 지점 간 가격 편차 |
| **부고 수신자 (조문객)** | 카톡으로 부고 링크 받은 지인 | 발인·장지·계좌·오시는 길 확인, 조의금 송금 | 링크 유출로 모르는 사람이 유족 정보·조의계좌를 봄 |

**한 사람이 여러 역할 겸함**: 상주 = 결제자 = 부고 발송자(세 역할이 한 사람에 몰림 → 공개 UX는 극단적으로 단순해야). **지점 직원 ≠ 본부** — 같은 데이터를 지점은 "내 지점만", 본부는 "전 지점 통합"으로 본다(권한 설계 핵심).

## 2. 시간순 여정 — 상황 / 쓰는 화면 / 없으면 벌어지는 일

| # | 단계(시점) | 상황 | 쓰는 화면 | 이 기능이 없으면 |
|---|---|---|---|---|
| 1 | **임종·사망 (0~2h)** | 병원 영안실 또는 자택. 극도의 시간압박·감정상태 | 홈 → 위치기반 지점 검색 + **"지금 임종하셨나요?" 응급 플로우** | 유족은 병원 연계 상조/장례지도사에게 그냥 배정 → **플랫폼을 거칠 이유 소멸(핵심 위험)** |
| 2 | **탐색 (2~4h)** | 어느 지점이 비었나·거리·비용대 비교 | 검색 결과(빈소 신선도 배지·지점유형 배지) + 상세 | 어디가 비었는지 몰라 전화 돌림 → 온라인 존재 이유 상실 |
| 3 | **예약·결제 (즉시)** | 빈소 선택 → 예약금/전액 결제 | 예약 폼(hold 15분) + PG 결제(**선불식 비해당 배지**) | 지점 승인 전 다른 데서 안치 → **더블부킹** |
| 4 | **용품 견적·선택** | 관·수의·제단장식 선택·합산 | **견적산출기**(선택 지점 확정단가로 실시간 합산) | 총액 모른 채 현장 추가금 폭탄 |
| 5 | **부고장 발송** | 템플릿 작성 → 카톡 링크 공유 | **부고장 생성기**(비공개 토글·유효기간) | 문자 개별 발송, 조문객 정보 파편화, 개인정보 무제한 노출 |
| 6 | **장례 진행 (3일)** | 조문·조의·상담 | 마이페이지(예약/결제/상담 내역) | 진행 상태·상담 이력 분실 |
| 7 | **사후 (발인 후)** | 정산·환불·영수증 | 결제내역·환불 | 예약금 정산 분쟁 |

## 3. 역할별 시야 차이 — 권한 설계의 핵심

같은 데이터가 역할에 따라 다르게 보인다:

| 데이터 | 유족 | 지점장/직원 | 본부(마스터) |
|---|---|---|---|
| 예약 1건 | 내 예약 상태 | 우리 지점의 승인·취소 요청 + 안치 캘린더 | 전 지점 거래액·수수료 집계 원장 |
| 빈소 현황 | 신선도 배지로 표시된 가용 여부 | **우리 지점만** 원터치 토글로 갱신 | **전 지점** 실시간 지도로 관제 |
| 용품 단가 | 견적 결과(확정가) | 우리 지점 밴드 내 조정(승인제) | 표준(권장)가 설정 + 편차 히트맵 |
| 결제 | 내 카드 내역 | 정산받을 금액(**결제 원본 PAN·승인정보 접근 불가**) | 전 결제·환불 원장 + 자금흐름 설정 |

**격리 원칙**: 지점은 결제 원본(카드번호·승인정보)에 접근 못 하게 격리한다. 이 격리를 마스터 「지점 관리」 화면에 명시적으로 노출해 "권한 설계를 실제로 했다"를 보인다.

## 4. 기능별 존재 이유 (전수 매핑)

- **응급 플로우** — 임종 순간 즉시배정 관행을 이기려면 "지금" 진입점이 필요(발견 ④).
- **지점 검색 + 신선도 배지** — 실시간의 신뢰 근거를 화면에 노출(발견 ②).
- **견적산출기** — 가격 투명성=신뢰라는 업계 문법(고이 정찰제) + 지점 확정단가 반영(발견 ⑦).
- **예약 hold 15분 + PG 예치 + 선불식 배지** — 더블부킹 방어 + 상조업 경계 방어(발견 ①③).
- **부고장(링크공유·비공개·유효기간)** — 알림톡 오해 방지 + 개인정보 노출 차단(발견 ⑤).
- **지점 원터치 빈소 토글 → 본부 지도 즉시 반영** — 실시간 병목(입력 UX) 해소(발견 ②).
- **본부 표준단가 + 지점 밴드 오버라이드** — 브랜드 가격 정합성 + 가맹 가격강제 위법 회피(발견 ⑥⑦).
- **자금흐름 다이어그램 토글** — PG 자금흐름 미정 리스크를 화면으로(발견 ③).
- **선불식 판정기 / 가맹·직영 규제 위젯** — 사업모델·법적 분기를 발주자가 직접 만져보게(발견 ①⑥).

## 5. 비는 구멍 (정의 없음 — 착수 미팅 확인 필요)

1. **사업모델 확정** — 본부-지점(직영/가맹) vs 오픈마켓? 가맹이면 정보공개서·가맹금·가격강제 축 발생.
2. **선수금 수금 주체** — 본부 중앙 수금인가? → 선불식 할부거래 강도(자본금 15억·선수금 50% 예치) 결정.
3. **자금흐름** — 플랫폼(본부) 수령형 vs 지점 직수령 대행형? → PG 등록·에스크로·정산·환불책임 주체.
4. **예약 취소·환불 정책** — 장례는 취소보다 "빈소 못 구함/이동" 케이스. 예약금 환불 기준·시점·수수료 미정.
5. **동시 예약 충돌** — 같은 빈소 동시 결제 시? 낙관적 락 / 선결제 우선 / 승인제 중 미정(데모는 hold 15분 + 승인제로 시연).
6. **지점 기존 현황판/POS** — 연동인가 대체인가? 이중입력 방지 방식.
7. **부고장 개인정보 범위** — 조의계좌·유족연락처 기본 공개/비공개? 링크 유효기간 기본값.
8. **정산 시점·PG 수수료 부담** — 지점 정산 주기, 수수료 부담 주체.
9. **"예약" 수요의 실재성** — 즉시배정 관행 하에서 예약 대기가 성립하는 비중(발견 ④).

> 이 9개는 데모에 "가정"으로 구현하되, 지원서·미팅에서 "이건 확정해야 할 지점"으로 명시한다.
