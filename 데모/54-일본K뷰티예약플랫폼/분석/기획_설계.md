**숨은 니즈**

- "병원, 에스테틱, …" 을 **한 예약 흐름**으로 묶으면 법적 구조가 깨집니다(2장 ①). 공고에는 없지만 이 분리가 설계의 뼈대가 되어야 합니다.
- "프리미엄 컨시어지"는 화면 톤이 아니라 **운영 방식**입니다 — 여행 일정 전체를 설계해 주는 서비스라는 것. 데모의 여정 플래너(다운타임 경고)가 그 답입니다.
- 8개 질의를 던진 것 = 발주 경험이 축적 중인 의뢰자. 회신은 항목별로 정확히, 근거와 함께.

## 7. 예약·결제 구축 방식 (질의 5)

1. 예약: 프로그램×날짜×슬롯 재고 모델(정원 관리) — 동시 예약 경합은 DB 트랜잭션으로 처리. 예약번호 규칙 `MYB-YYMMDD-NNN`.
2. 결제: 해외카드 PG(엑심베이 등) 결제창 연동 — JCB/VISA/MC/AMEX, KRW 승인 + JPY 참고 표기. 웹훅으로 결제 확정 → 예약 상태 전환.
3. 환불: 취소 수수료 단계(7일전 0/3~6일 30%/전일 50%/당일 100%)를 서버에서 계산해 부분 환불 API 호출. 규정은 特商法 표기·예약 화면 양쪽에 고지.
4. 의료 프로그램: 결제 없음 — 상담 신청만 접수하고 유치업 등록 구조와 연동(플랫폼은 시술 수납 안 함).

## 8. 일본 SEO 전략 (질의 12)

- 야후재팬=구글 엔진(2027.3까지 계약)이므로 **구글 일본어 최적화 단일 트랙**: SSR(Next.js)·ja-JP hreflang·구조화 데이터(Organization·Product·BreadcrumbList·Review — 단 의료 리뷰 마크업 제외)·Core Web Vitals.
- 일본어 검색어 설계: "韓国 パーソナルカラー診断 予約", "ソウル エステ 日本語" 류 롱테일 — 프로그램 상세를 검색 랜딩으로.
- 特商法 표기·운영자 정보 공개는 E-E-A-T 신뢰 신호로도 작동.

## 9. 앱 확장 구조 (질의 7)

- 웹을 Next.js(프론트) + API 서버(Supabase/PostgreSQL + Edge Functions) 로 분리 구축 → 앱(React Native/Flutter)은 **같은 API를 그대로 사용**. 예약·결제·회원 로직 재개발 없음.
- 결제는 앱에서도 PG 웹뷰 방식으로 동일 적용 가능. 푸시 알림(예약 리마인드)만 앱 단계에서 추가.
