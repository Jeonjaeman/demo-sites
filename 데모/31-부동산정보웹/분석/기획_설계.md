## 2장. 리서치 — 그대로 만들면 막히는 지점

우선순위: `그대로 만들면 작동하지 않음` > `운영 중 반드시 터짐` > `있으면 좋음`

### ★ 발견 1 — "프론트엔드 프로젝트"인데 프론트에서 못 하는 항목이 둘 있습니다

공고 **2-3(공공데이터 API 연동)** 과 **3-2(안전한 토큰 관리)** 는 브라우저 단독으로 성립하지 않습니다.

브라우저에서 직접 호출해 확인한 결과입니다(2026-07-29).

| 케이스 | 결과 | 상세 |
|---|---|---|
| 단순 GET (Origin 포함) | **통과** | `Access-Control-Allow-Origin: *` 응답. 브라우저에서 읽힙니다 |
| CORS 프리플라이트(OPTIONS) | **실패** | 204 응답에 ACAO 헤더 없음 |
| 커스텀 헤더 붙인 GET | **실패** | 프리플라이트가 막혀 `TypeError: Failed to fetch` |
| 서비스키 노출 | **노출** | `serviceKey` 가 URL 쿼리에 그대로. 도메인 제한 기능 없음 |

**여기서 흔히 잘못 진단합니다.** "공공데이터 API는 CORS가 막힌다"는 이야기가 많지만
실제로는 **단순 GET이면 통과합니다.** 진짜 문제는 CORS가 아니라 **키**입니다.

- `serviceKey`는 URL 쿼리스트링에 들어갑니다. 프론트에서 호출하면 **개발자도구 네트워크 탭에 그대로 남습니다.**
- 공공데이터포털 키에는 **카카오 JavaScript 키 같은 도메인 제한이 없습니다.** 복사해 가면 누구나 씁니다.
- 유출되면 **일일 한도(기본 1,000회)가 남에게 소진**됩니다.
- 요청 추적·인증 헤더를 붙이려는 순간 프리플라이트에서 막힙니다.

> 근거: [ServiceKey는 프론트엔드 코드에 직접 삽입하지 말고 서버 환경변수로 — 공공 API 키 발급 가이드](https://skills.itda.work/blog/2026/04/28/korea-public-api-keys-guide/) ·
> [공공데이터 API CORS 이슈와 프록시 서버](https://velog.io/@yoonyounghoon/공공데이터-API-CORS-이슈-해결을-위해-직접-프록시-서버-구축하기)

**결론: 브라우저에서 "안전한 토큰 관리"는 원리적으로 불가능합니다.** 브라우저에 내려간 값은 전부 열람됩니다.
서버 프록시가 유일한 답이고, **그 엔드포인트가 백엔드에 이미 있는지가 착수 전 1순위 확인 항목**입니다.
없다면 프론트 단독으로 2-3을 완료할 수 없습니다.

- **대응** — 관리자 [프론트 경계선] 화면에서 요구사항 7건을 `프론트 / 프론트+백엔드 / 백엔드 필요`로 분류하고,
  **버튼을 누르면 이 페이지에서 실제로 공공 API를 호출**해 키가 어디에 남는지 그대로 보여줍니다.

### ★ 발견 2 — 실거래가 API 응답에는 좌표가 없습니다

국토부 실거래가 API는 **법정동코드 5자리 + 계약년월**로 조회하고, 응답에는
법정동명·지번·단지명·전용면적·거래금액만 옵니다. **GPS 좌표가 없습니다.**

> 근거: [국토교통부_아파트 매매 실거래가 자료 — 공공데이터포털](https://www.data.go.kr/data/15126469/openapi.do)
> (조회 단위: 법정동코드 앞 5자리 + 계약년월 · 일일 호출 기본 1,000회)

그대로는 지도에 핀을 찍을 수 없습니다. 지오코딩이 필요하고, 카카오 로컬 API 쿼터(일 10만)를 소모합니다.

공고 **2-2는 "백엔드 API 데이터로 마커 표시"**, **2-3은 "공공 API 프론트 바인딩"** 인데
**두 데이터가 어디서 합쳐지는지 정의가 없습니다.** 백엔드가 좌표까지 주는지, 프론트가 지오코딩하는지가 미정입니다.

- **대응** — 데모 데이터도 원본 레코드에 좌표를 넣지 않고 **별도 지오코딩 테이블에서 매칭**합니다.
  관리자 [지오코딩 파이프라인]에서 `캐시 히트 / 신규 지오코딩 / 매칭 실패`를 실제 데이터로 계산합니다
  (이 데모 2,467건 기준 **71.5% / 24.6% / 3.9%**). **매칭 실패분은 지도에서 실제로 빠지고**
  목록에 "좌표 매칭 실패 — 지도에 표시되지 않습니다" 경고가 붙습니다.
  제안 구조는 **서버에서 1회 지오코딩 후 좌표 캐시**입니다.

### ★ 발견 3 — 마커가 1,000개를 넘으면 지도가 버벅입니다

공고 3-1이 "지도 렌더링 지연 최소화"를 요구합니다. 카카오맵 데브톡에
**마커 1,000개 이상에서 렌더링 지연**, **2만 개 클러스터링에 10초 이상** 보고가 있습니다.

> 근거: [마커 렌더링 속도, 최대 마커 개수 — 카카오 데브톡](https://devtalk.kakao.com/t/topic/132162) ·
> [카카오맵 API 클러스터링 속도 문의](https://devtalk.kakao.com/t/api/120599)
> 쿼터: 로컬 API 일 10만 · 지도 API 일 30만 · 통합 월 300만

서울 전역 매물은 쉽게 수천 건입니다. 이 데모도 2,467건입니다.

- **대응** — 지도를 canvas로 직접 그려 **프레임 시간을 실제로 측정**합니다(지어낸 수치 없음).
  좌하단 [렌더 성능] 패널에서 클러스터링을 끄고 켜면 값이 바뀝니다.

  | 방식 | 그린 요소 | 프레임(중앙값) |
  |---|---|---|
  | 개별 마커 | 2,371 | **33.4ms** (30fps 미만 — 버벅임) |
  | 클러스터링 | 71 | **1.0ms** |

  **33.4배** 차이입니다. 뷰포트 밖은 아예 그리지 않는 컬링도 함께 넣었습니다.

### 발견 4 — PG 결제는 프론트 콜백만 믿으면 금액이 바뀝니다

공고 2-4는 "결제 모듈 프론트엔드 연동 및 성공/실패/취소 라우팅"만 프론트 과업으로 적었습니다.
그런데 결제 성공 콜백의 금액을 그대로 신뢰하면 클라이언트에서 값을 바꿔 **0원 결제**를 만들 수 있습니다.

> 근거: 클라이언트 콜백만으로 주문을 처리하지 말고 **서버에서 PG API로 결제 상태를 검증**해야 하며,
> 위변조 방지 키를 프론트엔드 코드에 노출하면 결제 금액을 0원으로 조작할 수 있습니다
> ([PG 연동 결제 검증](https://velog.io/@jonghyun3668/결제-과정-이해하기PG사-연동) ·
> [이커머스 PG 연동 실수 5가지](https://divii.com/pg사-연동-이커머스-결제-시스템/))

- **대응** — 관리자 [결제 검증]에서 콜백 금액을 직접 바꿔 볼 수 있습니다.
  서버 검증이 없으면 차액이 그대로 손실로 표시되고, 있으면 PG 원장 재조회로 차단됩니다.
  **백엔드에 결제 검증 엔드포인트가 있는지**가 착수 전 확인 항목입니다.

### 발견 6 — 일부 공공 API는 국내 IP에서만 열립니다

> 근거: 일부 API는 보안상 국내 IP에서만 호출이 가능해 AWS 같은 해외 클라우드 환경에서 차단될 수 있습니다
> ([공공 API 키 발급 가이드](https://skills.itda.work/blog/2026/04/28/korea-public-api-keys-guide/))

Next.js를 Vercel 기본 리전에 올리면 서버사이드 공공 API 호출이 막힐 수 있습니다.
프록시를 서버에 두기로 해도 **그 서버가 어디에 있는지**가 문제가 됩니다.

- **대응** — 배포 리전을 국내로 고정하거나, 공공 API 호출만 국내 서버를 거치도록 분리합니다. 착수 전 확인 항목.

### 잘 되어 있는 부분도 짚습니다

- **화면정의서·와이어프레임·프로토타입이 모두 있습니다.** 기획 재작업이 없어 착수가 빠릅니다.
- **백엔드 API가 완료돼 있습니다.** 프론트가 기다릴 일이 줄어듭니다.
- **3-2에 "안전한 토큰 관리"를 적어 둔 것** — 보안 지점을 정확히 인지하고 계십니다. 다만 담당이 프론트가 아닐 뿐입니다.
- **우선순위 1순위를 업무 능력으로 둔 것** — 이 과업은 금액보다 인수 능력이 결과를 좌우합니다.

## 5장. 제안 스택

| 레이어 | 제안 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js (App Router)** | 공공 API 프록시를 Route Handler로 같은 저장소에서 해결할 수 있습니다. 발견 1의 답이 프레임워크 안에 있습니다 |
| 상태 | **Zustand** (공고 명시) | 지도 뷰포트·필터·선택 매물처럼 화면을 가로지르는 상태에 적합 |
| 지도 | **카카오 지도 JS SDK** + 클러스터러 | JavaScript 키는 도메인 등록으로 보호되므로 프론트에 두는 것이 정상 |
| 서버 통신 | **TanStack Query** | 뷰포트 이동마다 재조회가 발생합니다. 캐시·중복요청 제거가 곧 3-1의 "API 호출 최적화" |
| 배포 | **국내 리전 고정** | 발견 6 — 해외 리전에서 공공 API가 막힐 수 있습니다 |

**경계 합의가 먼저입니다.** 아래 세 엔드포인트가 백엔드에 있는지 확인하고 시작합니다.

1. 공공데이터 **프록시** (`GET /api/public/*`) — 없으면 Next.js Route Handler로 만들되 **추가 공수**
2. 결제 **검증** (`POST /api/payments/verify`) — 없으면 금액 위조가 열립니다
3. 매물 좌표 포함 여부 (`GET /api/properties` 응답에 lat/lng)

**36공수는 계약 30일을 넘습니다.** 그리고 **기존 코드를 보기 전에는 이 숫자가 확정되지 않습니다** —
인수 대상 코드의 상태가 공수를 크게 좌우합니다(공고 우대사항도 그 점을 짚고 있습니다).

그래서 이렇게 제안합니다.

## 8장. 착수 전 확인이 필요한 항목

1. **공공 API 프록시 엔드포인트가 백엔드에 있는가** — 없으면 2-3·3-2를 프론트 단독으로 못 합니다
2. **결제 검증 엔드포인트가 있는가** — 없으면 금액 위조가 열립니다
3. **매물 API 응답에 좌표(lat/lng)가 포함되는가** — 없으면 지오코딩 주체와 캐시 위치를 정해야 합니다
4. **기존 데모 코드의 상태** — 프레임워크 버전, 컴포넌트 재사용 가능 범위 (0차에서 확인)
5. **배포 리전** — 해외 리전이면 공공 API 호출이 막힐 수 있습니다
6. **결제 대상이 무엇인가** — 공고에 결제 품목이 없습니다. 유료 열람인지 구독인지에 따라 화면이 달라집니다
7. **9/2~9/15 13일의 범위 귀속** — 계약 포함 여부
8. **게시판의 범위** — 목록/상세/작성/댓글/신고 중 어디까지인지
