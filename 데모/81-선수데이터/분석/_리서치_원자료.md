> **한 줄 결론**: 이 공고의 실패 지점은 "CSV를 못 올린다"가 아니다.

> ② CSV를 정확한 선수·세션에 붙여도 **측정 조건(센서 위치·펌웨어·Hz·의수 착용·제품 버전)이 다른 세션끼리 비교하면 제품 개선 효과는 허상**이 된다. (경쟁 지원자 neorect가 짚은 "연결 규칙·컬럼 매핑 버전"보다 한 단계 아래)
> ③ "익명 ID"는 법적으로 **가명정보**이고, 장애·신체 정보는 **민감정보**라 별도 동의·접속기록 2년이 따라온다.
> ④ 창업지원 외주는 **협약 종료일 안에 증빙사진 포함 검수조서 + 결과보고**가 나와야 인정되므로, 11/30은 개발 마감이 아니라 **검수 마감**이다.

## 4. 명시된 니즈 vs 숨은 니즈

| 단서 (공고 문구) | 숨은 니즈 | 설계 응답 |
|---|---|---|
| "필요한 내용을 간단히 정리한 상태" + "IT 프로젝트 관리 경험 없음" | 요구사항 정의·결정 목록을 우리가 대신 만들어 줘야 함 | 5장 "비는 구멍"을 미팅 질문지로 · 결정 대기 항목을 문서로 |
| "센서 앱 별도 업체 개발 중" + "실제 데이터 미확보" | CSV 규격이 우리 납품 **이후** 확정 → 규격을 우리가 먼저 제안해야 함 | CSV 규격서 v0.1 + 샘플 + **규격 검증기** (F04) |

### F01. 센서 1개(브라 속)로 나오는 "좌우"는 팔의 좌우가 아니라 **몸통의 좌↔우 기울기·회전**이다 — 그중 회전(yaw)은 실내에서 믿기 어렵다 · (a)

- **등급**: P1 (정의 공백 — 그대로 만들면 "좌우 비교"가 무엇을 비교하는지 아무도 모름)
- **내용**
  - 상지 절단·의수 사용자의 보상 움직임은 **주로 몸통·어깨**에 나타난다 — 과제 수행 중 몸통 3평면 움직임과 어깨 외전이 증가 [확인]. → 몸통 센서로 보는 것 자체는 타당하다.
  - 그러나 **상부 몸통 IMU 1개는 좌·우 사지의 차이를 구분하지 못한다**: 배드민턴 선수 연구에서 상부 몸통 IMU는 무부상·편측 부상·양측 부상군을 구분하지 못했고 경골 IMU는 가능했다 [확인 ✓ Wylde 2022 p.190 "the upper trunk-mounted IMU was unable to distinguish between the non-injured, unilaterally injured and bilaterally injured groups"].
  - 1개로 가능한 것은 **몸통 자세의 부호 분포** — 왼쪽/오른쪽으로 기운 시간·최대각(roll), 왼쪽/오른쪽으로 돈 시간·최대각(yaw). 상부 몸통 IMU의 몸통 각도 정확도는 광학 모션캡처 대비 RMSE **측굴 3.0° · 축회전 4.6° · 굴곡 3.0°** [확인 ✓ Brouwer 2021].
  - **회전(yaw)은 자기센서 의존** → 실내 철골·금속·배선에 의해 왜곡된다 [확인]. Brouwer도 "주변 금속에 의해 지구 자기장이 왜곡될 수 있다"를 한계로 명시 [확인 ✓]. 기울기(roll/pitch)는 중력 기준이라 저가속 구간에서 상대적으로 안정 [추정].
  - 1개로 가능한 두 번째 방법: 달리기 같은 **주기 운동의 좌·우 스텝 시간 비교** — 몸통 가속도 자기상관(step regularity)으로 좌우 대칭을 추정하는 방법이 검증돼 있고 [확인], Apple 보행 비대칭도 좌·우 스텝 시간 비(max/min)로 정의 [확인 ✓]. 편측 전완 절단 엘리트 선수 트레드밀 달리기에서 **우측 다리 입각기가 유의하게 길고, 절단측 팔 스윙 속도가 빨랐다** [확인 ✓ Mally 2015] → 상지 절단이 하지 리듬의 좌우 차로도 나타난다.
  - **결론**: "좌우 움직임 비교"를 ① 몸통 기울기 좌/우 분포 ② 몸통 회전 좌/우 분포(신뢰도 표시) ③ 좌/우 스텝 시간 비(달리기 계열) 3개로 정의하면 센서 1개로도 성립한다. **"왼팔 vs 오른팔"을 원하면 센서가 양팔(또는 양 견갑)에 최소 2개** 필요 — 센서 업체 하드웨어 범위 → [미확인].
  - **전제**: CSV에 자세값(쿼터니언/오일러)이 들어와야 한다. 원시 가속도·자이로뿐이면 자세 계산(센서 퓨전)이 필요한데, 이는 공고가 제외한 "센서 자체의 분석 알고리즘" 영역이다.
  - 지표 공식 주의: 고전적 대칭지수 (L−R)/(½(L+R))는 **값이 0 근처일 때 폭주**한다 [확인]. 몸통 평균 기울기는 0° 근처가 정상이라 이 공식을 쓰면 안 된다 → max/min 비(Apple 방식) 또는 정규화 지수(NSI) 사용.

### F02. 센서를 뒤집어 달면 좌우 결론이 **통째로 반대**가 된다 — 부호 검증이 없으면 아무도 모른다

- **등급**: P1
- **내용**
  - 오일러각은 pitch ±90°에서 짐벌락, ±180° 경계에서 값이 튄다 [확인]. 실제 IMU 출력에서 roll이 −90° 아래 구간을 뒤집거나 yaw가 경계에서 점프하는 사례 [확인].
  - 쿼터니언 성분 순서 규약이 둘이다 — scalar-first (w,x,y,z) / scalar-last (x,y,z,w), SciPy 기본은 scalar-last [확인]. 순서를 잘못 읽으면 전혀 다른 자세가 된다.
  - 센서축→신체축 정렬은 정적 자세(N-pose 등) 또는 기능적 동작으로 보정하는 것이 표준 [확인]. 앞/뒤·위/아래로 바꿔 달면 roll 부호가 뒤집힌다 [추정 — 장착 방향에 따른 좌표계 반전].
  - 상지 절단자는 **선 자세 자체가 비대칭**이다: 상완 절단 92%·전완 절단 67%에서 흉추 측만, 만곡은 **절단측으로 볼록** [확인 ✓ Friz 1965]. → "정지 자세 = 0°"로 보정하면 **그 선수의 기본 기울기가 지워진다.** 양팔을 쓰는 T-pose 보정은 불가능할 수 있다.

### F04. 컬럼 매핑 버전만으로는 **단위가 바뀐 걸 못 잡는다** — 물리 법칙으로 검사해야 한다 (= "업로드 파일 형식 자동 확인"의 실체)

### 7-1. 좌우 움직임 비교 그래프 — 포함 (범위 한정)
- **포함 이유**: 공고가 스스로 쓴 배경("절단 부위 반대쪽 팔의 보상움직임 … 한쪽으로 치우친 운동 동작")이 이 그래프를 위한 것이다. 그래프는 미뤄도 되지만 **절단 측·측정 조건·지표 테이블을 지금 안 만들면** 나중에 붙일 때 과거 세션을 다시 정리해야 한다.
- **경계**: 공고가 제외한 "선수별 움직임 불균형 분석"과 구분 — 이번엔 **부호별 분포·비율(기술 통계)**까지. 판정·점수·추천·임상 문구는 후속 (F10).
- **전제 확인**: ① 센서 개수·위치 (1개면 몸통 좌우, 팔 좌우는 2개 이상) ② CSV에 자세값(쿼터니언/오일러) 포함 여부 — 원시값뿐이면 자세 계산은 센서 업체 앱에서 해서 내보내 달라고 요청 (센서 퓨전 = 공고 제외 범위).
- **빼면 나중에 붙이는 법**: 세션 요약 지표 테이블(`session_metric(session_id, metric_key, side, value, processor_version)`)과 선수 절단 측 필드만 지금 만들어 두면, 그래프는 화면 하나 추가로 붙는다. 과거 세션은 원본 CSV를 재처리해 지표만 채우면 된다 (F16).

### 7-2. 기간별 추이 그래프 — 포함
- **포함 이유**: 세션마다 요약 지표를 저장하면 추이는 날짜축 집계 쿼리다. 정부 과제 결과보고에서 "제품 버전 개선 전후"를 보여 줄 수 있는 유일한 화면.
- **주의**: 측정 조건이 다른 세션은 **다른 시리즈/기호**로 분리 (F03). 제품 버전 변경 시점에 세로선.
- **빼면 나중에 붙이는 법**: 세션 요약 Excel 내보내기만으로도 엑셀 피벗 차트로 대체 가능 — 그래서 요약 지표 저장은 어느 쪽이든 필수.

### 7-3. 업로드 파일 형식 자동 확인 — 반드시 포함
- **포함 이유**: 이 과제에서 실데이터는 납품 후 들어온다. 형식 확인이 없으면 첫 실데이터의 문제는 센서 업체·유지보수 업체·의뢰사 사이의 책임 공방이 된다 (F04).
- **단계**: 최소(헤더·필수 컬럼·타입·중복 해시) → 권장(단위 물리 검사·실제 Hz·결측·시간 범위·인코딩) → 확장(센서 업체용 규격 검증기).
- **빼면 나중에 붙이는 법**: 업로드를 "원본 저장 → 파싱"의 2단계로 분리해 두면 검사기는 그 사이에 끼울 수 있다. 단, 그 사이에 들어온 불량 데이터는 사후에 재처리로 걸러야 한다.

### 7-4. 공고만으로 판단이 어려워 확인이 필요한 것

## 8. 성공 기준 초안 (제안 필수 2)

검수조서에 그대로 옮길 수 있게 **측정 가능한 문장**으로 쓴다.

1. **전 흐름**: 가상 선수 10명·세션 100개(원본 약 600만 행 [계산: 100 × 60,000])로 등록 → 동의 → 업로드·연결 → 조회 → 비교 → 추출이 검수 체크리스트 상 오류 0건으로 통과한다.
2. **본인 데이터만**: 선수 계정으로 다른 선수의 세션 주소·API를 직접 호출해도 0건이 반환된다 (DB 레벨 권한 테스트 스크립트를 결과물로 납품).
3. **형식 자동 확인**: 불량 CSV 8종(인코딩·단위·Hz·결측·9시간 시차·중복·지수 표기 타임스탬프·필수 컬럼 누락)이 각각 정확한 사유로 경고 또는 차단된다.
4. **비교 신뢰**: 측정 조건이 다른 두 세션을 비교하면 100% 경고가 뜨고, 다른 항목이 표시된다.
5. **그래프 속도**: 100Hz 10분 세션 그래프가 일반 노트북 브라우저에서 2초 안에 표시된다 [목표치 — 검수 시 실측].
6. **엑셀**: 세션 요약 xlsx와 원본 CSV가 엑셀에서 한글 깨짐 없이 열리고, 자유 텍스트 셀의 수식 실행은 0건이다.
7. **인수인계**: 이 프로젝트에 참여하지 않은 개발자 1명이 README만 보고 1시간 안에 로컬 실행 + 가상 데이터 생성을 마친다 (리허설 1회를 검수에 포함).
8. **납품·명의**: 11/30 이전에 결과물 5종(소스·실행 URL·DB 구조·설치/운영 문서·결과보고서)과 증빙사진 포함 검수조서가 완료되고, 모든 계정(클라우드·저장소·도메인)이 의뢰사 명의다.
9. **개인정보**: 민감정보 별도 동의가 없는 선수는 업로드가 불가하고, 모든 조회·다운로드가 접속기록에 남는다.

### 9-2. 대안 B — 자체 서버 (Python FastAPI + PostgreSQL + Docker, 국내 VM)

## 10. 의뢰자 기획의 잘된 부분

1. **범위를 스스로 잘랐다.** 센서 알고리즘·실시간 앱·자동 연동·불균형 분석·사이즈 추천을 제외해 30일·400만원 MVP가 현실적이다. 미정 범위 3개도 정확히 그 경계에 놓여 있어 판단 질문이 명확하다.
2. **"가상 데이터로 테스트"를 명시했다.** 실데이터가 없다는 사실을 인정하고 검수 기준을 가상 데이터로 정의할 수 있게 해 두었다 → 시드 생성기·불량 픽스처·규격 검증기를 정식 결과물로 만들 근거가 된다.
3. **"다른 업체가 이어받을 구조"를 평가 기준에 올렸다.** 정부 과제 외주에서 흔한 '납품 후 고아 시스템'을 처음부터 막는 관점이다.
4. **익명 ID와 '본인 데이터만' 원칙을 처음부터 넣었다.** 법적으로 가명정보라는 점(F07)만 보완하면 그대로 쓸 수 있는 설계 방향이다.
