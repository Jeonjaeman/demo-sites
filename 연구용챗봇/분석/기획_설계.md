### 1-2. 문서 행간의 숨은 니즈

- **"학술 연구 목적"** → 진짜 요구사항은 "챗봇이 돌아간다"가 아니라 **"이 데이터로 논문을 쓸 수 있다"** 입니다. 그래서 재현성(모델 버전 고정), 배정 타당성(블록 무작위화), 윤리 절차(IRB 동의)가 기능 목록보다 우선합니다. 데모는 이 세 가지를 화면으로 증명합니다.
- **"기획 상태: 아이디어만 있는 상태" + "IT 프로젝트 관리 경험 없음"** → 기술 검토를 거치지 않은 초안입니다. 명시된 스택(Streamlit + 단일 CSV)이 바로 데이터 유실 지점이므로, 개발사가 먼저 짚어야 합니다.
- **"14일 / 300만원"** → 범위를 늘릴 여지가 없습니다. 화면 수를 늘리는 대신 **실패하면 실험 전체가 무효가 되는 지점**에 공수를 집중하는 편이 맞습니다.
- **"클라이언트 준비 사항: 프롬프트 초안"** → 프롬프트는 연구자가 계속 다듬습니다. 따라서 프롬프트 편집 기능만으로는 부족하고, **수정 시점 이후 데이터의 조건이 달라지는 문제**를 버전 기록으로 막아야 합니다.

## 2. 웹 리서치 — 의뢰자가 놓친 부분 (전부 데모에 반영)

### ① Streamlit + 단일 CSV = 동시 참가자에서 데이터 유실 (치명적)

요구사항의 저장 방식은 "DB 없이 CSV"입니다. 그러나 Streamlit 커뮤니티와 이슈 트래커에는 **단일 CSV를 DB처럼 쓰면 동시 사용자 환경에서 동작하지 않는다**는 점, 그리고 동시 요청 시 참가자 간 데이터가 섞이는 사례가 보고되어 있습니다. 실험은 모집 공고 직후 참가자가 몰리므로, 하필 가장 중요한 시점에 데이터를 잃습니다.

**대안 (데모 적용):** **CSV 산출물 형식은 그대로 두고 저장 계층만 SQLite로 교체**합니다. 파일 하나로 관리되어 별도 DB 서버가 필요 없다는 장점은 동일하고, 쓰기는 트랜잭션으로 직렬화되어 유실이 없습니다. 연구자는 기존과 똑같이 관리자 화면에서 CSV를 내려받습니다.

### ② 모델 스냅샷 미고정 = 실험 중간에 자극이 바뀜

`gpt-4o` 같은 별칭을 쓰면 OpenAI가 백엔드 모델을 갱신할 때 **실험 도중 자극(stimulus)이 바뀝니다.** 앞부분과 뒷부분 참가자가 사실상 다른 조건에서 응답한 셈이 되어 데이터를 논문에 쓰기 어려워집니다. 날짜 스냅샷 고정은 OpenAI의 권장 방식이며, 연구 논문들도 모델 ID를 스냅샷으로 명시합니다.

**대안 (데모 적용):** 날짜 스냅샷을 고정하고 **모든 화면에 상시 노출**합니다. 응답 레코드마다 모델 ID·temperature·seed·프롬프트 버전을 함께 저장해, 논문 방법론 절에 그대로 옮길 수 있게 했습니다. 실험 기간 중 스냅샷 은퇴 공지도 모니터링 대상입니다.

### ③ 참가자 사전 동의(IRB) 절차 부재

대화 데이터를 사람에게서 수집하므로 **인간대상연구**에 해당하며, 온라인 진행이라는 이유만으로 동의를 면제받을 수 없습니다. 동의 절차 없이 모은 데이터는 게재 심사에서 문제가 되고 기관 IRB 심의도 통과하기 어렵습니다.

**대안 (데모 적용):** **첫 화면을 온라인 동의 절차로 구성**했습니다 — 연구 목적·수집 항목·보관 기간·철회권·문의처 고지, 3개 항목 개별 체크, 동의 시각과 동의서 버전 기록.

### ④ 단순 무작위 배정은 집단 크기가 어긋남

"4개 집단 분기"만 적혀 있어 단순 무작위로 구현하기 쉽습니다. 그러나 **표본이 작을수록 집단 간 불균형 확률이 높고**, 불균형은 분산 차이를 만들어 검정력을 떨어뜨립니다. 반대로 블록 크기를 고정하면 다음 배정을 예측할 수 있게 됩니다.

**대안 (데모 적용):** **가변 블록 크기(4/8) 블록 무작위화.** 데모 46명 기준 집단 간 차이 ±1명을 유지하며, 연구자 콘솔에서 균형을 실시간 확인할 수 있습니다.

### ⑤ 새로고침 한 번에 참가자 데이터 소실

Streamlit의 세션 상태는 새로고침하면 초기화됩니다. 참가자가 실수로 F5를 누르면 그때까지의 대화가 사라지고 그 참가자는 재모집 대상이 됩니다.

**대안 (데모 적용):** **매 턴 즉시 저장(write-through) + 참가자 ID로 세션 복구.**

### ⑥ 자유 대화에 개인정보가 섞여 들어옴

참가자는 대화 중 이름·연락처·소속을 자연스럽게 언급합니다. 요구사항 3-2는 접근 통제만 다루는데, 실제로는 **수집 단계에서 들어오는 식별 정보**가 더 큰 문제입니다.

**대안 (데모 적용):** **저장 직전 PII 자동 마스킹**(전화·이메일·주민번호 패턴) + 다운로드 시 비식별 옵션.

## 4. 화면 구성

```
index.html (참가자)
├─ 1. 연구 참여 동의  — IRB 고지 6개 항목 + 3개 체크 (요구사항에 없던 제안)
├─ 2. 참가자 ID 입력  — 형식 검증 · 1인 1회 차단
├─ 3. 조건 배정       — 가변 블록 무작위화 결과
├─ 4. 챗 화면         — ChatGPT UI · 스트리밍 · 턴 카운터 · 최소 6턴 후 종료 활성
└─ 5. 완료            — 완료 코드 · 참여 요약(모델 ID 포함)

admin.html (연구자)
├─ 대시보드   — KPI 4종 · 집단 균형 바 · 실험 설정표(논문 기재용)
├─ 프롬프트   — 4개 조건 편집 · 저장 시 버전 기록 · 변경 이력
├─ 데이터     — 참가자 46명 · 집단 필터 · 대화 로그 뷰어 · CSV 3가지 반출
└─ 검토 항목  — 리스크 6건 + 각 항목별 적용한 대안
```

**실험 설계(예시):** 2(공감 표현 유·무) × 2(근거 제시 유·무) 피험자간 요인설계 → A 중립형 / B 공감형 / C 근거형 / D 공감＋근거형. 데모에서 같은 질문을 넣으면 조건별로 실제 다른 응답이 생성됩니다.

## 5. 실서비스 제안 스택

- **Streamlit** — 요구사항대로 유지. 14일 일정에 가장 현실적이고 연구자가 직접 수정하기도 쉬움
- **저장은 SQLite** — 위 ①의 유실 문제 해결. CSV는 반출 시점에 생성 (산출물 형식 동일)
- **OpenAI Python SDK** — `stream=True`로 체감 지연 감소, **날짜 스냅샷 고정**, temperature·seed 기록
- **비용 통제** — 참가자당 최대 턴 수 제한(20턴), max_tokens 상한, 일일 예산 상한 도달 시 신규 참여 자동 차단
- **배포** — 단일 VM + systemd, 일 1회 SQLite 스냅샷 백업 (연구 데이터 특성상 백업이 곧 보험)

14일 일정: 1~3일 설계 확정(동의서·프롬프트·스키마) → 4~8일 참가자 챗 + 배정 + 저장 → 9~11일 연구자 콘솔·CSV → 12~13일 **파일럿 테스트**(실제 참가자 5명 리허설) → 14일 산출물·인수인계
